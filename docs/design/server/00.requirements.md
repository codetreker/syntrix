# Syntrix Requirements

Status: accepted product requirements; platform boundaries remain a target architecture.

## Product and actor boundaries

Syntrix provides a general-purpose realtime document backend. Chat is the
reference stress scenario: frequent small writes, realtime delivery, historical
scrollback, and presence updates. These requirements apply to application
runtimes inside developer-owned instances.

The [system architecture](../../architecture.md) and
[boundary decision](../../../.agents/notes/proposed/architecture/2026-10-10-platform-console-instance-boundaries.md)
separate three products and authorities:

| Surface | Principal | Responsibility |
|---|---|---|
| Management | Syntrix employee | Platform scheduling, resource operations, fleet monitoring |
| Console | Developer | Developer account and management of one or more owned instances |
| Instance | Application end user | Project-scoped authentication and business document access |

A project belongs to an instance and owns an isolated identity realm. One project
can use multiple logical Syntrix databases. Employee accounts, developer accounts,
and application accounts have distinct token authority; an account or role in one
surface must not grant authority in another.

## Data ownership

An instance's private PostgreSQL stores system data: projects, application users,
OAuth/OIDC providers and clients, sessions, and logical database configuration and
metadata. MongoDB stores developer business documents. Instance Identity is a
runtime service alongside Query, Indexer, Puller, Streamer, and Trigger. Its target
includes its own OAuth/OIDC issuer and external-provider login within each
project's realm.

The existing Go runtime has users and database metadata in PostgreSQL, document
storage and token revocation in MongoDB, global user identity, and JWT login. It
has no project identity realms or complete OAuth/OIDC flow. The embedded
`packages/console` application is not the separate developer Console service.
The accepted boundaries describe required delivery, not implemented isolation.

## Functional requirements

- CRUD supports create, read, update, and delete of documents.
- Queries support filtering, ordering, and pagination, such as the last 50
  messages in `rooms/room-X/messages` before a selected timestamp.
- Batch operations support bulk changes, such as marking messages read.
- Only single-document atomicity is guaranteed. Cross-document transactions are
  unsupported; trigger workers require idempotent writes or compensation for a
  partially successful batch.
- Server-initiated realtime delivery targets less than 200 ms of server
  processing time. MongoDB change streams feed the realtime path; storage
  sharding and service scaling must retain bounded latency under high write load.
- Connections support the application presence scenario; presence guarantees
  require their own explicit lifecycle contract.

## Consistency, reliability, and scale

Single-document operations require strong CAS consistency. Cross-client
synchronization may converge eventually. Offline clients read and write locally
and synchronize after reconnection through the client replica; conflicts require
LWW or a documented custom merge policy.

Capacity targets include more than 10,000 active connections per node and
terabyte-scale business data. Stateless API/realtime services and sharded storage
support horizontal scale. Chat workload evaluation includes append-heavy writes,
edits/deletes, and time-ordered reads.

## Security

Application authentication uses validated tokens under the instance project's
identity authority. Document authorization must support data-driven rules, such
as requiring `request.auth.userId` to occur in `resource.data.members`. Identity
validation and database selection alone do not establish document permission.

Management operations require employee authorization; Console operations require
developer ownership or an explicitly delegated grant. The instance runtime must
validate project, database, principal, and token authority together. The current
unscoped JWT/admin model does not satisfy this target merely because database
names appear in URLs.

## Technology and deployment constraints

Go implements instance services. MongoDB provides business document storage and
change streams; PostgreSQL owns private instance system data. The TypeScript
client SDK provides REST and replica functionality with RxDB-backed local
storage. Local development uses Docker Compose; production deployment targets
Kubernetes. Consolidating instance services into one development process does
not collapse Management, Console, and instance authority into one product.

Optimize the receive, persist, and push critical path for the realtime target.
Retain single-document atomicity to bound storage coordination, and evaluate
rules against document contents at the data API boundary.
