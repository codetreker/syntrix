# Puller Service Architecture

**Date:** December 29, 2025
**Status:** Implemented
**Component:** Change Stream Puller (Fan-out Service)

## 1. Overview

The Puller is a standalone service that acts as a centralized fan-out layer between MongoDB and multiple event consumers. It watches MongoDB change streams, normalizes events, manages checkpoints, buffers events in PebbleDB, and distributes events to downstream consumers via gRPC streaming.

### 1.1 Design Goals

- **Single MongoDB Connection**: Minimize load on MongoDB by maintaining only one change stream connection per backend
- **Fan-out**: Distribute events to multiple independent consumers (Engine Index, Streamer, Trigger Service)
- **Reliability**: Ensure no event loss through checkpoint management and resume token persistence
- **Scalability**: Support horizontal scaling (see [future/001.shard-scaling.md](future/001.shard-scaling.md) for shard-based consumer scaling)
- **Observability**: Provide metrics and health checks for monitoring

## 2. Core Components

### 2.1 Change Stream Consumer

Establishes and maintains MongoDB change stream connection, handles connection failures and automatic reconnection, applies resume tokens on startup and after failures, and detects gaps in event stream.

Default capture includes both `documents` and `sys`. Custom configurations must
include both configured source namespaces so bootstrap and subsequent live
capture cover the same document inventory.

### 2.2 Event Normalizer

The Mongo adapter converts native change events to the canonical event format,
preserves typed document values and independent logical identity, and computes
event hashes for deduplication. Physical delete operations are filtered during
native capture. Logical deletion remains an update or replacement carrying a
tombstone.

### 2.3 Checkpoint Manager

Persists a single resume token for the change stream alongside buffered events in PebbleDB, recovers the token on startup, and provides atomic checkpoint updates by sharing the same write batch as the event. In multi-instance deployments, each instance maintains its own resume token in its local buffer.

### 2.4 Event Buffer (PebbleDB)

Persists events locally for durability and replay. Supports multiple consumers at different positions. Uses ordered key storage for efficient range scans. A failed batch stops later commits and remains observable through subsequent writes, checkpoint reads, and shutdown.

| Setting | Enforced limit |
|---|---|
| `queue_size` | Pending plus flushing events per backend; full capacity pauses admission before encoding |
| `batch_size` | Events in each commit; a full smaller queue also triggers a flush |

Capacity waiting ends on cancellation, closure, or write failure. Healthy shutdown drains admitted events in capped batches. These are event-count limits, not byte limits; full queues can delay capture and live delivery. The [write-admission decision](../../../../.agents/notes/implemented/bug-fix/2026-09-07-puller-pending-write-bound.md) records the failure and recovery constraints.

The buffer format marker is `typed-events-v2`. Opening a nonempty unversioned
buffer or a buffer with another format fails and requires an explicit offline
rebuild. Event decoding also rejects absent or incompatible wire versions.

| Encoded payload | Admission limit |
|---|---|
| Complete durable typed JSON event envelope | 64 MiB |
| Complete Puller protobuf response, including progress and envelope fields | 65 MiB |

Typed nodes can expand substantially beyond the source BSON size. These limits
do not guarantee that every valid 16 MiB Mongo document shape is admissible.
Oversized events fail capture before buffer admission or checkpoint advancement;
operators must reduce source data or coordinate a budget change and rebuild
capture. Sender and receiver enforce the complete RPC-message bound, and delivery
progress advances only after validation and successful send.
Buffer lineage identifies one durable buffer history; retained-position
validation prevents a consumer from treating a recreated buffer or pruned
history as continuous replay.

### 2.5 gRPC Server

Exposes server-side streaming API for consumers. Streams merged events from all backends. Applies catch-up coalescing when consumer is behind threshold. Consumer manages its own progress (Puller does not store it).

Local and gRPC subscriptions remain independent when their `consumer_id` labels match or are empty. Each subscription receives broadcasts and cleans up its own registration; labels are diagnostic only. The [subscription identity decision](../../../../.agents/notes/implemented/bug-fix/2026-09-09-puller-subscription-identity.md) records the lifecycle boundaries.

## 3. Canonical Event Schema

**IMPORTANT**: This section defines the Puller event schema. For the complete field naming conventions across all system components, see [Field Naming Conventions](../02.field_naming.md).

### 3.1 JSON Wire Format

Durable event envelopes use `wireVersion: 2`. Document and update-description
envelopes carry their own version and use the shared
[typed value encoding](../../../reference/filters.md#typed-values). For example:

```json
{
  "change_event": {
    "wireVersion": 2,
    "eventId": "unique-event-id",
    "database": "database-id",
    "mgoColl": "data",
    "mgoDocId": "storage-key",
    "opType": "insert",
    "fullDoc": {
      "wireVersion": 2,
      "id": "storage-key",
      "database": "database-id",
      "fullpath": "orders/order-1",
      "collection": "orders",
      "logicalId": "order-1",
      "collectionHash": "collection-hash",
      "parent": "",
      "updatedAt": 1234567890000,
      "createdAt": 1234567890000,
      "version": 1,
      "data": {
        "type": "object",
        "value": { "quantity": { "type": "int64", "value": "9007199254740993" } }
      },
      "deleted": false
    },
    "clusterTime": { "T": 1234567890, "I": 1 },
    "timestamp": 1234567890000,
    "backend": "backend-name"
  },
  "progress": "opaque-progress-marker"
}
```

### 3.2 Field Specifications

| Field | JSON Key | Type | Required | Notes |
| ----- | -------- | ---- | -------- | ----- |
| Change Event | `change_event` | object | For a data frame | Canonical event payload; absent on a readiness frame |
| Progress | `progress` | string | Yes | Opaque continuation marker |
| Ready | `ready` | bool | No | Control frame confirming verified replay has reached live mode |
| Wire Version | `wireVersion` | integer | Yes | Event envelope version, currently `2` |
| Event ID | `eventId` | string | Yes | Source-change identity for deduplication |
| Database ID | `database` | string | Yes | Explicit logical database |
| Mongo Collection | `mgoColl` | string | Yes | Adapter-native physical collection |
| Mongo Document ID | `mgoDocId` | string | Yes | Adapter-native storage key |
| Operation Type | `opType` | string | Yes | Lowercase source operation |
| Full Document | `fullDoc` | object | For insert/update/replace | Versioned explicit document envelope |
| Update Description | `updateDesc` | object | No | Versioned envelope with typed `updatedFields`, removed field names, and array truncations |
| Cluster Time | `clusterTime` | object | Yes | Source ordering metadata `{T, I}` |
| Transaction Number | `txnNumber` | int64 | No | Present for a transaction |
| Timestamp | `timestamp` | int64 | Yes | Unix milliseconds |
| Backend | `backend` | string | No | Backend identifier |

### 3.3 Operation Types

Source operations are lowercase `insert`, `update`, `replace`, and `delete`.
The Mongo native capture adapter filters physical `delete` events before
buffering. Business conversion ignores a physical delete if one is supplied
directly.

Indexer also accepts a documentless physical-delete input as a no-op projection
with progress advancement. A storage hash cannot identify logical postings; source
materialization rejects orphan candidates, and maintenance rebuilding reclaims
them. This path does not guess identity or stop unrelated indexes.

Syntrix logical deletion is an update or replacement carrying a tombstone
(`deleted=true`, cleared `data`, retained metadata). It remains a business deletion
notification. See [deletion semantics](../core/storage/03.stores.md#document-deletion-and-physical-cleanup).

### 3.4 Full Document Contract

`fullDoc` carries storage identity (`id`), logical database, collection, full path,
and logical document ID independently of business `data`. Decoding validates
that the logical ID agrees with the full path and collection. The envelope also
preserves version, timestamps, parent, collection hash, and deletion state.
Generic public `StoredDoc` JSON is not the internal transport representation.

The Mongo normalizer converts only the known top-level metadata dates
`created_at`, `updated_at`, and `sys_expires_at` to Unix-millisecond int64 values
in full documents and update deltas. Business date values are not silently
converted into query numbers and remain unsupported by the typed value domain.

Document data and update values retain exact signed integers, finite binary64
values, and recursively typed objects and arrays through buffer writes, replay,
and gRPC. Tagging every value prevents business properties named `type` or
`value` from colliding with codec metadata. Missing or incompatible versions and
invalid values fail explicitly. The
[indexed-query filter decision](../../../../.agents/notes/implemented/bug-fix/2026-09-07-indexed-query-filter-semantics.md)
records the identity and precision requirements.

The Mongo adapter enables `UpdateLookup` for update and replace operations and
rejects events without required full-document enrichment. Lookup may observe
state newer than the source change; the payload is not a historical snapshot.

### 3.5 Identity and Checkpoints

Logical identity is `(database, collection, logicalId)`. Business data cannot
supply or override that identity. The full path retains the document's concrete
source scope, while the storage key and event ID have separate roles.

`EventID` identifies a source change; `BufferKey` orders it in the backend buffer.
The native source resume token remains a separate capture checkpoint committed
with buffered events. Typed encoding does not reinterpret any of these values.
Consumer progress adds buffer lineage and retention validation around buffer
positions; it is not a native source token or a Store `WatchCheckpoint`.

## 4. Event Flow

### 4.1 Normal Flow

1. MongoDB emits change event
2. ChangeStreamConsumer receives event
3. EventNormalizer converts to internal format
4. Event and native resume token enter the buffer's batch queue
5. Background writer commits the events and latest token atomically
6. Live delivery follows queue admission and may precede step 5
7. Consumer saves progress marker locally

### 4.2 Startup Recovery Flow

1. Puller starts
2. CheckpointManager loads resume token; a read failure stops the backend
3. If resume token exists → resume from token
4. If no resume token → start from "now" (or "beginning" based on bootstrap mode)
5. ChangeStreamConsumer establishes connection
6. Begin processing events

### 4.3 Gap Detection and Recovery

Long event intervals (default: 5 minutes) produce diagnostic warnings; inactivity alone does not establish lost history.

| Condition | Capture behavior |
|---|---|
| Native connection failure | Retry using the existing durable resume token |
| Checkpoint read or event-processing failure | Stop the backend before later events can pass the failure |
| Failed cache batch | Stop further batch commits and retain the original failure |
| Unusable resume token or unavailable history | Stop the backend and preserve its checkpoint |

The [capture failure decision](../../../../.agents/notes/implemented/bug-fix/2026-09-08-puller-capture-failures.md) owns these error paths. Verified subscriptions expose buffer-lineage and retained-history failures;
source-history loss requires the explicit offline rebuild described in
[offline bootstrap and startup](../indexer/04.storage.md#offline-bootstrap-and-startup).

## 5. gRPC API

### 5.1 Service Definition

A single gRPC server handles all backends. Consumers subscribe to a merged event stream without knowing which backend events come from.

| Operation | Contract |
|---|---|
| `Subscribe` | Resume from an opaque marker's complete boundary timestamp group, or start at the current head when `after` is empty; boundary events may repeat |
| `BootstrapBoundary` | Require quiesced writers, active capture, empty reset buffers, and a durable source checkpoint for every backend; flush admitted writes and return their lineages with empty replay positions |
| `ValidateBoundary` | Require the configured backend set and active capture; reject another lineage, unknown position, or unavailable replay history |

`SubscribeRequest` carries `consumer_id`, `after`, `coalesce_on_catch_up`, and
`require_ready`. Consumer labels are diagnostic. With `require_ready`, the
subscription verifies source readiness and replay and emits a `ready` control
frame after registration and all replay events reach the consumer stream. Data
frames carry a canonical change event and progress; readiness frames have no
change event. Both local and remote verified subscriptions deliver this barrier
in band. Sending it does not establish downstream readiness: the Indexer applies
all preceding events, checks exact opaque equality between applied progress and
the barrier, and flushes durable state before becoming ready. Verified replay
opens snapshots under retention synchronization, so pruning cannot remove
required history between position validation and replay setup.

For each backend, delivery tracks the latest cluster timestamp and the EventIDs
already sent at that timestamp. Different IDs sharing a timestamp are delivered;
only repeated identities within that group and already completed older groups
are suppressed. Progress and the delivered-ID set change only after a successful
channel or gRPC send. The set is replaced when delivery reaches a newer timestamp.

A verified subscription reports an attempt failure and closes. The Indexer owns
recovery: it clears readiness, cancels the failed attempt, flushes and reloads
applied progress, validates that boundary, and subscribes again. Explicit
temporary failures use a one-second backoff with at most ten consecutive retry
attempts; a new in-band barrier must establish readiness. Owner cancellation
ends retries. Lineage mismatch, pruned history, unknown positions, and codec
failures require maintenance. Ordinary `Subscribe` retains its automatic
reconnection behavior; verified consumers need the validated recovery sequence.

The gRPC `full_doc` and `update_desc` byte fields carry the same versioned typed
envelopes used by durable storage. Native adapter metadata remains in the change
event fields. Local subscriptions and remote consumers share the same logical
identity and value semantics.

### 5.2 Progress Marker

The `progress` field in each event is an opaque string that encodes the current position across all backends. Consumers should:

1. Save the `progress` field from the last successfully processed event
2. Pass it as `after` when reconnecting; events in that timestamp group may repeat
3. Treat it as opaque: do not synthesize markers or compare their bytes to infer order

A verified boundary marker binds positions to every backend's durable buffer
lineage, including an empty position for a backend with no events. Validation
checks exact backend coverage, source readiness, lineage, and retained replay history; an
invalid or expired marker cannot silently restart at the head. Resume replays the
whole boundary timestamp group because the EventID hash suffix does not encode
source order. A new subscription starts with no delivered identities for that
group. Verified replay fails if pruning removed any part of the required group,
even when the marker's own event remains available. This changes consumer replay
semantics without changing native resume-token checkpoints or the marker format.
Offline index
bootstrap and startup use `BootstrapBoundary`, `ValidateBoundary`, and verified
subscription readiness together. The required writer quiescence, reset, scan,
and activation ordering is owned by
[offline bootstrap and startup](../indexer/04.storage.md#offline-bootstrap-and-startup).

### 5.3 Consumer States

- **Real-time**: Position near head, events forwarded as-is
- **Catching-up**: Position behind by `catch_up_threshold`, optional coalescing applied

### 5.4 Subscription Admission

`puller.grpc.max_connections` bounds active `Subscribe` RPCs per Puller gRPC
Server to limit per-subscription queues and replay work. Its default is 100;
nonpositive values use that default.

| Condition | Behavior |
|---|---|
| Several subscriptions share a TCP connection or consumer label | Count each RPC separately, including empty labels |
| One subscription covers several backends or changes delivery mode | Hold one slot throughout catch-up and live delivery |
| Capacity is full | Return `ResourceExhausted` before allocating a subscriber queue or opening replay |
| An admitted handler exits, including cancellation or failure | Release its slot |
| An initialized Server starts shutdown | Close existing registrations and reject new admission with `Unavailable` |

Capacity checks and registration are atomic with each other and shutdown. The
client observes server rejection through the stream's `Recv`; obtaining a stream
object alone does not confirm admission. Local subscriptions do not consume this
quota. The [admission decision](../../../../.agents/notes/implemented/bug-fix/2026-09-07-puller-grpc-admission.md)
records the counting rationale and lifecycle limits.

## 6. Key Design Decisions

### 6.1 PebbleDB Event Buffer

We use PebbleDB as a local event buffer because:

- Durable storage survives Puller restart
- Supports multiple consumers at different positions
- Ordered key storage enables efficient range scans
- LSM tree optimized for write-heavy workloads
- Configurable size limit with automatic cleanup

### 6.2 At-Least-Once Delivery

- Events and the latest capture token commit atomically; live publication can precede that commit, so this alone does not establish end-to-end at-least-once delivery
- Consumers must be idempotent (handle duplicate events)
- Events may be delivered multiple times on retry, reconnect, etc.

### 6.3 Catch-up Coalescing

When a consumer falls behind by more than `catch_up_threshold` events:

- Multiple updates to the same document are merged
- An explicitly supplied insert followed by physical delete can cancel; native capture filters physical deletes, while a logical tombstone remains an update or replacement
- Reduces catch-up time for slow consumers
- Consumer can disable via `coalesce_on_catch_up: false`
