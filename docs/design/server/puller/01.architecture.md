# Puller Service Architecture

**Date:** December 29, 2025
**Status:** Implemented
**Component:** Change Stream Puller (fan-out service)

## 1. Overview

Puller is the fan-out layer between MongoDB change streams and independent event
consumers. It maintains one native change stream per configured backend,
normalizes events, persists events and source checkpoints in PebbleDB, and serves
local and gRPC subscriptions through one transport-neutral delivery state
machine.

### 1.1 Design Goals

- Maintain one MongoDB change stream per backend rather than one per consumer.
- Fan out an ordered per-backend event stream to Indexer, Streamer, Trigger, and
  other consumers.
- Preserve durable source checkpoints and retained replay boundaries.
- Bound write and subscription queues and recover slow subscribers through
  retained replay.
- Keep local and gRPC delivery behavior aligned while preserving their distinct
  transport and error contracts.
- Expose capture health, admission failures, boundary failures, and replay
  failures rather than silently treating them as continuity.

Horizontal consumer ownership is separate future work; see
[shard-based consumer scaling](future/001.shard-scaling.md).

### 1.2 Position in the System

```text
MongoDB backends
       |
       v
+---------------- Puller ----------------+
| Change stream consumer                 |
|       |                                |
|       v                                |
| Event normalizer                       |
|       |                                |
|       +--> native checkpoint           |
|       |                                |
|       v                                |
| Durable event buffer (PebbleDB)        |
|       |                                |
|       +--> Subscriber + live queue ----+----+
|       |                                |    |
|       v                                |    |
| Shared subscription runner             |    |
|       |                                |    |
|       +--> local adapter               |    |
|       +--> gRPC adapter                |    |
+----------------------------------------+    |
       |                                      |
       +--> Indexer / Streamer / Trigger <----+
```

Live publication may precede the durable buffer commit. Retained replay and
consumer checkpointing provide recovery within their stated boundaries, but
live delivery alone is not an end-to-end durability acknowledgment.

## 2. Core Components

### 2.1 Change Stream Consumer

Each backend owns a MongoDB change stream connection. The consumer applies the
last durable native resume token at startup and after retryable connection
failure. Checkpoint read failure, event-processing failure, an unusable resume
token, or unavailable source history stops that backend before later events can
pass the failure.

Default capture includes both `documents` and `sys`. Custom configurations must
include every source namespace used by bootstrap so the initial inventory and
subsequent live capture describe the same document set.

### 2.2 Event Normalizer

The Mongo adapter converts native changes to the canonical event format,
preserves typed values and logical identity, and computes event IDs used for
deduplication. Native capture filters physical delete operations. Logical
deletion remains an update or replacement carrying a tombstone.

Update and replace streams use `UpdateLookup`. The resulting full document can
reflect state newer than the source change and is not a historical snapshot.

### 2.3 Checkpoint Manager

Each backend persists one native resume token with the corresponding buffered
events in the same PebbleDB write batch. A Puller instance with multiple
backends has one independent token per backend. A deployment with multiple
Puller instances has independent local buffers and tokens.

The native token is capture state. Consumer progress is a separate opaque marker
over retained buffer positions and lineages.

### 2.4 Event Buffer

PebbleDB stores normalized events for durable replay and supports consumers at
different positions. Ordered keys allow efficient scans by backend position.
A failed batch stops later commits and remains observable through subsequent
writes, checkpoint reads, and shutdown.

| Setting | Enforced limit |
|---|---|
| `queue_size` | Pending plus flushing events per backend; full capacity pauses admission before encoding |
| `batch_size` | Events in each commit; a full smaller queue also triggers a flush |

Capacity waiting ends on cancellation, closure, or write failure. Healthy
shutdown drains admitted events in capped batches. These limits count events,
not bytes; full queues can delay capture and live delivery. The
[write-admission decision](../../../../.agents/notes/implemented/bug-fix/2026-09-07-puller-pending-write-bound.md)
owns the failure and shutdown rules.

The buffer format marker is `typed-events-v2`. Opening a nonempty unversioned
buffer or a buffer with another format fails and requires an explicit offline
rebuild. Event decoding rejects missing and incompatible wire versions.

| Encoded payload | Admission limit |
|---|---|
| Complete durable typed JSON event envelope | 64 MiB |
| Complete Puller protobuf response, including progress and envelope fields | 65 MiB |

Typed nodes can expand beyond the source BSON size. These limits do not ensure
that every valid 16 MiB MongoDB document is admissible. Oversized events fail
before buffer admission or checkpoint advancement. Sender and receiver enforce
the complete RPC-message bound, and subscription progress advances only after
validation and successful delivery.

Buffer lineage identifies one durable history. Retained-position validation
prevents a consumer from treating a recreated buffer or pruned history as a
continuous stream.

Scheduled cleanup preserves complete timestamp groups as resumable boundaries:

| Cleanup policy | Protected history |
|---|---|
| Age | Every group inside the retention window and the newest persisted group before its cutoff |
| Capacity | At least the newest persisted group; older history may be evicted under pressure |

The age predecessor protects an idle subscription when the first newer event is
committed before delivery advances. Pending, uncommitted events do not release a
durable boundary. If a protected boundary alone exceeds `max_size`, cleanup
stops; the configured size is a soft cleanup target. Explicit deletion and older
capacity eviction can still invalidate a boundary.

### 2.5 Subscriber

Every local subscription and gRPC `Subscribe` RPC has an independent
`Subscriber`, even when consumer labels match or are empty. The subscriber owns:

- the current per-backend delivery positions;
- delivered EventIDs in each current timestamp group;
- a bounded live-event queue;
- a serialized recovery latch and capacity-one notification;
- closure independent of recovery notification.

The first rejected live admission latches recovery. Later events remain excluded
from live admission until the runner drains the stale queue and rearms recovery
immediately before retained replay. The
[subscription identity decision](../../../../.agents/notes/implemented/bug-fix/2026-09-09-puller-subscription-identity.md)
owns registration and label semantics.

### 2.6 Shared Subscription Runner

`internal/puller/core.RunSubscription` is the transport-neutral state machine for
local and gRPC delivery. It owns replay/live/recovery transitions, iterator
closure, Ready-once behavior, maintenance ordering, boundary-group
deduplication, prospective progress construction, and progress advancement after
successful delivery. A nil iterator or live-queue event is a terminal source
contract violation; it cannot be mistaken for an empty replay result.

Adapters provide callbacks for:

- opening ordinary or verified replay;
- delivering one event with its prospective progress marker;
- publishing the verified Ready barrier;
- periodic boundary validation or heartbeat work;
- resetting transport timers when live mode is entered.

The runner returns a structured terminal result with an exit kind, active phase,
primary error, and iterator cleanup error. Local and gRPC adapters map that
result without embedding transport status in the shared state machine. The
[adaptive consumption design](02.adaptive-consumption.md) defines the exact
transition and error contracts; the
[subscription state-machine decision](../../../../.agents/notes/implemented/architecture/2026-09-07-puller-subscription-state-machine.md)
records the ownership rationale and alternatives.

### 2.7 Local and gRPC Adapters

The local adapter owns channel delivery, terminal `PullerEvent` values for
verified subscriptions, the `onReady` callback, and one-second verified boundary
checks. Its live queue holds 1,000 events.

The gRPC adapter owns RPC admission, protobuf conversion, complete response-size
validation, Ready and heartbeat frames, gRPC status mapping, and Server
shutdown. Its live queue uses `puller.grpc.channel_size`, defaulting to 10,000
when nonpositive.

Both adapters register before replay opens. A nonempty marker enters retained
replay; an ordinary empty marker starts at the current head. Verified
subscriptions require a valid boundary and reject an empty marker.

## 3. Canonical Event Contract

The complete field naming convention is defined by
[Field Naming Conventions](../02.field_naming.md).

### 3.1 Durable JSON Envelope

Durable event envelopes use `wireVersion: 2`. Document and update-description
values use the shared [typed value encoding](../../../reference/filters.md#typed-values).

```json
{
  "change_event": {
    "wireVersion": 2,
    "eventId": "unique-event-id",
    "database": "database-id",
    "mgoColl": "data",
    "mgoDocId": "storage-key",
    "opType": "insert",
    "fullDoc": {
      "wireVersion": 2,
      "id": "storage-key",
      "database": "database-id",
      "fullpath": "orders/order-1",
      "collection": "orders",
      "logicalId": "order-1",
      "collectionHash": "collection-hash",
      "parent": "",
      "updatedAt": 1234567890000,
      "createdAt": 1234567890000,
      "version": 1,
      "data": {
        "type": "object",
        "value": {
          "quantity": { "type": "int64", "value": "9007199254740993" }
        }
      },
      "deleted": false
    },
    "clusterTime": { "T": 1234567890, "I": 1 },
    "timestamp": 1234567890000,
    "backend": "backend-name"
  },
  "progress": "opaque-progress-marker"
}
```

### 3.2 Fields

| Field | JSON key | Type | Required | Contract |
|---|---|---|---|---|
| Change event | `change_event` | object | Data frames | Canonical event payload; absent on Ready and heartbeat frames |
| Progress | `progress` | string | Yes | Opaque consumer continuation marker |
| Ready | `ready` | bool | No | One-time control frame after verified replay reaches live mode |
| Wire version | `wireVersion` | integer | Durable events | Event envelope version, currently `2` |
| Event ID | `eventId` | string | Data events | Source-change identity used for deduplication |
| Database ID | `database` | string | Data events | Logical database identity |
| Mongo collection | `mgoColl` | string | Data events | Adapter-native physical collection |
| Mongo document ID | `mgoDocId` | string | Data events | Adapter-native storage key |
| Operation type | `opType` | string | Data events | `insert`, `update`, `replace`, or `delete` |
| Full document | `fullDoc` | object | Insert/update/replace | Versioned typed document envelope |
| Update description | `updateDesc` | object | No | Versioned typed update envelope |
| Cluster time | `clusterTime` | object | Data events | Source order metadata `{T, I}` |
| Transaction number | `txnNumber` | int64 | No | Source transaction number |
| Timestamp | `timestamp` | int64 | Data events | Unix milliseconds |
| Backend | `backend` | string | Transport-dependent | Backend identifier |

### 3.3 Identity and Values

Logical document identity is `(database, collection, logicalId)`. Business data
cannot supply or override it. The full path identifies the concrete source
scope; storage key, event ID, buffer key, native resume token, and consumer
progress remain separate identities.

`fullDoc` preserves storage identity, logical identity, version, timestamps,
parent, collection hash, deletion state, and typed business data. Decoding
validates that logical ID agrees with full path and collection. Generic public
`StoredDoc` JSON is not the internal transport representation.

The normalizer converts only the known top-level metadata dates `created_at`,
`updated_at`, and `sys_expires_at` to Unix-millisecond integers. Business date
values remain outside the typed-value domain. Typed encoding preserves exact
signed integers, finite binary64 values, objects, and arrays. Missing versions,
incompatible versions, and invalid values fail explicitly. The
[indexed-query filter decision](../../../../.agents/notes/implemented/bug-fix/2026-09-07-indexed-query-filter-semantics.md)
owns the identity and precision requirements.

Physical MongoDB delete events are filtered during native capture. If supplied
directly, business conversion ignores a documentless physical delete. Indexer
can accept that input as a no-op projection with progress advancement; source
materialization rejects orphan candidates, and maintenance rebuilds reclaim
them. Logical tombstones remain business deletion notifications.

## 4. Event and Recovery Flows

### 4.1 Capture

1. MongoDB emits a native change.
2. The consumer obtains and normalizes the change.
3. The event and latest native resume token enter the backend batch queue.
4. Live fan-out may publish the normalized event.
5. The background writer commits events and the latest token atomically.
6. Retained replay becomes available from the durable buffer.

### 4.2 Capture Startup and Failure

1. Load the durable native resume token.
2. Resume from that token when present.
3. Without a token, start according to the configured bootstrap mode.
4. Establish capture and expose its readiness to verified-boundary operations.

Long event intervals, five minutes by default, produce diagnostics; inactivity
does not by itself prove a gap.

| Condition | Capture behavior |
|---|---|
| Native connection failure | Retry using the existing durable resume token |
| Checkpoint read or event-processing failure | Stop the backend before later events pass the failure |
| Failed cache batch | Stop later batch commits and retain the original failure |
| Unusable resume token or unavailable source history | Stop the backend and preserve its checkpoint |

The [capture failure decision](../../../../.agents/notes/implemented/bug-fix/2026-09-08-puller-capture-failures.md)
owns these error paths. Source-history loss requires the explicit offline rebuild
described by [Indexer storage](../indexer/04.storage.md#offline-bootstrap-and-startup).

### 4.3 Subscription

1. The adapter parses the marker, applies admission, registers the subscriber,
   and validates a verified boundary.
2. A nonempty marker opens replay from the last successfully delivered progress.
3. The runner delivers replay events and closes the iterator.
4. The runner enters live mode and publishes Ready once when requested.
5. Live delivery continues until cancellation, closure, failure, or recovery.
6. Overflow drains stale queued events while admission remains fenced, rearms
   recovery, and returns to step 2.

Replay includes complete boundary timestamp groups. The subscriber tracks the
EventIDs delivered at its current timestamp, preserving distinct siblings and
suppressing overlap between replay and live delivery. A new subscription has no
such in-memory set, so the boundary group may repeat.

## 5. Service APIs

### 5.1 Subscription Operations

| Operation | Contract |
|---|---|
| Ordinary `Subscribe`, empty `after` | Register at the current head and deliver later live events; do not replay retained history |
| Ordinary `Subscribe`, nonempty `after` | Replay the complete boundary timestamp group and later events, then deliver live events |
| Verified `Subscribe` / `SubscribeReady` | Require and validate a nonempty boundary, replay it, emit one ordered Ready barrier, and continue live delivery |
| `BootstrapBoundary` | Require quiesced writers, active capture, empty reset buffers, and a durable source checkpoint for every backend; flush admitted writes and return lineages with empty positions |
| `ValidateBoundary` | Require exact configured backend coverage and active capture; reject another lineage, unknown position, or unavailable retained history |

The gRPC request carries `consumer_id`, `after`, `coalesce_on_catch_up`, and
`require_ready`. Consumer labels are diagnostic. Data frames carry a change event
and prospective progress. Ready and heartbeat frames carry progress without a
change event; only Ready has `ready=true`.

Ready means the barrier was delivered by Puller. Indexer establishes its stronger
readiness condition by applying all preceding events, checking exact opaque
progress equality, and flushing durable state before serving. Verified replay
opens snapshots under retention synchronization so pruning cannot remove needed
history between validation and replay setup.

A verified attempt terminates on failure. Indexer clears readiness, cancels the
attempt, flushes and reloads applied progress, validates that boundary, and
subscribes again. Explicit temporary failures use a one-second backoff with at
most ten consecutive retries. Owner cancellation ends retries. Lineage mismatch,
pruned history, unknown positions, and codec failures require maintenance.
Ordinary remote subscriptions retain their client-managed reconnection behavior.

### 5.2 Progress Marker

Consumers must:

1. Save the progress from the last successfully processed event.
2. Pass it as `after` when reconnecting and accept that its timestamp group may
   repeat.
3. Treat it as opaque; do not synthesize markers or compare encoded bytes for
   order.

A verified boundary binds a position to every backend's durable buffer lineage,
including an empty position for a backend with no events. Validation checks
backend coverage, active capture, lineage, and retained history. Resume replays
the complete boundary group because the EventID hash suffix does not encode
source order.

### 5.3 gRPC Admission

`puller.grpc.max_connections` bounds active `Subscribe` RPCs per gRPC Server. The
default is 100; nonpositive values use that default.

| Condition | Behavior |
|---|---|
| Several subscriptions share a TCP connection or consumer label | Count every RPC, including empty labels |
| One subscription covers several backends or moves between replay and live | Hold one slot for its full lifetime |
| Capacity is full | Return `ResourceExhausted` before queue allocation or replay |
| An admitted handler exits | Release its slot on cancellation, closure, or failure |
| An initialized Server starts shutdown | Close existing registrations and reject new admission with `Unavailable` |

Admission, registration, and shutdown are serialized. A client observes server
rejection through `Recv`; obtaining a stream object does not confirm admission.
Local subscriptions do not consume this quota. See the
[gRPC admission decision](../../../../.agents/notes/implemented/bug-fix/2026-09-07-puller-grpc-admission.md).

## 6. Delivery Decisions and Limits

### 6.1 At-Least-Once Consumer Handling

Consumers must be idempotent. Replay, reconnect, and complete timestamp-group
boundaries can redeliver events. Puller updates delivery progress only after a
successful local channel or gRPC send. The consumer owns the processed
checkpoint after applying the event.

### 6.2 Coalescing and Catch-Up Selection

When a subscription opens retained replay with coalescing enabled, the replay
source can merge multiple events for the same document. An explicitly supplied
insert followed by physical delete can cancel; native capture normally filters
physical deletes, while a logical tombstone remains an update or replacement.

The `catch_up_threshold` and default consumer coalescing settings are currently
loaded and validated but do not select runtime catch-up. Ordinary subscriptions
enter initial replay only for a nonempty marker. Queue overflow is the only live
transition to recovery replay. The
[consumer settings proposal](../../../../.agents/notes/proposed/bug-fix/2026-09-07-puller-admission-and-catch-up-settings.md)
owns future lag measurement, threshold policy, effective default coalescing, and
local admission.
