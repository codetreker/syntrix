# Puller Subscription State Machine

**Date:** January 1, 2026
**Status:** Implemented
**Component:** Puller Service (local and gRPC delivery)

## 1. Purpose

Puller subscriptions combine low-latency live delivery with retained replay. A
bounded live queue absorbs short bursts; when that queue overflows, the same
subscription recovers from the durable event buffer. The transition must wake an
idle consumer, prevent later events from crossing a rejected event, and preserve
transport-specific error behavior.

Local and gRPC subscriptions use one transport-neutral runner for replay, live
delivery, overflow recovery, readiness, and periodic maintenance. The
[subscription state-machine decision](../../../../.agents/notes/implemented/architecture/2026-09-07-puller-subscription-state-machine.md)
records why this control flow has one owner. The
[overflow wakeup decision](../../../../.agents/notes/implemented/bug-fix/2026-09-16-puller-overflow-wakeup.md)
owns the live-admission fence and notification rationale.

## 2. Ownership

| Owner | Responsibilities |
|---|---|
| Subscription adapter | Parse the request, apply admission limits, register and remove the subscriber, validate verified boundaries, supply transport callbacks, map the terminal result, and publish transport-specific diagnostics |
| Shared runner | Sequence replay, live delivery, recovery, Ready, and maintenance; filter empty-start history before coalescing; close each iterator exactly once; calculate prospective progress; advance progress only after successful delivery |
| `Subscriber` | Own the bounded live queue, delivered position and boundary-group identities, empty-start admission groups, recovery latch and notification, queue drainage, closure, and serialized live admission |
| Replay source and buffer | Validate retained boundaries, open raw replay snapshots, seek to per-backend admission floors for empty-start recovery, preserve timestamp groups, and iterate retained events |
| Downstream consumer | Persist processed progress only after applying an event; tolerate bounded replay duplicates and recover according to its own durability contract |

The runner has no gRPC, protobuf, local-channel, logging, timer, or boundary-source
dependency. Adapters pass those operations through callbacks so their blocking,
failure, and cancellation behavior remains explicit.

## 3. Start Semantics

Adapters register the subscriber before replay or live delivery begins. This
ensures a concurrent source event is represented by retained replay, the bounded
live queue, or both.

| Request | Initial state |
|---|---|
| Ordinary subscription with empty `after` | Start at the broadcast registration boundary in live mode; exclude earlier retained events from overflow recovery |
| Ordinary subscription with a valid nonempty `after` | Replay from that position, then enter live mode |
| Verified subscription | Require a valid nonempty boundary covering every configured backend and lineage; validate it before running, replay it, then publish Ready |
| Malformed marker | Reject before the shared runner starts |

Replay includes the complete timestamp group containing each backend position.
The boundary event and siblings may therefore repeat. EventID identifies members
already delivered by the current subscription; it is not an ordering key within
the timestamp group.

The runner opens empty-start recovery at each observed backend's first
post-registration broadcast group or later successful progress, whichever is
later. It excludes backends without a post-registration broadcast, then filters
older identities in the first group before applying `coalesce_on_catch_up`.
The configured `catch_up_threshold` does not currently select a runtime mode.
Initial replay depends on a nonempty marker, and later replay depends on the
recovery latch.

## 4. Shared State Machine

```text
adapter parse / admission / registration / verified validation
                              |
                              v
                    after is nonempty?
                     /             \
                   yes              no
                    |                |
                    v                |
              initial replay        |
                    |                |
                    +-------+--------+
                            v
                       enter live
                            |
                            v
                 publish Ready once, if enabled
                            |
                            v
       +------------- live select ----------------+
       | event | recovery | maintenance | stop    |
       +---+-------+------------+-----------+------+
           |       |            |           |
      deliver      |         maintain       exit
           |       |
           |       v
           |  drain while fenced
           |       |
           |  rearm recovery latch
           |       |
           +----> replay from last successful progress
                       |
                       +-- recovery relatched --> repeat
                       |
                       +-- caught up -----------> enter live
```

### 4.1 Replay

For each replay pass, the runner:

1. Uses the subscriber's current delivered progress to open an iterator.
2. Rejects a nil iterator event as a replay-source contract violation and skips
   only events rejected by boundary-group deduplication.
3. Computes the progress marker that would result from the next event.
4. Delivers the event and prospective marker through the adapter.
5. Commits the subscriber position and delivered EventID only after delivery
   succeeds.
6. Reads the iterator failure and closes the iterator exactly once.
7. Repeats catch-up if recovery was relatched during the pass; otherwise enters
   live mode.

The terminal result keeps an iterator cleanup error separate from an open,
iteration, or delivery failure. Cleanup cannot replace the primary cause used by
the adapter.

### 4.2 Live Delivery

Live admission and recovery share one subscriber mutex:

```go
if recoveryPending {
    return false
}
select {
case liveQueue <- event:
    return true
default:
    recoveryPending = true
    notifyRecovery()
    return false
}
```

The notification is non-blocking, capacity one, and level-triggered by the
latched state. Repeated overflow coalesces into the pending notification. While
recovery is latched, later source events are rejected from the live queue and
remain recoverable through retained history. They cannot advance the
subscription position beyond the first rejected event.

The live loop selects cancellation, subscriber closure, recovery, maintenance,
and queued events. A prefix event already dequeued for delivery may finish before
recovery begins. Because later admission is fenced, that prefix necessarily
precedes the retained gap.

### 4.3 Drain Before Rearm

A recovery transition preserves this ordering:

1. Keep `recoveryPending` latched so new live admission remains rejected.
2. Drain stale entries from the bounded live queue without holding the recovery
   mutex.
3. Clear the consumed latch and notification immediately before replay.
4. Replay from the last successfully delivered position. For an empty-start
   subscription, seek each observed backend to the later of that position's
   timestamp group and its first post-registration broadcast group. Do not open
   an iterator for a backend without a broadcast. Filter the first group by the
   EventIDs actually broadcast after registration, checking cancellation and
   subscriber closure between candidates. Apply coalescing after this filter.

Clearing the latch before draining would permit a producer to refill the queue
with events that belong to the recovery interval. Holding the recovery mutex
while draining would make work proportional to queue capacity block producers.
If admission overflows after rearming, it latches a new recovery epoch; the
runner observes it after replay or through the live notification.

The subscriber records the first broadcast group for each backend before
deciding whether to enqueue or reject an event. This includes events rejected
while recovery is pending and prevents an empty delivery position from
turning recovery into a replay of pre-registration history. EventIDs within a
timestamp group have no capture-order meaning, so a single first EventID is
not a sufficient boundary.

### 4.4 Ready

Verified subscriptions publish Ready after initial replay completes and the
runner first enters live mode. The Ready frame carries the current delivery
progress and is emitted at most once for the subscription. Later recovery passes
return to live mode without another Ready frame.

For local verified subscriptions, the in-band Ready event is sent before the
`onReady` callback runs. The callback means the barrier was sent; it does not mean
the downstream consumer applied or persisted every preceding event. Consumers
must establish that stronger condition themselves.

### 4.5 Maintenance and Heartbeats

Maintenance callbacks run only from live mode; replay and recovery do not
interleave periodic work with iterator delivery.

| Adapter | Periodic behavior |
|---|---|
| Ordinary local | No periodic maintenance |
| Verified local | Validate the current retained boundary every second; a failure terminates the attempt |
| Ordinary gRPC | Send a heartbeat carrying current progress at the configured interval |
| Verified gRPC | Validate the current boundary, then send the heartbeat; validation failure prevents that heartbeat |

Entering live mode resets the gRPC heartbeat interval, including after recovery.
A heartbeat is a transport frame with no change event. It does not advance
progress and is distinct from the one-time Ready frame.

## 5. Ordering and Progress

For each backend, the subscriber tracks the latest delivered cluster timestamp
and the EventIDs delivered at that timestamp. Distinct IDs at the same timestamp
are delivered; identities already sent in the current boundary group and events
from older groups are suppressed.

A new subscription has no in-memory delivered-identity set and may receive its
boundary group again. Consumers must be idempotent. Puller progress describes
successful transport delivery, while the downstream checkpoint describes
successful application processing; neither implies the other.

## 6. Terminal Behavior

The runner reports an exit kind, the phase in which it stopped, the primary
error, and any iterator cleanup error. Adapters map that result as follows:

| Condition | Ordinary local | Verified local | gRPC |
|---|---|---|---|
| Malformed `after` | Close the channel | Emit a non-retryable terminal error, then close | Return `InvalidArgument` |
| Missing or invalid verified boundary | Not applicable | Emit a terminal error; capture unavailable is retryable | Return `Unavailable` for capture unavailability, otherwise `FailedPrecondition` |
| Replay open or iteration failure | Log and close | Emit a non-retryable terminal error, then close | Return `Internal` |
| Nil replay or live event | Log and close | Emit a non-retryable terminal error, then close | Return the runner error |
| Iterator cleanup failure without another primary failure | Log and close | Emit a non-retryable terminal error, then close | Return `Internal` |
| Iterator cleanup failure after delivery or another replay failure | Log cleanup separately; preserve the primary exit | Log cleanup separately and emit the primary terminal error | Log cleanup separately and return the primary transport error |
| Data or Ready delivery failure | Close; cancellation remains silent | Close; cancellation remains silent | Return the send or encoding error |
| Periodic boundary validation failure | Not applicable | Emit a terminal error; capture unavailable is retryable | Return `Unavailable` for capture unavailability, otherwise `FailedPrecondition` |
| Heartbeat send failure | Not applicable | Not applicable | Return the send error |
| Caller context cancellation | Close silently | Close silently | Return success from the handler |
| Subscriber or server closure | Close silently | Close silently | Return `Canceled` |

gRPC admission failures occur before the runner: shutdown returns `Unavailable`,
capacity exhaustion returns `ResourceExhausted`, and requesting verified replay
from a source without boundary support returns `Unimplemented`.

## 7. Retention

Verified replay validates the required boundary groups under retention
synchronization. If cleanup removed any required part, the subscription fails
without announcing Ready.

Age cleanup retains all events inside the retention window and the newest
persisted timestamp group before its cutoff. Capacity cleanup retains at least
the latest durable group and treats the configured size as a soft target when a
resumable terminal group requires more space. Explicit deletion, older capacity
eviction, and genuinely expired history can still invalidate a boundary.

## 8. Resource and Test Contract

- Local subscription queues hold 1,000 events.
- gRPC queues use the configured capacity, defaulting to 10,000 events.
- Queue limits count events, not bytes or elapsed lag.
- Recovery publication never blocks a producer, and its channel is never closed.
- Subscriber closure remains separate from recovery notification.

Shared runner tests cover initial replay, live delivery, recovery drainage,
replay from the last successful progress, Ready-once behavior, repeated live
entry, iterator closure, separation of delivery and cleanup errors, cancellation,
subscriber closure, nil-event rejection, and maintenance ordering. Adapter tests
retain local terminal event and callback ordering, gRPC status and heartbeat
behavior, admission, protobuf conversion and size limits, equal-timestamp replay,
overflow during replay and live delivery, and the logging/publication
lost-wakeup boundary.
