# Unified Adaptive Consumption Model

**Date:** January 1, 2026
**Status:** Implemented
**Component:** Puller Service (local and gRPC delivery)

## 1. Problem Statement

Puller subscriptions need low-latency live delivery without allowing a slow
consumer to create an unbounded in-memory queue. Disconnecting every slow
consumer causes reconnect flapping, while dropping queue entries without retained
replay creates delivery gaps.

The local and gRPC transports therefore use the same delivery model: bounded live
queues absorb short bursts, and retained replay recovers sustained backlog without
breaking the subscription. The handoff must wake an idle consumer and must prevent
newer live events from advancing progress past an event rejected from the queue.

## 2. Catch-up and Live Modes

```text
Subscribe with progress
          |
          v
  Begin recovery and drain stale live entries
          |
          v
  Replay boundary timestamp group and later events
          |
          +--- Recovery relatched during replay ---> Repeat catch-up
          |
          v
  Initial Ready barrier, when requested
          |
          v
  Live channel delivery
          |
          +--- Recovery notification ---> Catch-up
```

### 2.1 Catch-up Mode

Catch-up reads the retained event buffer. It starts when a subscription supplies
progress or when live admission latches recovery.

Each replay attempt clears the recovery latch, and the recovery transition
discards stale live entries before returning to live delivery. Replay starts from
the last successfully delivered position and includes the complete boundary
timestamp group. Identity-aware deduplication suppresses overlap already
delivered by the same subscription.

If live admission overflows during replay, recovery is relatched and the replay
pass repeats. If overflow occurs immediately after the final recovery check, its
notification remains pending and wakes the live loop.

### 2.2 Live Mode

Live delivery reads a bounded per-subscriber channel. Subscriber live admission
is serialized with the recovery state:

```go
if recoveryPending {
    return false
}
select {
case liveQueue <- event:
    return true
default:
    recoveryPending = true
    notifyRecovery()
    return false
}
```

The recovery notification is non-blocking, capacity one, and level-triggered by
the latched state. Repeated overflow coalesces into the existing notification.
While recovery is pending, later events are rejected from live admission and
remain in retained history. They cannot cross the missing event or advance the
subscription's delivery position.

The live consumer selects events, recovery, cancellation, and subscriber closure.
A prefix event already dequeued for delivery may complete before catch-up begins.
Because admission is fenced after the first rejection, that event necessarily
precedes the missing retained event. The consumer then replays from its last
successful delivery position.

## 3. Ordering and Progress

Delivery progress advances only after a successful local or gRPC send. Puller
does not persist the consumer's processed checkpoint; downstream consumers own
that checkpoint after applying the delivered event.

Replay includes the complete timestamp group containing current progress. MongoDB
events can share a cluster timestamp, and the EventID hash suffix is not source
arrival order. The subscriber tracks delivered EventIDs within its current group,
preserving distinct siblings while suppressing replay/live overlap.

A new connection resumes with no in-memory identity set and may receive its
boundary group again. Consumers must tolerate this bounded redelivery. Native
resume-token checkpoint semantics remain unchanged.

## 4. Retention and Readiness

Verified replay validates the entire required boundary group under retention
synchronization. If cleanup removed any part of that group, the subscription
fails rather than announcing incomplete readiness.

The initial Ready frame follows all successfully sent replay events. Consumers
must apply those events before accepting readiness.

Age cleanup keeps all events inside the retention window and the newest persisted
timestamp group before its cutoff. This protects an idle subscription's boundary
while the first newer event is committed but not yet delivered. Capacity cleanup
keeps at least the latest durable group and treats the configured size as a soft
target when a resumable terminal group requires more space. Explicit deletion,
older capacity eviction, and genuinely expired history can still invalidate a
boundary.

## 5. Resource and Lifecycle Rules

- Local subscription queues hold 1,000 events.
- gRPC queues use the configured capacity, defaulting to 10,000 events.
- Queue limits count events, not bytes or elapsed lag.
- Recovery publication never blocks a producer and its channel is never closed.
- Subscriber lifetime uses the existing `done` channel. Context cancellation,
  shutdown, replay failure, transport failure, and boundary failure retain their
  existing terminal behavior.

The [overflow wakeup decision](../../../../.agents/notes/implemented/bug-fix/2026-09-16-puller-overflow-wakeup.md)
owns the admission fence, notification alternatives, and concurrency rationale.

## 6. Consequences

1. Temporary backpressure moves the subscription to retained replay without a
   routine reconnect.
2. Idle subscribers cannot miss recovery merely because no later event arrives.
3. Newer live events cannot move progress beyond an event rejected by overflow.
4. Catch-up consumes retained-buffer reads and can still fail when required
   history is unavailable.
5. Local and gRPC loops remain separate transport implementations over the same
   subscriber recovery contract.
