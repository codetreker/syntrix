# Console-Managed Syntrix Instances

**Status:** Accepted design; implementation tasks are pending.
**Baseline:** Runtime deployment and developer Console are implemented independently.
**Scope:** Shared administrator-configured backends and developer-owned instance lifecycle.

The [platform architecture](../../../architecture.md) owns employee Management,
developer Console, and instance end-user boundaries. The [Console design](01.console.md)
owns implemented developer authentication and test workloads. This document owns
the planned instance resource model, allocation, initialization, management,
published runtime package selection, and five-PR delivery sequence. The [decision note](../../../../.agents/notes/proposed/architecture/2026-10-12-console-instance-lifecycle.md)
records alternatives, consequences, and deferred capabilities. The
[managed runtime contract](04.managed_runtime_contract.md) specifies PR 1 public
rendering, broker attachment, initialization ordering, and role readiness.

## Current Implementation and Integration Gaps

Console currently accepts a predefined HTTP test template and reconciles one
Deployment and Service from PostgreSQL intent. The browser provides login,
session restoration, logout, localization, and Overview. These are not instance
creation or administration interfaces.

The [runtime deployment](../../../../packages/syntrix/deployment/README.md) supplies
standalone and distributed templates, persistent derived storage, and an explicit
bootstrap Pod against existing backends. It does not allocate database accounts,
private databases, broker namespaces, or Console-owned instance records.

Current distributed composition uses fixed NATS stream defaults. The renderer
must supply instance-specific names, and Manager must forward existing consumer,
storage, and publisher options before shared-account operation is supported.
Both runtime stream upsert paths can overwrite a Console-created stream's limits;
managed startup needs an attach-and-verify contract. The current HTTP/TCP probes
show listener availability rather than complete component readiness.

The [manual release workflow](../../../../packages/syntrix/deployment/RELEASE.md)
publishes tested, version-matched deployment archives and public multi-platform
runtime images. It runs only when triggered on main; a new main commit alone is
not a published build. Current release metadata does not declare a managed runtime
contract version. PR 1 supplies that marker; PR 3 consumes the published package.

## Actors and Resource Model

Administrators own infrastructure registration and its high-privilege credentials.
An operator-controlled configuration import is the administration entrypoint for
this delivery. It updates versioned PostgreSQL records; no developer pool-write
API or employee login system is introduced. A future Management interface can
use the same records and execution boundary.

Developers own instances. Instance application accounts and bootstrap administrator
credentials belong to the instance, independently of Console sessions. Projects,
project identity realms, and OAuth remain governed by their existing designs.

| Resource | Shared infrastructure | Instance allocation |
|---|---|---|
| MongoDB | Administrator-managed replica set or compatible change-stream-capable cluster | Private physical database, collections, scoped database user |
| PostgreSQL | Administrator-managed server/cluster | Private system database and login role |
| NATS | Administrator-managed JetStream server and optionally one shared account/user | Dedicated stream, subject prefix, durable consumer |
| Kubernetes | Administrator-selected cluster, namespace, storage, and routing environment | Runtime controllers, Services, configuration, key, and PVCs |
| Console PostgreSQL | Console control database, possibly on the same physical PostgreSQL server | Developer authority, pools, profiles, bindings, intent, and receipts |

A private instance PostgreSQL database does not imply a separate PostgreSQL
server. Console's database and credentials remain distinct. A physical MongoDB
database contains several logical Syntrix databases; those logical databases
remain catalog/document namespaces inside the instance.

## Administrator Configuration and Allocation

Resource configuration includes a stable backend identity, type, endpoints, TLS
settings, protected credential version, allocation eligibility, instance-count
or broker-capacity limits, and capability observations. Deployment environments
bind compatible backend sets to a Kubernetes target, permitted namespace,
StorageClass, supported runtime-contract/profile versions, the fixed administrator
release source, and optional ingress/DNS/TLS configuration.
Developers do not choose pool IDs or raw manifests.

The administrator import validates the whole document before updating records.
Existing IDs receive explicit configuration versions; absent entries are not
implicitly deleted. Disabling an entry excludes new allocations but preserves
active bindings and cleanup capability. Changing physical server/account identity
requires a new resource identity; configuration editing cannot migrate instances.

Capability checks include database/role/user provisioning authority, runtime
connectivity, MongoDB replica-member reachability, JetStream availability and
required metadata support, and configured storage/routing support. A successful
control-plane Ping does not prove connectivity from runtime Pods. Provisioning
and acceptance still report actual dependency failures.

Allocation chooses an eligible environment and compatible shared backends using
a deterministic bounded policy, such as the least reserved instance count with
stable-ID tie breaking. The acceptance transaction reserves all required capacity
and writes bindings together or rejects the request without external effects.
Configured capacity is an admission budget, not a claim of hard PostgreSQL or
MongoDB storage quotas. NATS account/server limits remain authoritative even when
other account users consume capacity.

Bind the accepted instance to immutable external backend identities, generated
names, and configuration versions. Later retries cannot select a different server
or regenerate credentials. Runtime credentials and signing material are generated
once and stored encrypted before external effects. A master key is supplied to
Console through an operator-managed secret, outside its PostgreSQL records;
credential versions needed by active bindings remain available. Public responses,
logs, traces, and ordinary configuration snapshots exclude secret material.

## Published Runtime Package Selection

A new instance consumes the latest complete successfully published build from the
administrator-configured Syntrix release source. For this delivery, that source is
`codetreker/syntrix`, workflow `.github/workflows/syntrix-release.yml`, release tags
`^syntrix-[0-9]{6}\.[1-9][0-9]*$`, and image repository
`ghcr.io/codetreker/syntrix-server`; developer requests cannot replace these
identities or submit download URLs. Select published, non-draft, non-prerelease
releases in this family by numeric UTC date and numeric sequence, so `.10` follows
`.9`; validate that the date is real and agrees with metadata `release_date`. Verify the linked workflow run and exact attempt completed successfully
from the declared main commit. Incomplete publication remnants are not candidates.
The [release guide](../../../../packages/syntrix/deployment/RELEASE.md) owns the
producer's tag allocation, publication ordering, and metadata fields.

Resolve the selected GitHub Release and its exact `syntrix-VERSION.tar.gz` asset.
Download it using bounded requests, compute its archive SHA-256, and retain its
repository/release/tag/asset identity and size. Extract with bounded file count,
unpacked bytes and path lengths; reject traversal, absolute paths, unexpected
entries and links that can escape the private extraction directory. Require the
expected root directory, both canonical mode templates, the CLI for the Console
host CPU (`linux-amd64` or `linux-arm64`), and `meta.json`. Console host architecture
is independent of the selected Kubernetes node platforms.

Validate version/tag, full source commit, image repository/tag/index digest,
platforms, workflow identity and attempt, and `managed_runtime_contract` together.
The bundled CLI's `deployment-contract` output must agree with metadata and
advertise the required modes and bootstrap/acceptance/full phases. Only explicitly
supported contract versions can be deployed. A missing marker or an incompatible
latest package fails visibly before backend effects; Console does not silently
select an older compatible release. Registry checks compare the selected version
tag's index digest and target platforms with the recorded release metadata. The
index digest remains validation and diagnostic evidence, not part of Pod image
references.

Persist the complete release receipt in Console PostgreSQL before allocating
backends or launching Pods: source identities, computed archive hash, version,
source SHA, image/index digest/platforms, workflow attempt, contract version and
resolved-at timestamp. Cache the private verified package by immutable asset
identity and archive hash. Retry or cache recovery retrieves and verifies that
exact asset/hash, never a newly selected release. Retained verified cached bytes
remain usable if the remote asset disappears; changed downloaded bytes are rejected.
When the required exact verified package cannot be recovered, package-dependent
create/start/restart/update phases remain blocked with a safe error. Stop/delete
and ownership observation use durable resource receipts and do not depend on
package availability; existing unsettled-owner and destructive-cleanup gates still apply.

The provisioning adapter invokes that downloaded CLI and its matching templates
with a bounded process context, private values and output files, fixed argument
structure and no shell. Console overrides the package example's image value with
the recorded version tag, such as
`ghcr.io/codetreker/syntrix-server:261013.1`, and renders
`imagePullPolicy: IfNotPresent`. No digest suffix or floating `:latest` is used in
its Pod references. The existing archive's tag-and-digest examples remain valid
operator inputs; Console supplies its own managed values. Backend credentials
never appear in command arguments, logs or captured errors. The public renderer
remains the CLI implementation and runtime test owner. Console must not interpret
arbitrary newer templates using its compiled-in renderer: template syntax alone
does not prove compatible model fields, validation, initialization or probes.
PR 2 can reuse the public broker specification only for supported contract versions.

Bootstrap, read-path acceptance, finalization and every full runtime role use the
same recorded package and versioned image tag. Request replay, recovery, start and
restart keep that selection. The publication policy requires a version tag never
to be repointed or overwritten; corrections receive a new version. The current
publisher allocates fresh versions without overwrite, but this is an operational
no-overwrite policy, not a GHCR-enforced immutability guarantee. `IfNotPresent`
can reuse node-cached images; repointing a tag would therefore violate the selected
release contract and could produce different binaries on different nodes.
New publication does not upgrade existing instances. PR 4 can
accept an explicit supported compatible release revision using the same package
validation; incompatible runtime/data-format migrations remain rejected.

## Durable Records and Mutation Contract

Extend the existing workload controller rather than adding another reconciliation
service or a Kubernetes custom-resource authority. Normalize multiple bindings
and resource receipts where the current single Deployment/Service columns cannot
represent the bundle.

| Record | Durable responsibility |
|---|---|
| Resource configuration/version | External identity, capabilities, allocation eligibility, protected administrator credentials |
| Profile/environment version | Runtime placement, fixed release source, supported contract versions, capacity, storage, broker policy, and routing |
| Instance | Developer owner, display name, accepted spec, desired revision/state, observed revision/status/phase |
| Backend binding | Selected backend/version, allocation ID, generated database/user/role or NATS names, credential references, ownership receipts |
| Runtime release receipt | Exact release/tag/asset/workflow identities, archive SHA-256, version/source SHA, image index digest/platforms, supported contract version, resolved-at timestamp |
| Runtime artifact | Role, kind, namespace/name, recorded UID, allocation generation, desired revision, observed controller generation |
| Mutation receipt | Developer-scoped idempotency key, action, canonical request hash, expected revision, instance/operation identity and result |
| External-effect attempt | Persisted-before-call phase/target/attempt identity, exact request generation, and prepared/in-flight/applied/rejected/unresolved outcome |

Creating an instance accepts the following product fields:

```json
{
  "name": "shop-production",
  "mode": "distributed",
  "profile": "standard",
  "allowed_origins": ["https://shop.example.com"]
}
```

The proposed `/api/v1/instances` API derives the owner from the existing verified
Console session. Mutations retain exact Origin and CSRF checks. Create uses an
`Idempotency-Key`; replay checks the original receipt before current configuration
availability. A changed payload for the same key conflicts. Successful acceptance
returns 202, the instance/operation receipt, and Location, before provisioning.
An owner-scoped request-receipt lookup resolves a lost response without allocating
a second instance. Listings use cursor pagination before presenting complete
inventory counts.

Start/stop/restart, configuration changes, resize, and delete also use action
receipts. Expected desired revisions reject competing changes. Desired revision,
operation identity, Kubernetes resourceVersion, and controller generation are
separate values. Delete becomes irreversible desired intent and supersedes other
convergence; an old action cannot resurrect it.

Resource updates validate stable installation/instance/role ownership and recorded
UID, then use resourceVersion concurrency checks. Mutable spec digest and applied
revision do not replace stable ownership. Cleanup must remain possible after a
partly applied or older spec. An ownership mismatch blocks action; a matching name
alone never authorizes adoption or deletion.

Before a remote request, record its attempt and effect identity. Mutating clients
must not transparently resend state-owner creation after an unknown outcome;
subsequent reconciliation observes that original attempt first. An owned object
carrying its unique effect identity can establish that the create committed.
Definitive rejection establishes no effect. Cancellation, client timeout, a
missing response, and an absence observation do not establish rejection.

Bootstrap handoff, completed stop, and destructive cleanup are gated on settlement
of every earlier attempt that can introduce a runtime/storage owner. An unresolved
attempt prevents normal activation or backend destruction even when current Pods
are absent. Continue observation without launching another attempt; where no
authoritative receipt exists, mark the operation blocked. Trusted operator recovery
must reconcile the target with authoritative server-side request completion or an
actual execution fence before recording settlement. An unsupported backend/fence
or insufficient evidence leaves the operation blocked; a timeout or confirmation
checkbox cannot override this gate. Tombstones repair late data/resource effects
but do not substitute for the state-owner settlement gate.

## Database Allocation and Initialization Ownership

Console uses administrator connections to allocate the private PostgreSQL
database/role and MongoDB database/user. Generated names derive from the immutable
instance ID and are never reused for a different instance. PostgreSQL databases
exclude PUBLIC access and grant the dedicated runtime role only the required
private database/schema privileges. The runtime role is not a superuser and has
no database/role creation privilege. MongoDB users receive only their instance
database's required document, collection/index, and change-stream capabilities.

PostgreSQL `CREATE DATABASE` cannot execute inside a transaction, so Console's
acceptance and external allocation are not atomic. Persist original names,
credentials, and phase receipts, then inspect the allocated database/owner after
uncertain outcomes. Existing names without verified allocation provenance block
creation. The same ownership rule applies to MongoDB databases, users, and
collection identities. [PostgreSQL CREATE DATABASE](https://www.postgresql.org/docs/current/sql-createdatabase.html)

Runtime modules own the `auth_users` and database-catalog schema, default logical
database, source collections/indexes, and revocation initialization. Console
orchestrates that runtime initialization without copying SQL/index definitions.
The current factory does not invoke every existing EnsureIndexes helper; managed
initialization must wire and verify owner-defined non-cleanup preparation separately
from cleanup finalization. MongoDB `documents`, `sys`, and current revocation
storage remain within the allocated physical database. The runtime owns exact
index definitions and reports a versioned specification receipt; Console records
that receipt without duplicating schema or index definitions.

The runtime bootstrap administrator is generated independently of the Console
developer account. Its initial credential is delivered through an explicit
owner-authenticated connection-information operation with no-store responses;
it is excluded from lists, ordinary polling, browser persistence, and diagnostics.
Updating bootstrap configuration does not reset an existing account password.

## Shared-Account NATS Contract

An immutable instance ID determines one literal namespace token:

```text
S = SYNTRIX_<instance-id-hex>_TRIGGERS
stream: S
subject prefix: S
stream subjects: S.>
durable consumer: S_DELIVERY
consumer filter: S.>
```

Evaluator and delivery configuration use the same stream and storage policy.
Publisher SubjectPrefix applies exactly once to the existing database/collection/
document task subject, including hashed long-subject fallback. All Worker replicas
of one instance share its durable consumer; different instances have disjoint
streams and subject filters. Display-name changes preserve these identities.

Use existing stream_name, consumer_name, storage_type, RetryAttempts, and provider
options. Manager must forward them consistently. Console creates the complete
stream and consumer specifications with allocation metadata and profile limits;
managed runtime startup attaches and verifies rather than issuing incomplete
CreateOrUpdateStream calls. Both publisher construction and consumer subscription
must obey that contract. Operator-managed deployment remains supported through
the same provider/renderer contracts, without depending on Console records.

Profiles specify an explicit compatible storage policy and bounded stream
byte/count/age limits. Default Limits retention can retain acknowledged messages;
a bounded stream cannot be silently changed to unlimited by runtime startup.
Stream policy changes reconcile through an accepted configuration revision.
[NATS stream limits](https://docs.nats.io/nats-concepts/jetstream/streams)

Shared account credentials provide routing separation, not an authentication
boundary between runtime instances. They are not exposed through developer
connection information. Connection diagnostics sanitize credentialed URLs.
Changing shared credentials is an administrator-managed revision affecting every
bound instance; delete never revokes a shared account/user/credential.

Record exact stream/consumer names, allocation metadata, and creation receipts.
NATS delete APIs lack Kubernetes-style UID preconditions; metadata inspection
followed by deletion is not an atomic incarnation fence. Names remain permanently
reserved, cleanup uses exact names, and deletion tombstones continue checking for
late effects. A manually replaced resource with conflicting provenance blocks
cleanup instead of being adopted.

## Provisioning, Bootstrap, and Readiness

```mermaid
flowchart LR
    Accepted[Accepted and reserved] --> Resolve[Resolve and freeze published package]
    Resolve --> Allocate[Allocate backends]
    Allocate --> Prepare[Prepare config key and storage]
    Prepare --> Bootstrap[Initialize and bootstrap]
    Bootstrap --> Handoff[Stop maintenance and wait]
    Handoff --> Runtime[Start normal runtime]
    Runtime --> Verify[Verify read path and query]
    Verify --> Finalize[Finalize and verify cleanup]
    Finalize --> Activate[Activate and verify all roles and access]
    Activate --> Ready[Ready]
```

Release resolution is a persisted pre-allocation phase. Once its receipt is saved,
all rendering and runtime execution use that recorded package; newer releases do
not change an in-flight instance operation.

These are persisted phases, not one long HTTP request or PostgreSQL transaction.
The existing reconciler lease and per-instance row serialization remain the work
owner. Each external call/observation has a bounded timeout; the overall operation
has a separately persisted deadline. Scheduling prioritizes active provisioning
and deletion while retaining bounded observation of ready instances and tombstones.

Initialization operates on newly allocated private data that has not been handed
to application clients. The system controls its writers and cleanup boundary.
Attaching existing unmanaged data requires a separately designed maintenance
operation; a checkbox cannot establish write quiescence.

Fresh PVCs require explicit bootstrap even with empty source databases. Before
maintenance, all normal state-owning Pods must be absent. Run the existing bare
`restartPolicy: Never` bootstrap Pod and observe its UID and initialized readiness.
It remains running after successful initialization, so Pod Succeeded is not the
completion condition. Persist the completion/handoff receipt, gracefully delete
maintenance, and confirm its absence before normal roles open those same claims.
Do not force-delete a state owner or rely on ReadWriteOnce for process exclusivity.

Transient dependency/API errors retry the same phase and identities. Ownership
conflicts, missing recorded PVC/key state, and failed partial bootstrap become
blocked states requiring explicit correction/recovery. Restart does not select
bootstrap or reset flags. Do not recreate lost derived/source state silently.

Lifecycle actions have explicit phase preconditions:

| Phase | Legal actions and result |
|---|---|
| Allocation or resource preparation | Delete supersedes creation; stop requests a paused operation after attempts settle. Start resumes only a safely paused pre-bootstrap phase. |
| Bootstrap running | Restart/configure/resize are rejected. Stop cancels maintenance after effects settle and preserves partial claims as initialization-required, not initialized. |
| Bootstrap completed or handoff | Preserve the durable completion receipt; stop finishes the drain without activating normal roles. A later start continues the recorded handoff. |
| Ready or initialized stopped | Start/stop/restart use initialized state; ordinary supported configuration/resize follows revision checks. |
| Partial bootstrap failure or lost recorded state | Start/restart cannot rebuild. The supported destructive recovery is owned deletion followed by a new create; no reset/rebootstrap action is advertised. |
| Unresolved external effect | Only observation and trusted settlement recovery can discharge the gate. Delete/stop intent is durable but completion waits; no new owner is activated. |
| Deleting or deleted | Creation/update cannot resurrect the instance; retry/observation continues exact owned cleanup. |

The UI exposes the supported recovery choices and their data consequences. Failed
pre-bootstrap allocation can resume the original phase after the dependency is
corrected; partially initialized derived state cannot take that generic retry path.

Bootstrap and normal read-path acceptance hold internal cleanup and Trigger
writers as well as external writers. Use the explicit acceptance-only runtime
option/render; held roles do not satisfy full instance readiness. After read-path
component and authenticated indexed-query acceptance, invoke
the same runtime image's bounded initialization finalizer and persist its observed
cleanup receipt. Prepared component readiness permits that acceptance traffic; it
does not authorize releasing application access or writers. Keep document cleanup
TTL inactive through normal indexed-query acceptance. Shared MongoDB servers
receive no instance-wide change to the global TTL monitor. An uncertain finalizer
result remains a recorded effect; inspect/converge the same exact specification
and settle it before deletion. After recording finalization, activate the full
normal render and verify every required role and configured access before releasing
application writes. Replacing an acceptance state owner obeys the same settlement/
drain gate as bootstrap handoff. Missing cleanup on restart is observable and never
silently repaired.

Instance Ready requires the accepted runtime revision, initialized databases,
the verified finalized cleanup receipt, required controller/Service endpoints,
readiness of enabled runtime components,
and a real authenticated indexed query. Realtime/Trigger component failure must
not be hidden by a healthy API/TCP listener. Required readiness contracts and
meaningful component acceptance are added within their owning runtime modules.

Routing uses an administrator-configured ingress class, domain/DNS, and TLS
environment. A host derived from the instance ID is published after external-path
acceptance. An environment without routing advertises internal-only access; it
does not fabricate a public URL. allowed_origins feeds the same validated REST
CORS and realtime policy. No public access is handed out during bootstrap.

## Management and Deletion

| Operation | Supported contract |
|---|---|
| Stop/start | Change desired runtime replica state; preserve databases, source credentials, PVCs, and signing key. |
| Restart | Change an accepted restart generation and observe replacement Pods; never bootstrap/reset. |
| Resize | Change approved CPU/memory, permitted role replicas, and managed broker limits; standalone/Puller/Indexer/evaluator remain singleton. |
| Configure | Validate a complete revision, update versioned configuration, and restart affected roles. |
| Rotate credentials | Execute the backend's declared overlap or quiesced transition with persisted stages; never replace a password through an ordinary configuration edit. |
| Delete | Explicitly confirm destructive cleanup of instance-owned data/resources; retain a durable cleanup record. |

Storage shrink, StorageClass or broker storage/retention-mode changes, standalone/distributed conversion,
incompatible image/catalog upgrades, backup/restore, and reattaching foreign data
are explicit migration/recovery capabilities outside ordinary resize/configure.
They are rejected through capability validation, not attempted as implicit
bootstrap. Pinned package/image/profile versions make the supported boundary observable.
An explicit compatible release revision passes source/package/contract validation
before rollout; ordinary start/restart/configuration never refreshes the version.

Deletion first stops serving and all normal/maintenance owners, then removes
recorded NATS consumers/streams, private MongoDB database/user, private PostgreSQL
database/role, and owned Kubernetes configuration/key/PVC resources. UID checks
apply where supported; other backends use recorded ownership/provenance and
never-reused names. Partial cleanup remains visible and retryable. Release logical
capacity only after its promised cleanup is confirmed. Kubernetes volume deletion
is constrained by the StorageClass/PV reclaim policy; report retained physical
storage without claiming byte-level erasure.

Delete never removes shared servers, MongoDB replica sets, PostgreSQL clusters,
NATS accounts/users/shared credentials, or Console's control database. Stop is the
data-preserving lifecycle operation. A delete-and-retain-data product requires
separate discoverable retained-data ownership and restore semantics before being
exposed.

## Credential Transition Contract

Rotation records prepared, quiescing, backend_changed, verified, applying,
converged, and retired stages, each with exact credential versions and protected
attempt receipts. Generate and persist replacement secrets before changing a
backend. Authentication using the recorded replacement verifies the current
password value; it does not prove that an earlier password request has settled.
An unresolved password mutation blocks resend, completion/retirement, and the
next credential generation until authoritative completion or an actual execution
fence is established. After definitive rejection, retries set the same recorded
replacement and never generate another one. Do not automatically roll back to an
old password after an unknown result.

For allocated MongoDB/PostgreSQL users with a single password, use a quiesced
transition: record prior desired running/stopped state, settle owner-introducing
requests, stop every affected runtime process, change that same scoped user's
password, verify it, publish the credential/config revision, then resume only
previously running services and confirm readiness. This admits explicit downtime
without changing database/user ownership. Stopped instances receive the new
validated desired secret and remain stopped; retirement never relies only on
currently running Pods. Failure stays in the recorded stage with protected
replacement material and an explicit blocked/retry result.

NATS shared credential rotation is an administrator operation over every bound
instance. With externally prepared overlapping credentials for the same account,
validate the new version's access to recorded owned streams, update every active
and stopped binding, and settle/drain old-generation Pods before authorizing
administrator retirement. Console must not pretend an ordinary NATS client can
change server authentication. Retirement is recorded only after the administrator
completes the backend change and its rejection of the old credential is verified.

If the NATS administrator cannot provide overlap, explicitly quiesce all affected
instances before the external password/config change, then import/validate the
replacement and restore their recorded desired states. Partial adoption, a stale
stopped binding, an unresolved launch, or insufficient retirement authority blocks
completion. Pool capability validation rejects unsupported transitions; it never
quietly performs an in-place shared-password replacement while services run.

## Implementation Ownership

Resource registration, protected credential custody, backend allocation and
cleanup belong to a Console resource module, including its own config package.
Console internal/config composes module settings. Workload owns instance intent,
operations and reconciliation; provisioning owns Kubernetes execution. A future
Management adapter can take execution responsibility without changing developer
authority or accepted intent semantics.

Promote the existing pure runtime renderer/config into the existing public
packages/syntrix/deployment directory and embed its canonical templates. It owns
the packaged CLI implementation and shared broker specification. Console's
provisioning adapter owns release discovery, verified private package caching,
bounded matched-CLI execution and Kubernetes effects. Resource allocation owns
backend configuration and grants no generic executable-download capability.
File output remains CLI-owned. Module/image/release build inputs are explicit;
neither copied templates nor sibling source layout define runtime deployment.

The browser integrates through existing session authority, same-origin cookie,
Origin and CSRF contracts. Account/resource changes cancel private requests and
clear owned page data. Non-overlapping polling shows observed_at and safe phase/
reason, pauses appropriately, and rejects superseded receipts. Unknown create
outcomes retain request identity; language changes preserve forms and operations.

## Observability and Validation

HTTP acceptance establishes request_id, developer_id, instance_id, operation_id,
and desired revision. Persist operation correlation for detached reconciliation;
pool/binding/allocation and resource-role identities accompany each external
phase. Context-aware calls carry that scope through deadlines and authority loss.
One existing reconciler owns scheduling and shutdown; no unowned worker or second
generic job subsystem is introduced.

Failures record safe category, component, phase, retryability, and available
correlation fields. Raw connection strings, credentials, tokens, generated
manifests, and request secrets are excluded. Metadata/readiness receipts stay
queryable in Console PostgreSQL, while stdout JSON supplies execution logs. To
investigate an operation, filter parsed JSON by instance_id and operation_id,
then order phases by timestamp and compare desired/applied revision with the
instance operation receipt. Missing or delayed observations are reported as stale.

Acceptance uses two concurrent instances sharing the same MongoDB, PostgreSQL,
and NATS account. It proves scoped database credentials cannot access each
other's data, Trigger messages reach only the corresponding instance, same-instance
Worker replicas share one durable, and deleting one instance preserves the other
and all shared infrastructure. Fault probes cover acceptance-response loss,
effect-before-receipt failure, restart/authority loss during allocation/bootstrap,
partial update/delete, late effects, and credentials absent from diagnostics.
Package probes cover numeric release ordering, manual publication versus main
commits, draft/failed publication rejection, unsupported latest contract, archive
path/size attacks, metadata/CLI disagreement, unsupported host/node platforms,
digest/hash mismatch, asset disappearance and retries across newer publication.
Rendered resources must use the recorded version tag and `IfNotPresent` for
every creation phase and role, without a digest suffix or `:latest`. Verify the
release tag's observed digest against metadata and reject mismatches; retain that
digest as evidence. Publication corrections must allocate a new version.

Runtime and Console retain enforced go-cov race/coverage and critical-block gates.
Frontend uses its existing type/catalog/test/build/browser gates. Real PostgreSQL,
MongoDB replica-set, NATS, prepared Kubernetes, and browser checks complement
unit/typed-client tests. No command creates or repairs the maintainer's cluster.

### PR 1: Managed Runtime Deployment Contract

The [detailed runtime design](04.managed_runtime_contract.md) owns APIs, module
boundaries, initialization/readiness semantics, and implementation gates.

- Extract the existing pure renderer/config to the shared public owner; embed
  existing templates and preserve explicit-source CLI generation and secret-safe
  atomic output. Wire module/image/release build inputs explicitly.
- Add and verify the published metadata/CLI managed-runtime contract version and
  phase capabilities; preserve a version/source-matched packaged CLI and templates.
- Generate immutable instance NATS identities and complete broker configuration;
  validate evaluator/delivery consistency and forward all existing options.
- Introduce managed attach/verify through the existing pubsub provider; ensure
  neither publisher nor consumer silently rewrites owned stream policy. Preserve
  operator provisioning through the same complete-spec contract.
- Wire module-owned preparation/inspection/finalization, internal-writer acceptance
  hold and the same-image finite finalizer; finalize after indexed-query acceptance,
  then activate and verify all roles before write/access release.
- Add ordinary subscription admission and enabled-role readiness through existing
  owners; propagate terminal background failures and use truthful role probes.
- Apply one origin policy to REST/realtime and sanitize diagnostics.
- Validate both modes/phases, actual shared-account routing for two instances,
  same-instance Worker sharing, policy conflict rejection, and runtime race/coverage.

This PR exposes no Console allocation or developer instance API.

### PR 2: Administrator-Configured Backend Allocation

- Add resource/profile/environment schema and typed module config; bootstrap/import
  complete administrator definitions with versioning, disable and reference rules.
- Register the fixed administrator release source, supported contract versions and
  profile compatibility policy; allocation never downloads or runs release tools.
- Add encrypted credential custody with an externally supplied master key and
  persisted runtime credential/signing-material versions; add no developer pool
  mutation or secret-read endpoint.
- Accept allocator inputs from instance identity/profile; reserve capacity and
  bindings atomically, generating names and secrets once before external effects.
- Implement inspect/create/recover/cleanup for private PostgreSQL database/role,
  MongoDB database/user, and complete instance NATS stream/consumer specifications.
- Prove real-backend cross-instance access rejection, request/phase replay,
  ownership conflicts, non-atomic allocation recovery, and shared-resource preservation.
- Persist attempt identity before remote effects and preserve unresolved outcomes;
  provide controller-readable settlement and blocked-recovery evidence.

This PR provides controller-consumable allocation contracts without exposing an
unfinished public instance workflow.

### PR 3: Durable Instance Lifecycle

- Extend existing workload intent and receipts to instance bundles; implement
  paginated list/detail, profiles, create request lookup, and idempotent actions.
- Resolve the latest complete published package, validate metadata/CLI/archive,
  freeze its receipt before backend effects, and render using the downloaded
  version-matched CLI/templates through the existing provisioning adapter.
- Reconcile allocation, typed runtime resources, bootstrap completion/handoff,
  read-path acceptance controllers/query, cleanup finalization receipts, full-role
  activation/acceptance, and configured access routing.
- Preserve the selected package/version tag with `IfNotPresent` across replay,
  retry, stop/start/restart and every bootstrap/acceptance/finalizer/full-role
  phase; keep the recorded index digest as validation evidence, test newer publication,
  removed/changed assets, unsupported latest contracts and private process cleanup.
- Implement stop/start/restart and explicit destructive delete; preserve UIDs,
  original bindings, key/state and late-effect tombstones. Confirm cleanup scope.
- Persist phase deadlines, safe blocked/retry reasons and observed timestamps;
  prioritize active operations without dropping ready/deleted observation.
- Verify restart and authority-loss recovery at phase boundaries, lost responses,
  failed initialization, missing key/PVC, and one-instance deletion without effects
  on another instance or shared infrastructure.
- Verify late owner creation cannot bypass handoff, stopped completion, or data
  destruction; unknown attempts block transitions until authoritative settlement.
- Implement legal action checks for interrupted bootstrap and expose deletion/new
  creation as the destructive partial-bootstrap recovery, preserving completed
  bootstrap receipts for a later start.

This PR does not expose unsupported resize/configure actions.

### PR 4: Revisioned Configuration Convergence

- Add expected-revision and idempotent receipts for complete config/profile changes;
  keep stable ownership separate from mutable desired/applied spec.
- Accept explicitly requested compatible published release revisions only after
  validating and recording their matched package; ordinary configuration does not
  upgrade the runtime, and incompatible runtime/data migrations remain rejected.
- Apply versioned configuration and accepted restart generations with recorded
  UIDs/resourceVersion checks; aggregate convergence before reporting completion.
- Implement advertised CPU/memory/replica resize and supported credential revisions;
  administrator shared-credential rotation identifies all affected bindings.
- Implement the recorded quiesced MongoDB/PostgreSQL transition and capability-based
  overlapping/quiesced NATS administrator workflow, including stopped bindings
  and verified retirement authority.
- Converge the accepted NATS byte/count/age limits through the Console-owned
  complete stream specification. Preserve stream/consumer identities and require
  runtime attachment to retain the new policy after restart.
- Reject topology conversion, storage shrink/class change, and incompatible
  image/data-format migration through explicit capability validation.
- Verify racing updates, stale remote writes, partial rollout, dependency failure,
  deletion during update and preserved keys/data without implicit bootstrap.
- Verify interrupted/conflicting broker resize, observed applied limits after
  recovery, and continued delivery in the other shared-account instance.
- Verify effect-before-receipt password changes, restart during each rotation
  stage, stopped-instance adoption, partial shared-credential convergence and
  blocked retirement while old-generation launches remain unresolved.
- Hold a delayed password mutation for one generation while requesting another;
  verify the later rotation and retirement cannot proceed until every prior
  credential mutation is authoritatively settled or fenced.

## Deferred Capabilities and Preserved Constraints

Employee Management login/execution, developer OAuth, project/end-user realms,
database-server installation, HA/sharding, backup/restore, topology/data-format
migration, and delete-with-retained-data inventory remain separately owned work.
The controller and versioned execution boundary preserve those extension points
without claiming their guarantees. Administrator configuration import supplies
the resource-management entrypoint here; an administrator browser UI can later
use the same records but needs its own employee authority and credential workflow.

Instance-level configuration does not grant project administration or expand
current end-user identity scope. Planned endpoints and capabilities remain absent
until their PR completion gates pass and their reference contracts are updated.
