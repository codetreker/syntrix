# Platform Management Control Plane

**Updated:** October 10, 2026
**Status:** Proposed operating mechanisms within accepted product boundaries

## 1. Ownership

Management is the employee-facing platform outside developer instance runtimes.
It owns platform scheduling, monitoring, and operations. The developer Console
serves developers who create and manage one or more own instances. An instance
serves application end users through its runtime services, MongoDB, and PostgreSQL.
The [system architecture](../../../architecture.md) and
[boundary decision](../../../../.agents/notes/proposed/architecture/2026-10-10-platform-console-instance-boundaries.md)
own that division.

Each instance owns projects with isolated enduser realms; each project can use
multiple logical databases. Instance PostgreSQL stores instance system data,
including project identity and database metadata. Management must not borrow a
developer instance's PostgreSQL as its platform-wide durable authority. The
Management backend and Console account protocols remain open decisions.

`services.Manager` in the Go runtime assembles dependencies and manages process
startup and shutdown. It does not implement this control plane. Existing
logical-database CRUD, suspension, and deletion operate within the runtime; those
capabilities do not establish fleet membership, scheduling, or reconciliation.

## 2. Proposed Membership and Scheduling Mechanisms

Managed runtime nodes need identifiable capabilities, observable membership,
and bounded heartbeat/reconciliation behavior. An expiring lease records
membership and new-work eligibility; it does not by itself stop a partitioned
node from continuing work it already owns.

Exclusive assignments therefore require a monotonically increasing fencing
generation checked by the actual work owner. Reassignment must prevent stale
ownership from authorizing conflicting work. Shutdown relinquishes membership
and cancels workers within a configured bound. The
[cluster control-plane proposal](../../../../.agents/notes/proposed/architecture/2026-09-07-cluster-control-plane.md)
owns membership, leases, fencing, and configuration rationale.

Scheduling must preserve instance and project ownership. Cluster membership
alone grants neither application identity authority nor developer data access.
Shard assignment and handoff retain their own
[consumer-scaling proposal](../../../../.agents/notes/proposed/architecture/2026-09-07-consumer-shard-scaling.md).

## 3. Desired Configuration and Reconciliation

Managed settings need one authority, an identifiable desired revision, and each
node's applied revision and status. Configuration publication uses an expected
revision to reject concurrent changes. Durable acceptance and successful fleet
convergence are distinct results.

Only settings explicitly classified as dynamically safe may reconcile without
a restart. A node validates a complete revision, stages resources, and either
applies that complete revision or reports failure while retaining the previous
one. Settings requiring restart must be identified before acceptance. Heartbeat,
retry, and work queues require bounds; recovery must not introduce competing
configuration authorities.

Static configuration remains an explicitly selected runtime operating mode.
Platform orchestration may build on deployment-platform discovery/configuration
or its own durable store, but the adapter and backend choice require a separate
availability, consistency, and operating-cost decision.

## 4. Monitoring and Operations

Management aggregates platform health and operational state for Syntrix employees.
Developer-facing Console diagnostics present the developer's own instance state;
project Identity remains inside the instance and handles enduser OAuth/OIDC
issuing and external-provider login.

Membership and configuration diagnostics should identify instance, node, lease
generation, desired/applied revision, and operation correlation without exposing
connection secrets or enduser credentials. Metrics, logs, and tracing remain
owned by the [observability proposal](../../../../.agents/notes/proposed/architecture/2026-09-07-application-observability.md)
and [monitoring design](../../monitor/003.metrics_collection.md).

Backup, restore, point-in-time recovery, and data/schema migration require their
own authorization, failure, and recovery contracts. This document does not choose
an API, persistence schema, backend, or backup implementation. The
[backup and recovery proposal](../../../../.agents/notes/proposed/feature/2026-09-07-database-backup-recovery.md)
owns that operating gap.

## 5. Current Gaps and Acceptance

The repository implements configured standalone/distributed startup and
logical-database lifecycle operations, not a platform Management service or
developer instance provisioning. Project realms and the target instance Identity
capabilities are also unimplemented. Current metadata and authentication storage
must not be presented as the platform's authority or as proof of target isolation.

A future control plane must demonstrate observable join/expiry/partition behavior,
stale-owner fencing, complete configuration revisions after failures, bounded
reconciliation and shutdown, and continued explicit static-mode operation.
Selecting its backend must account for availability and contention independently
of any developer instance's system-data store.
