# Developer Console

**Status:** Implemented bilingual developer login/shell, authentication, and predefined Kubernetes test-workload API; resource administration UI and full instance lifecycle remain target work.

## Audience and Ownership

`packages/console-server` is the independent developer-facing service. Console
accounts have authority over their own deployment requests and workloads. They
are separate from Management employees and application end users authenticated
by an instance's Identity module. The [platform architecture](../../../architecture.md)
owns this hierarchy; the [Console decision](../../../../.agents/notes/implemented/architecture/2026-10-11-console-server-postgres-kubernetes.md)
owns persistence, authentication, deployment recovery, and scope constraints.
The [client decision](../../../../.agents/notes/implemented/architecture/2026-10-12-console-client-session-and-distribution.md)
owns the browser session, locale, and static-distribution mechanisms.

A developer can ultimately own multiple Syntrix instances. Each instance contains
Syntrix runtime services, a private physical MongoDB business-document database,
and its private PostgreSQL system database. These databases use scoped
credentials and may run on shared servers. It owns projects, each with an
isolated end-user Identity realm and multiple logical databases. Console's PostgreSQL is a separate developer
control database; it does not replace any instance's system database.

The current service deploys predefined HTTP test workloads. It does not yet
allocate private instance databases or provision the managed runtime bundle,
administer projects, or proxy instance document and authentication APIs. The former embedded
administration SPA and Gateway static route have been removed. The independent
`packages/console-client` application delivers developer login and an authenticated
Overview. The Go backend remains API-only; the frontend does not yet expose
workload or instance administration pages.

## Service Structure

The service owns an independent Go module, entrypoint, HTTP server, and background
executor. Modules own their configuration types, defaults, and validation;
`internal/config` only loads and composes them.

| Module | Responsibility |
|---|---|
| Authentication | Configured developer bootstrap, password verification, opaque sessions, CSRF validation |
| Database | Console PostgreSQL connection and schema initialization |
| Workload | Developer ownership, desired lifecycle, idempotency, frozen template snapshots, operation records |
| Provisioning | Kubernetes client configuration, resource creation, readiness observation, identity-checked cleanup |
| Server | HTTP request validation, session adapters, API responses, process health |

Kubernetes execution is behind the provisioning module. When employee-facing
[Management](02.control_plane.md) supplies platform execution, Console can retain
developer ownership and durable request acceptance while replacing this adapter.
The process-level instance `services.Manager` is unrelated to that platform.

## Browser Client

The client owns React routes `/login` and `/overview`, session and language
providers, and native semantic controls with Console-owned light CSS tokens.
Borgee's client supplies the pinned palette/control/layout reference, not an
employee authority or shared account model. Overview shows the current developer
and a welcome state without invented resources or links to unsupported pages.
Unknown routes show a localized not-found page. Return navigation permits known
application routes only, never external or protocol-relative destinations.

The same final components/styles power a frontend-only interactive mockup for
login, restoration, expiry, failures, uncertain mutation recovery, locale
persistence, and mobile navigation. Fixtures and scenario controls are excluded
from production entrypoints. Desktop uses a compact sidebar/main layout; mobile
navigation traps focus, supports Escape/backdrop dismissal, and restores focus
to its trigger. Labels, autocomplete, keyboard submit, password visibility,
pending controls, and live error feedback are part of the login contract.

### Session Authority and Async Operations

The browser stores developer, expiry, and CSRF data in memory. Passwords, session
records, CSRF values, and cookies are not placed in localStorage/sessionStorage.
The backend cookie and `/auth/v1/me` own authority. Initial restoration hides
protected content; 401 is anonymous, while network/dependency failure displays
an unavailable state with Retry. Failed logout does not clear state as though
server revocation succeeded.

Requests carry a per-tab auth generation, and superseded reads are aborted. Only
current-generation results may publish a session or clear it. Same-tab login and
logout share a pending-operation barrier: expiry, visibility, and cross-tab
checks mark a dirty flag while a mutation runs, then coalesce one authoritative
`/me` check. A read cannot supersede that mutation or publish its earlier session.
Route and locale changes preserve owned pending mutations.

Timeout, cancellation, response loss, or invalid success JSON may hide an applied
login/logout. The controller reconciles `/me` without replaying the mutation. A
valid 200 or 401 establishes session or anonymous state; failed reconciliation
shows explicit unknown/unavailable state, retains the last session only as a
snapshot, and blocks protected content/mutations. 403 remains permission/CSRF
denial, not expired authentication; CSRF denial revalidates without automatic
mutation replay. Teardown aborts owned work, and the next mount restores afresh.

Expiry timers, visibility return, and secret-free BroadcastChannel notifications
trigger authoritative checks. A tab with a pending mutation queues the trigger.
Without BroadcastChannel, visibility and authenticated-request 401 remain
convergence triggers. Shared-cookie responses across tabs are not globally
ordered; after overlapping actions settle and a later `/me` succeeds, visible
tabs converge to current backend authority. Account change cancels private work
and clears account-owned page state. There is no refresh endpoint or sliding
session renewal.

### Language and Feedback

Lingui eagerly loads `en` and `zh-CN` catalogs before the first render. Preference
is `system | en | zh-CN`, stored under `syntrix.console.languagePreference`.
Explicit selection wins; system selection inspects browser languages in order,
accepting English variants and Chinese tags that resolve to the Hans script.
Unsupported languages use English; malformed tags are skipped. The runtime
updates `<html lang>` and owns browser language/storage event subscriptions.
Storage failure preserves working in-memory selection and displays localized
persistence feedback. Language activation does not remount forms, routes, or
sessions; errors remain categories/descriptors translated at render time.

Transport preserves operation, HTTP status, category, and request ID even for
non-JSON error bodies. UI feedback is localized; diagnostics exclude passwords,
CSRF/session values, request bodies, and raw backend error text. Requests failing
before the backend have no server request ID. Auth requests have a 30-second
deadline, allowing the backend's default 25-second deadline to respond first.

## Developer Authentication

Configuration declares stable developer IDs, usernames, and bootstrap passwords.
PostgreSQL stores account IDs and password hashes. Bootstrap creates missing
accounts; restarting with changed configuration does not silently reset an
existing password or transfer resource ownership. Duplicate IDs/usernames and
invalid configuration fail startup. Passwords and hashes are not public fields.

Login establishes a random opaque session with a separate CSRF token and a
bounded lifetime, defaulting to 24 hours. Hashed session credentials are stored
in PostgreSQL. The HTTP-only `console_session` cookie is scoped to Console, and
production deployment requires HTTPS with secure cookies. Login requires the
configured public origin; authenticated mutations require `X-CSRF-Token` matching
the session. Logout revokes the server-side session. Current-account reads derive
the developer from the verified session, never from a supplied developer ID.

Console sessions do not grant instance application privileges. Instance JWTs and
employee credentials do not authenticate Console requests. Developer OAuth,
profile editing, and credential-change flows remain future work; stable developer
IDs preserve workload ownership when those mechanisms are added.

## Durable Source Data

Console PostgreSQL is the source of truth for developer accounts, sessions,
workload ownership, accepted desired state, immutable template snapshots,
idempotency records, operation progress, Kubernetes object identities, and
observation timestamps. No instance PostgreSQL or Kubernetes ConfigMap substitutes
for this database. Database failure fails acceptance and authenticated operations;
there is no local or Kubernetes fallback authority.

Templates are configured by the operator. An accepted create request freezes the
template's image, ports, environment, resources, health checks, and Kubernetes
target. Restart and retry use that persisted snapshot even if configuration
later changes. Developers select an enabled template; they cannot submit
arbitrary Kubernetes objects or unrestricted deployment configuration.

Workload records retain desired state separately from observed status and
`observed_at`. An old successful observation is not proof of current availability.
Deleted workloads retain terminal and idempotency records so retries of an old
create request cannot resurrect them.

## Planned Managed Instances

The [managed-instance lifecycle](03.instance_lifecycle.md) owns the planned
allocation, API, reconciliation, configuration, and bilingual instance UI. Its
durable task sequence contains five implementation PRs; it does not change the
current API described below. The
[lifecycle proposal](../../../../.agents/notes/proposed/architecture/2026-10-12-console-instance-lifecycle.md)
owns allocation, execution, and deferral rationale.

Administrators register existing shared MongoDB, PostgreSQL, and NATS servers,
privileged credentials, and deployment profiles. Developers submit a name,
standalone/distributed mode, profile, and allowed origins. Console allocates a
physical MongoDB database and scoped user plus a private PostgreSQL database
and scoped role for each instance. Distributed mode can share a NATS account:
immutable instance IDs select unique streams, subject namespaces, and durable
consumers, and workers within one instance share its consumer. Database and
NATS server Pods are outside this lifecycle.

Console PostgreSQL will own resource registrations, profiles, immutable bindings,
revisioned desired configuration, lifecycle phases, allocation/cleanup receipts,
and encrypted secret custody. Runtime processes receive instance-scoped database
credentials and the permitted shared broker credentials; privileged database
provisioning credentials remain with Console. The
lifecycle extends the existing durable-intent and identity-checked execution
principles to databases, trigger artifacts, bootstrap, and runtime resources.
Employee Management execution, developer OAuth, and project realms remain
separate work. Current operator templates still require an isolated NATS server
or account because they use fixed trigger names; managed shared-account support
requires the runtime contract changes in the planned sequence.

## API and Lifecycle

The [Console API reference](../../../reference/console_api.md) owns payloads,
error responses, and request headers.

| Method and path | Behavior |
|---|---|
| `POST /auth/v1/login` | Verify persisted developer credentials and establish a Console session |
| `GET /auth/v1/me` | Return the session's developer, expiry, and CSRF token |
| `POST /auth/v1/logout` | Revoke the current session |
| `GET /api/v1/templates` | List available template IDs |
| `POST /api/v1/workloads` | Accept `template_id` with required `Idempotency-Key` |
| `GET /api/v1/workloads` | Return at most 100 workloads owned by the developer |
| `GET /api/v1/workloads/{id}` | Read an owned workload and its recorded observation |
| `DELETE /api/v1/workloads/{id}` | Persist deletion intent for an owned workload |

Every resource lookup derives ownership from the authenticated developer;
another developer's identifier does not disclose or mutate their workload.
Creation/deletion acceptance returns 202; an already deleted resource can return
its terminal state with 200. Acceptance is distinct from Kubernetes readiness.

Create first commits a resource record, template snapshot, desired state, and
operation identity in PostgreSQL. A developer-scoped idempotency key resolves to
the original operation; reusing it with different request content returns a
conflict.

One executor holds a PostgreSQL session advisory lock. Each workload transaction
uses a row lock to serialize its desired revision with the bounded Kubernetes
call and receipt. This prevents competing executors or a stale create worker
from contradicting accepted deletion. Losing database execution authority stops
new Kubernetes work. PostgreSQL and Kubernetes are not a shared transaction:
persisted intent and identity-checked retry recover an interruption between
external effect and receipt storage.

The fixed HTTP test template produces a Deployment and ClusterIP Service in the
configured namespace. The Deployment anchors resource ownership through
the Service's owner reference. Installation/workload identities and Kubernetes
UIDs identify resources; matching a name alone never authorizes adoption or
deletion. Foreign objects cause a visible failure. Readiness requires the intended
Deployment generation, updated/available replicas, and matching ready Service
endpoints. A failed Deployment rollout is reported as failed while reconciliation
continues.

Deletion commits intent before cleanup. The executor observes or removes only
matching resources with identity/UID checks, confirms their absence, and then
records the deleted terminal status. Failed or incomplete cleanup remains
visible and recoverable after restart. Deleted tombstones continue to be observed:
an earlier Kubernetes create can commit after its client request times out.
Any subsequently discovered owned resource returns to deleting and is cleaned.
The last observation confirms absence at that time; it is not an atomic barrier
against a remote request whose outcome remains uncertain.

## Static Distribution

The client ships independently as an nginx static image. Auth/API paths proxy to
the Console server under the same browser origin, preserving Host including port,
Origin, and fetch metadata without route rewrites. They never fall through to
SPA HTML. Direct application-route reloads serve the entry document; missing
assets return 404. HTML uses no-store and hashed assets use immutable caching.
Each image owns version-matched entry/assets. The example deployment uses one
replica with Recreate, accepting update downtime while keeping one release bundle
active; older open clients may need to reload after updates.

Development defaults to `http://localhost:5173` using Vite strictPort; a collision
fails rather than choosing an untrusted port. Explicit port/target overrides
require matching backend public-origin configuration. Relative
requests use same-origin cookies, and the proxy forwards to backend
`127.0.0.1:8090` with changeOrigin disabled. Backend `server.public_origin` must
match the browser origin. Production TLS termination supplies the public HTTPS
origin and Secure-cookie policy. Cross-origin direct API access is outside the
existing CORS contract.

The frontend manifest belongs to its package; the backend Kubernetes manifest
remains in `packages/console-server/deployment/kubernetes.yml`. The static web
container needs neither Kubernetes provisioning credentials nor a mounted
ServiceAccount token. It listens on 8080 with a read-only root filesystem and
writable configuration/temporary emptyDir volumes. Runtime `CONSOLE_API_ORIGIN`
selects the internal backend, defaulting to `http://console-server:8090`; the
backend public origin remains the browser's external origin. The
[client README](../../../../packages/console-client/README.md)
owns development, mockup, validation, and deployment commands.

## Development and Operations

The operator provides an existing Kubernetes development cluster, including k3d
when used locally. Console uses an explicit kubeconfig and context outside the
cluster, or an explicitly selected ServiceAccount mode inside the cluster.
The supplied deployment hosts Console in `syntrix-platform`, which can also
host future Management services. Requested test workloads run in `syntrix-tests`.
Current Kubernetes access uses one Console ServiceAccount and the role required
for those workload operations. Management's service permissions are defined
with its implementation; Console executes the present lifecycle directly.
Namespace and RBAC permissions bound its resource authority. Persisted targets
contain namespace and installation ID; both must match executor configuration.
The installation ID is stable for one Console installation and cluster target,
and must change when relocating to another cluster. A changed namespace or
installation ID rejects the old workload target. Console does not independently
prove cluster identity from a reused kubeconfig/context or create, initialize,
replace, or stop that cluster.

ClusterIP is an internal endpoint. Local verification can use port-forward
against the deployed Service; creation does not promise a public URL, Ingress,
domain, or certificate. The [package README](../../../../packages/console-server/README.md)
owns build/run instructions and supported configuration.

Structured logs correlate HTTP/deployment work using request ID, developer ID,
workload ID, status, and bounded error category where applicable. Logs and
responses exclude passwords, session/CSRF secrets, kubeconfig contents, and
database credentials. Observations include their time; process liveness alone
does not prove workload availability.

Schema upgrades may be destructive. This service does not supply legacy account,
namespace, or data migration, and startup does not implicitly wipe databases.
Disposable development resets are explicit operator actions.

## Remaining Instance Administration Requirements

Full instance provisioning adds durable storage, complete bundle readiness,
resource limits, credential distribution, backup/deletion policy, and endpoint
publication to the template lifecycle. Project management must preserve the
instance/project/database hierarchy and use independently authorized instance
operations. End-user Identity remains inside the selected instance.

The delivered login/shell has a final-style interactive mockup. Future resource
pages need the same treatment for empty, denied, stale observation, and operation
progress states. Navigation guards and hidden buttons remain presentation
behavior; server-side authorization owns access. The
[workload interface proposal](../../../../.agents/notes/proposed/feature/2026-10-12-console-workload-interface.md)
adds owned queries,
mutation idempotency, account-change cleanup, and bounded polling. Theme, OAuth,
self-service, and domain administration are not shell capabilities.

Runtime rule publication must validate a complete artifact before activation,
retain the previous valid version after failure, expose version/rollback state,
and audit administrative changes. Rule push/rollback idempotency retains its
original result for 24 hours; failed activation must not replace a complete valid
revision. These contracts are owned by the
[publication lifecycle](../../../../.agents/notes/proposed/architecture/2026-09-07-security-rule-publication-lifecycle.md),
[publication validation](../../../../.agents/notes/proposed/feature/2026-09-07-security-rule-publication-validation.md),
[account provisioning](../../../../.agents/notes/proposed/feature/2026-09-07-admin-account-provisioning.md),
and [audit](../../../../.agents/notes/proposed/feature/2026-09-07-administrative-audit-records.md)
proposals. Diagnostics, [realtime inspection](../../../../.agents/notes/proposed/feature/2026-09-07-console-realtime-inspection.md),
and [trigger management](../../../../.agents/notes/proposed/feature/2026-09-07-console-trigger-management.md)
still require complete scoped backend contracts. Future readiness aggregation
must distinguish ready, unavailable, unknown, and stale dependency reports;
Gateway liveness cannot turn failed authentication/storage checks into success.
[Account self-service](../../../../.agents/notes/proposed/feature/2026-09-07-console-account-self-service.md)
adds developer profile/credential operations to Console authority.
[Administrative CLI commands](../../../../.agents/notes/proposed/feature/2026-09-07-administrative-cli.md)
retain rule push/dry-run/activation/rollback/version listing and account
administration, using explicitly selected employee, developer, or instance scope.

A future data browser must preserve typed query pagination and bigint precision:
opaque cursors continue the requested limit, and query builders use the eight
shared operator spellings. Canonical integer text becomes int64; decimal/exponent
text becomes binary64. Integers render and copy as exact JSON tokens, and bigint
timestamps are range-checked before date conversion. Editors remove server
metadata from writes; documents with any recursively nested business int64 value
remain read-only with an explanation when using an ordinary JSON editor. Metadata
int64 fields alone do not make a document read-only. Collection discovery remains
separate from document sampling. See the [typed value contract](../../../reference/filters.md#typed-values)
and [instance Query API](../../../reference/api.md#query-operations). These
requirements survive removal of the previous UI; the new service does not expose
a document browser.
