# Developer Console and Instance Administration

**Updated:** October 10, 2026
**Status:** Accepted Console boundary; existing UI is embedded instance administration

## 1. Audience and Ownership

The developer Console service serves developers. Each developer creates and
manages one or more own Syntrix instances. It is separate from the Management
platform, which serves Syntrix employees and owns platform scheduling, monitoring,
and operations, and from instance runtimes, which serve application end users.
The [system architecture](../../../architecture.md) owns this hierarchy; the
[boundary decision](../../../../.agents/notes/proposed/architecture/2026-10-10-platform-console-instance-boundaries.md)
records the accepted direction and its implementation gaps.

Each instance contains runtime services, MongoDB, and PostgreSQL. It owns
projects, each with an isolated enduser identity realm and access to multiple
logical Syntrix databases. The Console presents developer administration of that
hierarchy. Application end users sign in to their project's runtime through the
application; they are not the audience of the developer Console.

Developer accounts, employee access, and project-local enduser identities have
different authorities. A user's display name, a logical database name, or a
client-side role indicator must not substitute for server-side ownership checks.
Console account protocols and the platform's backing storage remain separate
implementation decisions.

## 2. Accepted Console Responsibilities

The Console exposes the developer's own instance lifecycle and configuration,
with instance selection preceding project and logical-database administration.
Runtime operational details presented to a developer must remain scoped to that
developer's instances. Employee scheduling and fleet operations belong to
[Management](02.control_plane.md).

Project identity configuration belongs to the instance Identity module. Identity
is a peer runtime module alongside Indexer and Puller; it supports both the
instance's OAuth/OIDC issuer role and external-provider login for each project's
end users. Console configuration of that module does not turn Console into the
enduser issuer or move identity records into the platform control plane.

Instance PostgreSQL holds system data: projects, end users,
OAuth/provider/client/session data, and logical-database configuration and
metadata. MongoDB holds developer business documents. Project selection must
scope identity and data operations; selecting a logical database alone cannot
establish an isolated identity realm. Private system records are managed through
authorized system operations, not application document APIs. Deleting one
project database does not delete the project's end users.

## 3. Current UI and Gaps

`packages/console` currently implements an embedded administration SPA for a
single configured runtime. The gateway serves it at `/console/`; it calls that
runtime's authentication, logical-database, document, user, rules, and health
interfaces. Its [README](../../../../packages/console/README.md) owns development
and build commands.

This package does not implement the independent developer Console service or
instance provisioning. Its existing users and administrative roles are part of
the current shared runtime identity model, not separated developer accounts or
project-local enduser realms. Current user data and database metadata use
PostgreSQL, while revocation storage uses MongoDB. Projects, isolated realms,
OAuth/OIDC issuing, and external-provider login are not implemented.

| Area | Current embedded UI | Remaining target work |
|---|---|---|
| Scope | One runtime endpoint | Developer-owned instance selection and administration |
| Authentication | Runtime login and token refresh | Separate Console account protocol and project runtime identity |
| Databases | Existing logical-database pages | Project ownership and project-to-database scope |
| Data browser | Typed query pages and document tools | Server-enforced target hierarchy and authorization |
| Users | Runtime administration of current shared users | Project-local enduser lifecycle and realm isolation |
| Rules | Current rule inspection and publication interface | Complete versioning, validation, activation, and rollback lifecycle |
| Observability | Existing runtime health integration | Scoped developer diagnostics and separate employee fleet operations |
| Realtime and triggers | Existing transport APIs; incomplete management pages | Inspection and operational controls with complete server contracts |

Capability ownership in this table does not claim that all existing management
pages or their planned features are complete. The
[reference alignment proposal](../../../../.agents/notes/proposed/process/2026-09-07-reference-contract-alignment.md)
owns current API documentation gaps.

## 4. Existing Frontend Structure

The package uses React, TypeScript, Vite, TailwindCSS, Zustand, React Router,
Axios, and Lucide. Its package manifest owns dependency versions.

```text
packages/console/
├── package.json
├── vite.config.ts
├── src/
│   ├── lib/                 # Runtime API and document helpers
│   ├── router/              # Route definitions and layout wrappers
│   ├── pages/               # Authentication, data, and administration pages
│   ├── components/          # Shared UI and feature components
│   └── stores/              # Current embedded app authentication state
└── tests/                   # Frontend behavior checks
```

The gateway resolves built assets from `../console/dist` when the runtime starts
in `packages/syntrix`. The Go build does not generate frontend assets. This is the
current embedded-UI deployment contract; it does not determine how the future
independent Console service is packaged or hosted. The
[package layout decision](../../../../.agents/notes/implemented/architecture/2026-10-09-package-layout.md)
and [build-delivery proposal](../../../../.agents/notes/proposed/process/2026-09-07-console-build-delivery.md)
own those details and remaining distribution work.

## 5. Data Browser Contract

| Capability | Query value and page behavior |
|---|---|
| Document list | Use the database-scoped typed page API, preserve the requested limit, and pass opaque `nextCursor` for continuation |
| Query builder | Use the eight shared operator spellings; canonical integer text becomes int64, decimal/exponent text becomes binary64 |
| Viewer, preview, and copy | Preserve bigint values as exact JSON integer tokens |
| Timestamps | Range-check bigint before converting to a JavaScript date |
| JSON editor | Remove server metadata from writes; documents containing any business int64 field are read-only with an explicit explanation |

The editor restriction prevents ordinary JSON writes from changing an integer's
type or precision after lossless query decoding. It applies recursively to
business data; metadata int64 fields alone do not make a document read-only.
Collection navigation remains separate from query pagination. See the
[typed value contract](../../../reference/filters.md#typed-values) and
[Query API](../../../reference/api.md#query-operations).

These existing value-preservation rules remain useful when the UI gains project
and instance selection. They do not themselves authorize data access or provide
realm isolation.

## 6. Runtime Administration Requirements

The following requirements describe unfinished runtime administration features.
They do not define new Console or Management endpoints.

### Rules and Enduser Administration

Rule publication must validate a complete artifact before activation and expose
an identifiable active version. Invalid or failed activation must preserve the
previous complete version. Nodes retain the last valid rules when reload fails,
report degraded status, and surface detailed diagnostics only to authorized
administrators. Activation, rollback, user enable/disable, and role changes need
server authorization and audit records.

Dry-run, version history, rollback, administrative account provisioning, and
publication validation remain owned by their proposals:

- [Rule publication lifecycle](../../../../.agents/notes/proposed/architecture/2026-09-07-security-rule-publication-lifecycle.md)
- [Rule publication validation](../../../../.agents/notes/proposed/feature/2026-09-07-security-rule-publication-validation.md)
- [Account provisioning](../../../../.agents/notes/proposed/feature/2026-09-07-admin-account-provisioning.md)
- [Administrative audit records](../../../../.agents/notes/proposed/feature/2026-09-07-administrative-audit-records.md)

Enduser administration targets a selected project's realm in the accepted
architecture. Account identifiers, provider bindings, sessions, and permissions
must remain scoped to that realm; shared runtime users are the current
implementation gap.

### Diagnostics and Inspection

Developer diagnostics can describe the health of their instances, rule reloads,
realtime activity, and trigger execution. Fleet scheduling and employee operations
remain Management responsibilities. Realtime inspection and trigger-management
pages require complete server APIs and must not imply a supported ordinary SDK
subscription capability merely because private replica WebSocket transport exists.
See the [realtime inspection proposal](../../../../.agents/notes/proposed/feature/2026-09-07-console-realtime-inspection.md)
and [trigger management proposal](../../../../.agents/notes/proposed/feature/2026-09-07-console-trigger-management.md).

## 7. Security and Interaction Requirements

All privileged operations require server-side authorization within the selected
instance and project. Client-side navigation guards and hidden controls are UI
behavior, not the authorization boundary. Sensitive fields, password hashes,
provider secrets, and signing material must not be returned to the browser.

Production entry points require HTTPS. Explicit allowed origins, rate limits,
request-size limits, and bounded paginated reads protect administration APIs.
Administrative mutations must report failure, support confirmation where the
operation is destructive, and leave an audit trail identifying actor, scope,
operation, result, and request correlation without credentials. Rule dry-runs,
loading states, progress, and error feedback help developers assess operations.

The current embedded app sends bearer tokens in Authorization headers, stores
its runtime authentication state in browser local storage, refreshes tokens,
and displays a session warning. Those facts describe existing behavior; the
future Console account protocol and project OAuth/OIDC session design remain
open. Their contracts must define expiry, refresh, logout, credential protection,
and realm scope explicitly rather than inherit browser storage assumptions.

Existing routes are documented by the [REST reference](../../../reference/api.md)
and [gateway route registration](../../../../packages/syntrix/internal/gateway/rest/handler.go).
Future instance provisioning, project management, identity configuration,
versioned rule operations, and employee operations require their own accepted
contracts before endpoint or storage schemas are specified.
