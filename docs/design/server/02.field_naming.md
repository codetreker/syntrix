# Field Naming Conventions

**Date:** December 30, 2025
**Status:** Canonical Reference
**Purpose:** Single source of truth for field names across all system components

## Overview

This document defines the canonical field names used throughout the Syntrix system. All components (storage, API, events, SDK) MUST use these exact names to ensure consistency.

**When in doubt, refer to this document.**

---

## 1. Identifier Fields

### 1.1 Database Identifier

| Context | Field Name | JSON Key | BSON Key | Notes |
| ------- | ---------- | -------- | -------- | ----- |
| Storage (Document) | `Database` | `database` | `database` | Stored in MongoDB |
| Storage (Event) | `Database` | `database` | - | Change stream events |
| Puller (NormalizedEvent) | `Database` | `database` | - | **Shorter key for wire format** |
| API Response | - | `database` | - | Matches storage |

**Rationale:** Puller events use shorter `database` key to reduce bandwidth on high-volume event streams. All other contexts use `database` for clarity.

### 1.2 Document Identifier

| Context | Field Name | JSON Key | BSON Key | Notes |
| ------- | ---------- | -------- | -------- | ----- |
| Storage (Document) | `Id` | `id` | `_id` | Full path hash: `database:hash(fullpath)` |
| Storage (Event) | `Id` | `id` | - | References document ID |
| Puller (NormalizedEvent) | `DocumentID` | `documentId` | - | Explicit name for clarity |
| API Response | - | `id` | - | User-facing document ID |

**Rationale:**
- Storage uses short `id` / `_id` following MongoDB conventions
- Puller uses explicit `documentId` to distinguish from `eventId`

### 1.3 Event Identifier

| Context | Field Name | JSON Key | Notes |
| ------- | ---------- | -------- | ----- |
| Storage (Event) | `ChangeID` | `changeId` | Stable identity of one source change across watches and retries |
| Puller (NormalizedEvent) | `EventID` | `eventId` | Puller event identity |

`Event.ChangeID` is issued by the Store and is separate from `Event.Id`, which
remains the document key. Neither field is an ordered checkpoint. Puller
currently creates its event identities through its direct Mongo ingestion path;
it does not consume Store `ChangeID` values.

### 1.4. Store Watch Checkpoints

`WatchCheckpoint` is an opaque Store-issued string. It can be persisted or
transmitted, but callers must not inspect its backend encoding or compare its
bytes for ordering. `WatchStream.InitialCheckpoint()` establishes the initial
source boundary. Each `WatchFrame.Checkpoint` reports a completed source prefix,
including when `WatchFrame.Event` is nil. Persist it only after all required work
through that frame succeeds. Native resume tokens do not belong to
`storage.Event`. The [Watch contract](core/storage/03.stores.md#2-document-watch)
owns scope, source identity, and failure behavior.

### 1.5 JWT Claim Identifiers

| Context | Field Name | JSON Key | Notes |
| ------- | ---------- | -------- | ----- |
| JWT Claims | `Database` | `tid` | Legacy claim key retained |
| JWT Claims | `UserID` | `oid` | Legacy claim key retained |

**Rationale:** JWT claims keep `tid`/`oid` to preserve backward compatibility with existing tokens and integrations. The auth layer maps these to internal `Database`/`UserID` values.

## 2. Operation Types

### 2.1 Storage Event Types

Used in `storage.Event.Type`:

| Constant | Value | Description |
| -------- | ----- | ----------- |
| `EventCreate` | `"create"` | Document inserted, replaced, or restored from a tombstone |
| `EventUpdate` | `"update"` | Document modified |
| `EventDelete` | `"delete"` | Logical deletion; Store Watch filters physical cleanup into progress |

### 2.2 Puller Operation Types

Used in `NormalizedEvent.OperationType`:

| Constant | Value | MongoDB Source | Description |
| -------- | ----- | -------------- | ----------- |
| `OperationInsert` | `"insert"` | `insert` | New document |
| `OperationUpdate` | `"update"` | `update` | Field update |
| `OperationReplace` | `"replace"` | `replace` | Full document replace |
| `OperationDelete` | `"delete"` | `delete` | Mongo document physically removed |

**Mapping from MongoDB to Storage:**

| MongoDB operationType | Storage EventType | Notes |
| --------------------- | ----------------- | ----- |
| `insert` | `create` or `delete` | Inserted state determines whether the document is live or a tombstone |
| `update` | `update`, `create`, or `delete` | Immutable deleted-field changes identify restore or soft-delete operations |
| `replace` | `create` or `delete` | Replacement state determines whether the document is live or a tombstone |
| `delete` | `delete` | Direct mapping |

**Important:** Puller preserves MongoDB's original operation type (`insert`, `update`, `replace`, `delete`) for downstream consumers that need the distinction. Storage layer simplifies to three types.

Business conversion ignores raw physical `delete`; a tombstone update or
replacement represents Syntrix logical deletion. Store Watch `EventDelete`
covers both source changes. See [deletion semantics](core/storage/03.stores.md#document-deletion-and-physical-cleanup).

## 3. Timestamp Fields

### 3.1 Document Timestamps

| Field | Type | JSON Key | BSON Key | Description |
| ----- | ---- | -------- | -------- | ----------- |
| `CreatedAt` | `int64` | `createdAt` | `created_at` | Unix milliseconds, set once on creation |
| `UpdatedAt` | `int64` | `updatedAt` | `updated_at` | Unix milliseconds, updated on every write |

### 3.2 Event Timestamps

| Context | Field | Type | JSON Key | Description |
| ------- | ----- | ---- | -------- | ----------- |
| Storage Event | `Timestamp` | `int64` | `timestamp` | Unix nanoseconds; Mongo source cluster time has second precision |
| Puller Event | `Timestamp` | `int64` | `timestamp` | Unix milliseconds |
| Puller Event | `ClusterTime` | `primitive.Timestamp` | `clusterTime` | MongoDB cluster time `{T, I}` |

Store event timestamps are metadata, not an ordering or resume position.
`WatchCheckpoint` carries the Store continuation; converting a Store timestamp
to a Puller representation requires an explicit unit and semantic decision.

**ClusterTime Format:**
```json
{
  "clusterTime": {
    "T": 1234567890,
    "I": 1
  }
}
```

- `T`: Seconds since Unix epoch
- `I`: Increment within the same second (ordinal, not time-based)

## 7. Puller-Specific Fields

### 7.1 NormalizedEvent Schema

This is the canonical event schema for inter-service communication.

```go
type NormalizedEvent struct {
    // Identity
    EventID      string `json:"eventId"`      // Unique event ID
    Database     string `json:"database"`       // Database identifier (short key)
    Collection   string `json:"collection"`   // Collection name
    DocumentID   string `json:"documentId"`   // Document identifier

    // Operation
    OperationType OperationType          `json:"operationType"` // insert/update/replace/delete
    FullDocument  map[string]interface{} `json:"fullDocument,omitempty"`
    UpdateDesc    *UpdateDescription     `json:"updateDescription,omitempty"`

    // Metadata
    ClusterTime   primitive.Timestamp `json:"clusterTime"`
    TxnNumber     *int64              `json:"txnNumber,omitempty"`
    Timestamp     int64               `json:"timestamp"`
}
```

### 7.2 UpdateDescription Schema

```go
type UpdateDescription struct {
    UpdatedFields   map[string]interface{} `json:"updatedFields,omitempty"`
    RemovedFields   []string               `json:"removedFields,omitempty"`
    TruncatedArrays []TruncatedArray       `json:"truncatedArrays,omitempty"`
}

type TruncatedArray struct {
    Field   string `json:"field"`
    NewSize int    `json:"newSize"`
}
```

## 9. Naming Convention Rules

### 9.1 Go Field Names

- Use `PascalCase` for exported fields
- Use `camelCase` for unexported fields
- Suffix with type for clarity: `Database` not `Database`, `DocumentID` not `Document`

### 9.2 JSON Keys

- Use `camelCase` for all JSON keys
- Keep keys short but descriptive
- Exception: Puller uses `database` (not `database`) for bandwidth optimization
- Exception: JWT claims keep `tid` and `oid` for compatibility

### 9.3 BSON Keys

- Use `snake_case` for all BSON keys
- Exception: `_id` follows MongoDB convention
- Exception: `fullpath` - common developer idiom, kept as single word

### 9.4 Constants

- Use `PascalCase` for Go constants
- String values use `lowercase` (e.g., `EventCreate = "create"`)

## 11. Store and Puller Integration

Store events and Puller events are separate interfaces. Current Puller ingestion
uses a Mongo client directly, so these fields do not describe an implemented
Store-to-Puller adapter:

| Store value | Integration obligation |
|---|---|
| `Event.Id` | Preserve document identity independently of change identity |
| `Event.ChangeID` | Preserve stable source-change identity independently of Puller replay ordering |
| `Event.Database` | Preserve logical database scope |
| `Event.Type` | Define the mapping from Store create/update/delete semantics |
| `Event.Document`, `Event.Before` | Preserve available payloads without claiming guaranteed historical images |
| `Event.Timestamp` | Preserve documented units and source-time meaning explicitly |
| `WatchFrame.Checkpoint` | Persist after required ingestion work, separately from the event payload |

The former Store API accepted raw `interface{}` resume tokens without a public
durable codec. Callers now use Store-issued `WatchCheckpoint` values. The Mongo
decoder does not infer legacy encodings; persisted old tokens require an explicit
migration or a deliberate new starting boundary. The
[Store Watch note](../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md)
owns this change and the remaining Puller integration costs.
