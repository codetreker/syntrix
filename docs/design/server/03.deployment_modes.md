# Instance Runtime Deployment Modes

**Updated:** October 12, 2026
**Status:** Implemented runtime modes, standalone/distributed templates, and manifest generation;
platform orchestration remains proposed

## 1. Deployment Boundary

The modes in this document choose how services communicate inside one Syntrix
instance. They do not define the Management platform or developer Console service.
The [system architecture](../../architecture.md) and
[boundary decision](../../../.agents/notes/proposed/architecture/2026-10-10-platform-console-instance-boundaries.md)
own those separate components and their audiences. The proposed
[managed runtime contract](console/04.managed_runtime_contract.md) specifies
Console-consumable rendering, broker attachment, staged initialization, and
role readiness; the operating commands here describe the delivered runtime.

The target instance owns Syntrix runtime services and private physical MongoDB
and PostgreSQL databases with scoped credentials. Database servers may be shared.
It owns projects with isolated enduser realms; a project can use multiple logical
Syntrix databases. Those ownership rules hold whether runtime services share a
process or run separately. Current code does not yet implement projects, project
realms, or the target OAuth/OIDC capabilities.

## 2. Mode Comparison

| Aspect | Standalone | Distributed |
|---|---|---|
| Startup | `--standalone` | `--all` or selected service flags |
| Service communication | Direct calls | gRPC between applicable services |
| Process layout | One process | One process or separate processes |
| Scaling | Shared process resources | Separate role placement with singleton state-owner limits |
| Fault isolation | Shared process fate | Depends on actual process placement |
| Service addressing | Local references | Configured service URLs |
| Trigger transport | In-memory pubsub | External NATS JetStream |

Mode determines communication independently of process placement. In distributed
mode, `--all` runs runtime services in one process using gRPC; sharing a process
does not make it standalone or provide process-level fault isolation.

## 3. Mode Selection

| Input | Result |
|---|---|
| `--standalone` | Standalone |
| `deployment.mode: standalone` without `--standalone` | Standalone |
| `deployment.mode: distributed` | Distributed unless `--standalone` overrides it |
| No configured mode | Distributed by default unless `--standalone` is supplied |

The CLI reads the configured mode and lets `--standalone` override it. `--all`
and individual service flags select services after mode resolution; they do not
override a configured standalone mode. In standalone mode, the runtime starts
the local service assembly irrespective of selected distributed service flags.

The configuration and CLI choose runtime startup. They do not create developer
instances, assign a platform owner, or provision project-local identity realms.

## 4. Current Process Assembly

```text
Standalone process:
Gateway -> local Query -> local Indexer -> local Puller
Streamer -> local Puller
Evaluator -> in-memory pubsub -> Delivery

Distributed mode, one or multiple processes:
Gateway -> Query gRPC client
Query -> Indexer gRPC client
Indexer / Streamer / Evaluator -> Puller gRPC client
Evaluator -> NATS JetStream -> Delivery
```

The existing `services.Manager` initializes shared storage and identity
dependencies, creates local services or remote clients, registers gRPC services,
and manages startup and shutdown. It is process dependency injection, not the
employee-facing Management platform. The current password/account/token
implementation remains embedded under `identity/authn`; transport-free
contracts live under `internal/identity`. Gateway owns required/optional HTTP
Bearer adapters and the local document-authorization engine. Realtime consumes
its token verifier, and Trigger Delivery consumes its system-token issuer.
`authn.NewServices` constructs the local account, shared public-key verifier,
and system-token issuer separately. The verifier retains only public material,
but API/Trigger Worker process assembly still loads the configured private key
to construct local issuing capabilities. These object boundaries do not add a
remote Identity service or private-key-free Gateway deployment. Identity runtime
owns local repository/capability composition and administrator bootstrap;
document/catalog assembly borrows the same physical Backends. Manager stops
consumers before closing the Backends owner once. Verification-key distribution
and independent Identity deployment remain pending. Identity owns YAML `identity.authn`/`identity.admin`; Gateway owns
`gateway.authz` and its configuration lifecycle. Deployment files and local
overrides must place custom rule paths under `gateway.authz.rules_path`.
A separately scoped project Identity
module with issuer and external-login responsibilities remains target work.

In-memory standalone pubsub is not an embedded NATS server or a durable broker.
An `embedded_nats` configuration field does not establish that implementation.

## 5. Operating Commands

Run from the repository root:

```bash
make -C packages/syntrix build
(cd packages/syntrix && ./bin/syntrix --standalone)
```

Standalone still requires the configured MongoDB and PostgreSQL services. The
[development environment](../../../deployment/dev/README.md) owns infrastructure
setup. MongoDB must support change streams through a replica set.

Distributed mode can run all services together or selected services:

```bash
(cd packages/syntrix && ./bin/syntrix --all)
(cd packages/syntrix && ./bin/syntrix --query --indexer)
```

Configure service addresses for distributed communication, for example:

```yaml
gateway:
  query_service_url: "localhost:50051"
  indexer_service_url: "localhost:50051"
  puller_service_url: "localhost:50051"
```

The supplied configuration and relative data/log paths assume
`packages/syntrix` as the working directory. Console runs independently from
`packages/console-server`; the former embedded frontend and Gateway static route
are removed. See the [Console README](../../../packages/console-server/README.md)
for its PostgreSQL and Kubernetes prerequisites.
The [package layout decision](../../../.agents/notes/implemented/architecture/2026-10-09-package-layout.md)
owns these paths.

## 6. Container, Templates, and Manifest Generation

The instance package owns its [Dockerfile](../../../packages/syntrix/Dockerfile),
[standalone template](../../../packages/syntrix/deployment/standalone/kubernetes.template.yml),
[distributed template](../../../packages/syntrix/deployment/distributed/kubernetes.template.yml),
and `syntrix-cli render-kubernetes`. The image contains the statically built
instance binary. Configuration, connection credentials, and signing keys remain
mounted runtime inputs; packaging does not change authentication or document API
contracts. The [manual release workflow](../../../packages/syntrix/deployment/RELEASE.md)
publishes a public amd64/arm64 image and an archive containing both Linux CLIs,
metadata, and version-matched deployment files. Main-only dispatch fixes the
source SHA, and build/tests precede remote tag creation so a compilation or test
failure cannot reserve a version. Anonymous image access and an uploaded archive
precede Release publication. Daily UTC tag allocation and partial-publication
limits are owned by the [release decision](../../../.agents/notes/implemented/process/2026-10-13-manual-syntrix-release.md).

The generator accepts a template file and one strict YAML values document. Values
select mode, namespace, resource prefix, image, storage, existing connections,
origins, administrator bootstrap, and per-role workload names, replicas, and CPU/
memory requests/limits. Unknown fields, duplicate keys, multiple YAML documents,
invalid names/quantities, missing roles, unsupported replica counts, and requests
above limits fail generation. Template parse/execution diagnostics omit source
contents and runtime values while preserving their raw cause in the error chain.
Rendering and YAML validation finish before stdout/file emission; their failures
leave stdout empty and an existing private output file unchanged. The
[deployment guide](../../../packages/syntrix/deployment/README.md) owns commands
and values.

Both modes require existing MongoDB and private instance PostgreSQL. Every MongoDB
advertised replica member must be reachable from Pods, and PostgreSQL credentials
must permit initialization of system tables. Distributed mode additionally
requires existing NATS JetStream in an instance-isolated server or account.
Current templates use fixed `TRIGGERS` stream/subjects and durable consumer
`consumer`; Kubernetes names do not isolate those broker artifacts. Database
installation, source persistence, and backups remain operator-owned; templates create only runtime resources.

| Placement | Normal process layout and persistent state |
|---|---|
| Standalone | One local service assembly, one runtime claim retaining signing keys, Pebble indexes/progress, and Puller buffers |
| Distributed | API, Query, Puller, Indexer, Streamer, Trigger Evaluator, and Trigger Worker Deployments; separate Puller and Indexer claims; operator-managed shared signing-key Secret |

Distributed API and Trigger Worker issuing capabilities use the same immutable
PKCS#1 RSA signing-key Secret as bootstrap. This distributes existing local
Identity capabilities; it does not create an independently deployed Identity
service. Standalone can use that Secret or retain its generated signing key in
its data claim.

State-owning standalone, Puller, Indexer, and Trigger Evaluator workloads permit
zero or one replica. Other distributed roles accept explicit replica counts up
to Kubernetes' signed 32-bit limit, but these values do not establish fleet
coordination. API authorization/rule caches remain process-local; a rule push to
one replica is not broadcast. Distributed Trigger transport currently creates a
MEMORY JetStream stream and uses the durable consumer named `consumer`; a NATS
volume does not make pending trigger tasks survive a NATS restart. Standalone
Trigger transport is also in-memory. These are current runtime limits, not
additional guarantees supplied by the templates.

Normal rendering honors configured replicas. Explicit bootstrap rendering forces
all normal Deployments to zero and adds a temporary standalone maintenance Pod
with `restartPolicy: Never`. Distributed bootstrap mounts both derived-store
claims at their normal paths so the Indexer catalog and Puller lineage remain
usable by the later separated roles. All external/source writers and MongoDB TTL
cleanup must remain paused, and existing state-owning Pods must stop before the
maintenance Pod starts. The renderer requires both `--bootstrap` and
`--writes-quiesced`; that attestation does not itself fence writers.

The operator confirms bootstrap's applied subscription-readiness barrier,
gracefully deletes the maintenance Pod and waits for deletion, then applies a
normal render. This gives one process exclusive ownership of the derived stores
and prevents bootstrap from automatically repeating on Pod restart. Compatible
initialized state can start with normal rendering; invalid state fails rather
than silently rebuilding. The [Indexer bootstrap contract](indexer/04.storage.md#offline-bootstrap-and-startup)
owns recovery.

`services.Manager.Start` returns synchronous local Puller/Indexer startup errors
and rejects startup before bootstrap readiness. The CLI cancels owned work and
invokes shutdown before returning a startup failure as a nonzero exit. A normal
Kubernetes workload restarts the failed container and validates persistent state
again, allowing a delayed Puller to become available without a second dependency
retry loop in Manager. Invalid derived state still fails closed; process restart
does not imply bootstrap or reset. During Manager startup, signal cancellation is
normal shutdown only when the owner is canceled and the returned error also
represents cancellation.

API and bootstrap probes use `/health` on port 8080. Other distributed roles use
TCP probes on port 9000; the runtime does not expose a gRPC health RPC for these
probes. Exact GET/HEAD requests to `/health` bypass the general application limiter
without changing other endpoint or authentication budgets. Listener availability
does not prove dependency, Indexer replay, or consumer readiness, and TCP probes
can briefly pass during startup validation/replay. Confirm a real authenticated
indexed query through the normal API before resuming writes and TTL cleanup.

The [deployment decision](../../../.agents/notes/implemented/architecture/2026-10-12-instance-container-kubernetes.md)
records ownership, persistence, bootstrap, and scaling rationale. Public TLS
ingress and source-database lifecycle remain separate operator responsibilities.

## 7. Platform Orchestration

The Management platform serves Syntrix employees and owns scheduling, monitoring,
and operations across managed instances. The developer Console serves developers
who create and manage their own instances. Neither component is produced merely
by selecting standalone or distributed runtime startup.

Membership leases, safe configuration reconciliation, ownership fencing, and the
Management durable backend remain proposed in the
[control-plane design](console/02.control_plane.md). Static runtime configuration
continues to have one explicit authority per managed setting. Platform storage
must not borrow a developer instance's PostgreSQL system-data store. Console
already owns separate PostgreSQL source data and a direct Kubernetes adapter for
predefined test workloads; it does not deploy complete instances or supply the
Management fleet reconciler. Its development cluster is operator-provided, with
an explicit context and namespace. The generated service manifests are operator deployment
artifacts and do not add a Console provisioning API.

The planned [Console managed-instance lifecycle](console/03.instance_lifecycle.md)
reuses the runtime bundle renderer while adding administrator-registered shared
servers, per-instance physical MongoDB/PostgreSQL databases and scoped
credentials, and durable Console-owned reconciliation. Distributed managed
instances use per-instance stream/subject/consumer names within a shared NATS
account; workers of the same instance share one consumer. That support requires
planned runtime contract changes and does not apply to the current fixed-name
operator templates. Runtime provisioning does not create database/NATS server
Pods or implement the employee Management service. The managed-instance design
owns its five-PR implementation sequence and acceptance requirements.
