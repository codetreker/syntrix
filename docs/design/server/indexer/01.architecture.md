# Indexer Service Architecture

Date: December 26, 2025
Status: Draft
Scope: Internal layout and data flows for the Indexer service.

## Why
- Provide accelerated lookup/ordering for queries while keeping storage as the source of truth.
- Decouple index maintenance from Query Engine so they can evolve independently.
- Allow pluggable index backends (in-memory → RocksDB/external KV) without touching Query logic.

## Overview

The Indexer maintains derived scalar and membership indexes from source documents.
Native Puller events and offline source scans share projection rules. Query uses
ordered candidate streams and independently validates authoritative documents.

```text
Query -> Indexer candidate stream -> concrete index partition/view
  |                                       ^
  +-> authoritative Store reads           |
                                   atomic projections + progress
                                          ^
                                native Puller / offline Store scan
```

Production initialization uses a complete write-quiesced bootstrap catalog.
Persistent restart validates native replay history and applies a ready barrier;
memory process loss requires rebuilding. The
[storage contract](04.storage.md#offline-bootstrap-and-startup) owns these boundaries.
A separate local event buffer and automatic online rebuild orchestration remain
part of the proposed recovery design below, not prerequisites already supplied
by production startup.

## Package Layout

```
├── manager/               - Index manager (template matching, index routing)
├── encoding/              - OrderKey encoding/decoding
├── template/              - Index template loading and matching
├── mem_store/             - In-memory index store
├── persist_store/         - PebbleDB persistent store
├── rebuild/               - Rebuild orchestration and throttling
├── reconciler/            - Index reconciliation
├── grpc/                  - gRPC server implementation
├── client/                - gRPC client for distributed mode
└── config/                - Indexer configuration
```

The rebuild-related modules describe broader recovery facilities. Production
bootstrap uses the existing native Puller buffer and the shared projection/store
contracts; automatic online reconciliation remains proposed.

## Service Interface

| Operation | Responsibility |
|---|---|
| `OpenCandidates` | Complete ordered groups, pinned index view, typed predicate assignments, and work accounting |
| `Search` | Internal single-result index lookup |
| `ApplyDocumentProjection` | Replace complete multikey postings with applied progress |
| `Bootstrap` | Quiesced complete source scan and atomic catalog publication |
| `Start` / `WaitReady` | Validate stored coverage/replay, then wait for applied and flushed readiness |
| `Health` / `Stats` | Availability and instance observations |

The [candidate protocol](03.grpc.md#ordered-candidate-stream) owns the local/gRPC
query contract; source documents remain the authority.

`Stats(ctx)` samples the current Service instance across all databases. Local
and remote calls share the [statistics contract](03.grpc.md#statistics): loaded
template count, processed-event count, and local last-count time. Event counters
reset with a new Service instance; concurrent samples are not joint atomic snapshots.

## Data Flows

### Puller Subscription

Indexer consumes native Puller events under a diagnostic consumer label. It
persists the existing progress marker atomically with document projections. A
verified subscription validates backend identities, buffer lineages, and retained
history. The ordered ready frame follows replay; Indexer becomes ready only after
all preceding events have been applied and flushed.

Subscription/capture failures are visible and make serving unavailable. A broken
boundary does not silently restart at current head. Automatic history-gap repair
remains in the [recovery proposal](../../../../.agents/notes/proposed/architecture/2026-09-07-indexer-recovery-lifecycle.md).

### Index Update Flow

```text
native Puller event with typed values and independent logical identity
     -> match concrete collection templates
     -> build every complete posting replacement
     -> atomically publish replacements and progress
```

Empty replacement sets remove previous memberships. Logical tombstones contain
cleared business data; physical source cleanup is not another business deletion.
Projection errors preserve the failure and prevent progress from passing the
failed event.

### Search Flow

```text
Query -> select complete access/order plan -> pin generation and view
     -> merge branches into complete groups -> authoritative source reads
     -> validate all predicates, visibility, current position and posting
     -> refill final document page -> documents + cursor + effective order
```

The [index design](02.index.md#query-to-index-matching-rules) owns eligibility and
numeric/bound semantics. Store reads are explicit authoritative reads; index lag
and source mutations do not create a snapshot across pages.

### Recovery Scenarios

| Scenario | Supported behavior |
|---|---|
| Initial deployment / memory-state loss | Explicit writer-quiesced offline bootstrap |
| Complete persistent restart | Catalog/fingerprint/progress validation and applied replay readiness |
| Changed templates / missing catalog / incompatible derived format | Fail availability; explicit maintenance reset and complete rebuild |
| Lost retained history / changed buffer lineage | Reject resume; no silent current-head reset |
| Online rebuild during writes | Proposed recovery work |

An unavailable or rebuilding index produces an explicit query error. Query does
not fall back to an unrestricted source scan or a truncated 500-document result.
The two direct public routes remain deliberate unordered listing and ID-only
lookup paths. HTTP error mapping belongs to the
[Query API](../../../reference/api.md#query-errors).

## Index Templates

Index templates define which fields to index for which collections. For detailed template definition, pattern matching rules, and conflict handling, see [Index Implementation Details](02.index.md#index-templates).

### Template Definition (YAML)

```yaml
templates:
  - name: chats_by_timestamp
    collectionPattern: users/{uid}/chats
    fields:
      - { field: timestamp, order: desc }
    includeDeleted: true

  - name: messages_by_sender
    collectionPattern: rooms/{rid}/messages
    fields:
      - { field: senderId, order: asc }
      - { field: timestamp, order: desc }
    includeDeleted: true
```

## In-Memory Index Structure

```
Index Manager
    │
    └─> map[string]*Database  (keyed by database name)
            │
            └─> Database
                  ├── Name: "myapp"
                  ├── Mu: RWMutex
                  │
                  └─> map[string]*Index  (keyed by pattern|templateIdentity)
                          │
                          └─> Index
                                ├── Pattern: "users/*/chats"
                                ├── TemplateID: "timestamp:desc"
                                ├── Mu: RWMutex
                                ├── ByID: map[string][]byte  (docID → OrderKey)
                                └── Tree: btree[OrderKey → DocRef]
```

**Two-Layer Design**:
- First layer: `map[database]*Database` for database-level isolation and lifecycle management
- Second layer: `map[pattern|template]*Index` for indexes within each database

**Benefits**:
- Database deletion: remove entire Database object without scanning all indexes
- Database-scoped index management; callable Stats remains instance-wide
- Clearer code structure aligned with business concepts
- Same collection pattern in different databases = completely isolated indexes

For detailed index structure, OrderKey encoding, and search execution, see [Index Implementation Details](02.index.md#projection-and-read-views).

## Event Buffer

The proposed online recovery design uses a separate local event buffer for
concurrent rebuild catch-up. This section records that future design; current
offline bootstrap relies on validated native Puller history.

### Why Local Buffer?

| Concern | Shared Puller Buffer | Local Indexer Buffer |
|---------|---------------------|---------------------|
| Rebuild read pattern | 10 indexes = 10 scans | Write once, read many |
| Retention control | Puller's policy (1h default) | Indexer's policy (rebuild duration) |
| Isolation | Puller failure affects Indexer | Independent lifecycle |
| Storage path | `data/puller/events/` | `data/indexer/events/` |

### Buffer Operations

```go
// Write: called for every event from Puller
buffer.Write(evt *StoreChangeEvent, checkpoint bson.Raw)

// Read: used during rebuild catch-up
iter := buffer.ScanFrom(startKey)  // iterate from recorded position
for iter.Next() {
    evt := iter.Event()
    index.Upsert(evt)
}

// Cleanup: retention-based or on-demand after rebuild
buffer.DeleteBefore(cutoffKey)
```

### Key Format

Same as Puller buffer: `{ClusterTime.T:10d}-{ClusterTime.I:10d}-{EventID}`

This ensures:
- Lexicographic order = temporal order
- Efficient range scans for rebuild catch-up
- Deduplication by EventID

## OrderKey Encoding

OrderKey is a byte sequence that enables lexicographic sorting for indexed fields. For detailed encoding specification, see [Index Implementation Details](02.index.md#orderkey-encoding).

**Summary**:
- Version byte prefix for future compatibility
- Fields encoded in order with direction support (asc/desc)
- Document ID appended as tie-breaker
- Cursor/startAfter uses same encoding (base64-url on wire)

## Configuration

```yaml
indexer:
  templatePath: "config/index/templates.yaml"
  puller:
    address: "localhost:9091"        # Puller gRPC address (empty = in-process)
    reconnectBackoff:
      initial: "1s"
      max: "30s"
      multiplier: 2
  progress:
    path: "data/indexer/progress"    # Progress marker storage
  rebuild:
    batchSize: 500
    qpsLimit: 5000
    maxConcurrent: 2
  lag:
    softWarnSeconds: 30
    hardRebuildSeconds: 120
  buffer:
    path: "data/indexer/events"
    maxSize: "5GiB"              # Max disk usage for event buffer
    batchSize: 100               # Events per PebbleDB batch write
    batchInterval: "100ms"       # Max delay before flush
  cleaner:
    interval: "1m"               # Cleanup check interval
    retention: "4h"              # Keep events for rebuild catch-up
```

For gRPC service configuration, see [Indexer gRPC Service](03.grpc.md).

## Observability

- **Planned metrics**: hit/miss counters, search latency, rebuild duration, lag versions
- **Health**: per-index status (healthy/rebuilding/lagging/failed)
- **Logs**: template load, rebuild start/complete, gap detection

## Risks & Mitigations

| Risk | Mitigation |
|------|------------|
| Index lag | Source-validate candidates; surface unavailable indexes and require explicit recovery when history is invalid |
| Event ordering | Idempotent apply; version-based dedup |
| Memory pressure | Configurable index limits; pluggable backend |
| Rebuild during traffic | Online reconciliation/handoff remains proposed; current bootstrap requires write quiescence |
| Buffer disk usage | Configurable maxSize (5GiB default); retention-based cleanup |
