# Index Storage Design

Status: Implemented query storage and offline bootstrap; automatic online recovery
remains proposed.

Memory and Pebble provide the same projection and candidate-read contracts.
Persistent mode retains complete generations across restart. Memory mode loses
derived state on process exit and requires a new bootstrap.

## Storage Identity and Format

```text
IndexRef = database + concrete collection + template fingerprint + generation
posting  = IndexRef + encoded field tuple + logical document ID
reverse  = IndexRef + logical document ID -> complete posting-key set
catalog  = database -> generation + template fingerprints + bootstrap progress
```

Patterns discover concrete collections; they are not storage partitions. The
format marker is `syntrix-index-v2`. Nonempty unversioned stores and incompatible
markers fail opening; they are never served as empty valid indexes. Encoded scalar
keys and typed source envelopes use version 2. Rebuild derived data during the
[breaking upgrade](#breaking-upgrade).

## Store Interface

| Operation | Contract |
|---|---|
| `ApplyDocumentProjection` | Own complete posting replacements for one document across matching templates and the existing progress marker |
| `ReadView` | Pin one concrete partition across every branch of a candidate stream |
| `ReadGeneration` | Resolve the published catalog/generation and failure state |
| `PublishGeneration` | Publish one completed partition with its bootstrap progress |
| `PublishBootstrapCatalogs` | Atomically publish the complete database inventory and common progress |
| `SetFailure` | Make the affected partition unavailable |
| `Flush` / `LoadProgress` | Observe durable projection/progress publication or its failure |
| `Close` | End owned work and release resources; propagate failures |

The public Query path uses candidate views. The older single-key operations remain
internal APIs; they do not define the multikey query contract.

## Document Projection Publication

All matching-template projections are built before admission. Each replacement
contains the full posting set; an empty set removes every previous posting.
Logical tombstones clear business values and can retain only projections permitted
by the template's current deletion/field shape.

| Backend | Atomic visibility and durability |
|---|---|
| Memory | Remove old sets, install all replacements, and publish progress under one store synchronization boundary |
| Pebble admission | Copy/own immutable replacements; pending supersedes the whole older replacement |
| Pebble commit | Delete old persisted sets, insert new sets, replace reverse records, and persist applied progress in one synchronous batch |
| Failure | Preserve failure and uncommitted work; do not publish progress past unsuccessful replacements |

```text
complete replacements + progress
              |
              v
       immutable pending state
              |
       pending -> flushing
              |
              v
  one batch: postings + reverse sets + progress
              |
              v
      synchronous commit -> release flushing state
```

Expansion limits are checked before mutation. Index processing errors occur after
the source write; affected partitions become unavailable and the consumer stops
before advancing beyond the failing event. Correct the source/limits and perform
the explicit recovery procedure. Native Puller checkpoint semantics are unchanged.

## Database Retirement

Database index invalidation is serialized with event projection. It removes that
database's postings, generations, and catalog while publishing a retirement
marker under the same visibility boundary; Pebble commits the deletion and marker
atomically. Queued events for the retired database then perform no projection and
advance existing applied progress, so they cannot repopulate removed indexes or
stop other databases' consumption.

Retirement takes precedence over generation lookup and survives persistent restart.
Startup accepts a missing catalog only for a database with an explicit retirement
disposition. Ordinary generation or single-catalog publication cannot clear it;
complete bootstrap catalog publication clears markers only for databases included
in the new complete inventory. This is derived-index lifecycle state, not a change
to source document deletion or native Puller checkpoint identity.

## Search Consistency

One candidate stream owns one view across all branches. Memory pins stable ordered
trees without retaining a write-blocking mutex during source reads. Pebble acquires
its persistent snapshot and immutable pending/flushing references under state
synchronization, preventing a flush transition from disappearing from both views.

Precedence is `pending > flushing > persisted`. Replacements suppress all older
postings for their document, even if every replacement lies outside the requested
range. Suppression does not mark the replacement as emitted. Every branch uses the
same complete overlay and closes its iterator before the view closes.

| Per-view default budget | Bound |
|---|---|
| Overlay replacements | 10,000 |
| Encoded overlay bytes | 16 MiB |
| Examined entries | 100,000 |

Overlay bounds are checked before flattening/sorting keys. A budget failure rejects
the read; it cannot bypass pending state. Examined work includes suppressed disk
rows and overlay postings. Persistent iterators and memory scans intersect cursor
position with the filter lower bound and respect the exclusive upper bound.

## Configuration

```yaml
indexer:
  databases: [application]
  template_path: index_templates
  startup_timeout: 30s
  bootstrap_batch_size: 256
  bootstrap_page_bytes: 8388608
  storage_mode: pebble
  store:
    path: data/indexer/indexes.db
    batch_size: 100
    batch_interval: 100ms
    queue_size: 10000
    block_cache_size: 134217728
```

| Mode | Startup and lifetime |
|---|---|
| `memory` (default) | Bootstrap and keep the same process alive; process loss requires rebuilding |
| `pebble` | Resume a complete catalog after source-boundary validation; invalid or incomplete state requires explicit rebuilding |

`startup_timeout` bounds startup validation. Bootstrap has its separate operation
timeout. Neither timeout becomes the lifetime of successfully started capture or
subscription workers.

## Offline Bootstrap and Startup

Bootstrap requires all writers to remain quiesced: application clients, direct
source clients, workers, metadata changes, and physical cleanup/TTL. The CLI
attestation does not itself fence external writers. Other processes using the
configured derived-store paths must be stopped.

```bash
syntrix --standalone --bootstrap-indexes --writes-quiesced --reset-derived \
  --bootstrap-timeout=30m
```

The same maintenance-start flags support distributed mode with local Puller and
Indexer ownership. A distributed listener may start during maintenance; keep
external clients fenced until readiness. The process remains running after
successful bootstrap, which also makes memory mode usable.

| Stage | Required boundary |
|---|---|
| Prepare | `--reset-derived` archives only the validated configured Indexer and Puller buffer directories before opening them; source storage is preserved |
| Inventory | Union default/configured database IDs, Indexer database IDs, template databases, and every metadata database ID; metadata storage is required |
| Capture validation | Every authoritative write source and its ordinary/system physical namespaces must be covered by configured Puller capture |
| Establish boundary | Start native capture, persist its source-established checkpoint, and verify empty, unpruned buffers with their lineages |
| Scan | Enumerate authoritative concrete collections including system scopes and tombstone-only collections; scan bounded ID-ordered source pages through the shared projection |
| Finish | Flush projections, validate retained boundary, and verify database inventory has not changed |
| Publish | Commit every database catalog and one common generation/progress atomically; a partial inventory is never ready |
| Apply readiness | Subscribe with verified replay; process the ordered ready barrier only after preceding events are applied and flushed |
| Serve | Start normal internal services only after applied readiness; then external writers can be resumed |

A complete catalog covers empty collections and collections subsequently created
under its templates. It also certifies databases with no matching templates, so
startup can detect incomplete coverage. A local expected boundary prevents a
remote configured Puller from certifying another buffer lineage.

On normal persistent startup, validate catalog completeness, current template
fingerprints, saved progress, exact backend set, buffer lineage, and retained
history. The Indexer is unavailable until its ordered replay barrier has been
applied and flushed. Failed capture, invalid history, or subscription failure is
visible; startup does not silently reset to the current head.

Temporary transport failure clears readiness and cancels the failed attempt.
Indexer flushes and reloads applied progress, validates the boundary, and retries
with a one-second delay for at most ten consecutive attempts. Readiness returns
only after the new ordered barrier is applied and flushed. Lineage mismatch,
pruned/unknown positions, and codec failures require maintenance rather than a
current-head reset. Owner cancellation stops retry work.

The CLI accepts `--bootstrap-timeout` (default 30 minutes), `--writes-quiesced`, and
optional `--reset-derived` only with bootstrap mode. Unsafe reset paths, overlapping
paths, and symlink traversal fail validation. Actual archive paths are logged.
Failed bootstrap requires another explicit derived reset and complete rebuild.

## Breaking Upgrade

1. Quiesce all source and metadata writers, including physical cleanup, and stop
   processes using the derived stores.
2. Deploy matching Query, Indexer, Puller, and SDK versions. Query pages, typed
   values, candidate streams, event envelopes, and indexes use the new contract.
3. Run maintenance bootstrap with explicit reset of configured derived stores.
   Preserve source documents; no in-place legacy index/buffer conversion occurs.
4. Resume writers after the same runtime has applied its replay-readiness barrier.
   Discard old public query cursors.

The Puller still owns its original backend-native resume token, EventID, and
BufferKey. Bootstrap progress adds lineage/retention validation metadata rather
than redefining those identities. See the
[Puller boundary contract](../puller/01.architecture.md).

## Performance Considerations

### Expected Latency

| Operation | MemoryStore | PersistStore | Notes |
|-----------|-------------|--------------|-------|
| Upsert | ~1μs | ~10-50μs | Async batch amortizes |
| Search (cache hit) | ~10μs | ~50-100μs | Block cache helps |
| Search (cache miss) | N/A | ~1-5ms | SSD read |
| Get by ID | ~100ns | ~10-50μs | Usually cached |

### Memory Usage

| Component | MemoryStore | PersistStore |
|-----------|-------------|--------------|
| Index data | Proportional to data | Block cache (default 128 MiB) |
| Pending ops | N/A | ~1KB × QueueSize |
| Iterator buffers | Minimal | ~10KB per active search |

## Observability

Projection failure logs retain event/backend correlation, hashed scope/document
identity, template fingerprint, generation, a sanitized failure category, and
the name/value of an exhausted projection budget. They exclude source values and
raw error text. Bootstrap logs carry operation ID, generation, hashed inventory
scope, phase/state, database/collection counts, scanned/projected document counts,
and posting counts. These records distinguish validation, scanning, publication,
readiness, and failure without treating observed counts as a readiness shortcut.

The metric names and StoreHealth sketch below remain instrumentation design,
not a claim that these exporters are installed. Runtime readiness follows the
applied replay barrier described above; instance statistics have their own
[delivered contract](03.grpc.md#statistics).

### Planned Metrics (PersistStore)

```
indexer_store_writes_total{status="success|error"}
indexer_store_reads_total{status="success|error"}
indexer_store_batch_size_histogram
indexer_store_batch_latency_seconds
indexer_store_pending_ops_gauge
indexer_store_disk_bytes_gauge
```

### Health Check

```go
// MemoryStore
func (s *MemoryStore) Health() StoreHealth {
    return StoreHealth{Status: "ok"}
}

// PersistStore
func (s *PersistStore) Health() StoreHealth {
    return StoreHealth{
        Status:      "ok",
        DiskUsage:   s.db.Metrics().DiskSpaceUsage(),
        PendingOps:  len(s.pending),
        LastFlush:   s.lastFlushTime,
    }
}
```

## Remaining Recovery Work

Online rebuilding during concurrent writes, automatic history-gap reconstruction,
live template reconciliation, and resumable rebuild jobs remain in the
[recovery proposal](../../../../.agents/notes/proposed/architecture/2026-09-07-indexer-recovery-lifecycle.md).
Offline bootstrap does not claim those guarantees. Its quiescence cost and manual
reset requirement are explicit.

The [completed query decision](../../../../.agents/notes/implemented/bug-fix/2026-09-07-indexed-query-filter-semantics.md)
owns the numeric, multikey, materialization, and upgrade trade-offs. The earlier
[pending-search decision](../../../../.agents/notes/implemented/bug-fix/2026-09-09-indexer-pending-search-results.md)
records why suppressing obsolete entries is distinct from emitting replacements.
