# Index Implementation Details

Status: Implemented query semantics; broader online recovery remains proposed.
Scope: Index templates, ordered candidate execution, and document projections.

See [Indexer Architecture](01.architecture.md) for service responsibilities and
[Index Storage](04.storage.md) for publication and bootstrap.

## Responsibilities

- Project source documents and native Puller events through the same typed rules.
- Replace all postings for each document atomically with applied progress.
- Supply a complete, ordered candidate stream with access/residual assignments.
- Preserve exact scalar values, concrete collection identity, and logical IDs.
- Expose index availability and [instance statistics](03.grpc.md#statistics).

## Index Templates

Templates are loaded from the configured `indexer.template_path` directory
(default `index_templates`). Each YAML file names a logical database. Files for
the same database are merged; duplicate definitions fail validation.

```yaml
database: application
templates:
  - name: posts_by_tag_time
    collectionPattern: users/{uid}/posts
    fields:
      - { field: tags, mode: membership }
      - { field: createdAt, order: desc }
    includeDeleted: false
```

| Property | Contract |
|---|---|
| `collectionPattern` | Discover concrete collection paths; each `{variable}` matches one segment |
| `fields[].field` | Top-level business name or reserved metadata; dotted paths are rejected |
| `fields[].mode` | `scalar` by default, or `membership` |
| Scalar direction | `asc` or `desc` |
| Membership direction | Ascending equality encoding; not a document ordering dimension |
| Membership count | At most one membership field per template |
| `includeDeleted` | Include logical tombstones according to their current cleared-data shape |
| Fingerprint | Binds normalized pattern, all field modes/directions, deletion policy, and scalar codec version |

Arrays/objects in a scalar index field fail projection. A membership field emits
one posting per distinct immediate scalar/null member. Missing, scalar, null, or
empty-array fields emit no membership postings; nested arrays and objects are
not flattened. Unsupported numeric source values fail rather than being dropped.
A membership template cannot serve a query unless a `contains` probe fixes that
dimension and proves candidate completeness.

## OrderKey Encoding

```text
IndexRef = database + concrete collection + template fingerprint + generation
posting  = version + encoded fields + encoded logical document ID
reverse  = IndexRef + logical document ID -> complete posting set
```

Collection patterns select templates; they never replace concrete collection
identity. Equal sort values in distinct documents have different postings because
the logical ID is a prefix-free final string component. Storage hashes and
business `data.id` values are not logical IDs.

| Encoding rule | Reason |
|---|---|
| Version 2 scalar codec | Reject incompatible derived data and cursors explicitly |
| `missing < null < false < true < numbers < strings` | One total order with missing distinct from null |
| Exact int64 + finite binary64 magnitude | Preserve integers beyond binary64's exact-integer range |
| Canonical signed zero | Equality, membership deduplication, bounds, and cursor hashing agree |
| UTF-8 byte string order | Deterministic comparison without locale or normalization differences |
| Escape zero bytes and terminate each component | Prefix-free concatenation, including the document ID |
| Invert the whole component for descending fields | Reverse scalar ordering without changing field boundaries |

The [typed value contract](../../../reference/filters.md#typed-values) defines the
accepted numeric domain. A public cursor is a versioned query envelope containing
an opaque position, not a raw OrderKey. The envelope also binds query scope,
effective order, template, generation, and branch manifest.

## Projection and Read Views

Build every matching-template replacement before admitting an event. The storage
operation owns complete immutable posting sets, including empty replacements.
Removing an array member, changing its type, or clearing tombstone data removes
all obsolete postings. The same projection handles offline scan, replay, and live
events. Physical source cleanup does not add a second logical deletion.

| Bound per document/template | Limit |
|---|---|
| Array elements inspected | 10,000 |
| Distinct postings | 1,024 |
| Total encoded posting bytes | 1 MiB |
| Candidate position | 4,096 bytes |

Expansion failure preserves the previous complete projection, marks affected
serving state unavailable, and prevents progress from passing the failed event.
It is an asynchronous indexing error after the source write, not a rejection of
that write. See [storage publication](04.storage.md#document-projection-publication).

Memory read views pin stable ordered trees. Pebble views capture one persistent
snapshot with immutable pending/flushing replacements; all query branches share
that view. Pending replaces flushing, which replaces persisted postings. A
replacement suppresses every old posting even when its new postings lie outside
a particular scan range. Views and iterators close with their owning stream.

### Matching & Conflict Handling (Collection Pattern)
- Matching: split `collection` and `collectionPattern` into segments; `{var}` matches exactly one segment. Reject patterns with empty/invalid segments.
- Priority (higher wins): 1) more fixed segments; 2) longer total segments. If still tied → conflict.
- Conflicts: if two templates match a path with equal priority, treat as conflict and fail apply for that doc (or drop the lower-ranked when explicit weight is provided; default: fail-fast). Templates with the same structural pattern (e.g., `user/{uid}/chats` vs `user/{user_id}/chats`) are considered duplicates and should be rejected at definition time. Emit metrics/logs for conflicts.
- Multiple matches allowed when priorities differ (e.g., more concrete beats generic); each non-conflicting match results in its own index entry.

### Query-to-Index Matching Rules

Every predicate is assigned to access, residual evaluation, or both. Query
materialization re-evaluates the full conjunction, including access predicates.
An eligible index must expose all potentially matching documents in one common
order; merely matching some filter names is insufficient.

| Predicate | Access strategy |
|---|---|
| `==` | Inclusive scalar point |
| `>`, `>=`, `<`, `<=` | Typed interval with exact inclusive/exclusive boundaries |
| `in` | Distinct point probes, intersected with same-field conditions |
| `!=` | Disjoint present-scalar intervals excluding the equality point |
| `contains` | Fixed probe on an explicit membership dimension |
| Conditions outside usable access fields | Complete residual evaluation when the ordered candidate plan remains complete |

A plan requires an access predicate or compatible explicit ordering. There is no
unrestricted Store-scan fallback. Membership dimensions must be fixed. After
removing fixed fields, the remaining physical dimensions must match the effective
order; hidden unfixed fields cannot change document-ID tie ordering. An eligible
definition is selected deterministically using pattern priority, access coverage,
and template name. Continuation pins that definition and its generation.

#### Same-Field Constraints

- Equality values must agree and satisfy every range condition.
- Keep the strongest lower/upper endpoints; strict wins equal-value ties.
- Empty intersections produce no candidates after query/plan/cursor validation.
- Normalize and deduplicate point probes before branch expansion.
- Cap branch count at 128 and encoded branch metadata at 1 MiB; reject excess.

A fixed point on one field permits ordering by subsequent scalar fields. A range
on a preceding field does not fix it and cannot supply a different global suffix
order. For example, `[role, createdAt desc]` can merge fixed `role in [...]`
branches by time; a variable `role != ...` interval cannot produce that time order.
An eligible time-ordered template can instead evaluate role as a residual.

#### Effective Order and Bounds

Explicit order appends logical ID ascending unless already specified. Without
explicit order, use the selected template's scalar fields and ID; membership
fields are excluded. All branches must project monotonically to this same key
`K` and seek strictly after an arbitrary valid `K`.

Both stores intersect cursor positioning with filter bounds. Bounds use an
inclusive lower and exclusive upper key. A prefix successor increments the
rightmost non-FF byte and truncates the suffix; no arbitrary maximum suffix is
appended. Descending conversion preserves strictness. Bounds cannot cross
concrete collections, templates, generations, or typed field families.

### Candidate Execution

```text
one index read view -> bounded branch iterators -> ordered merge by K
                                                     |
                                                     v
                                      complete equal-K candidate group
                                                     |
                                                     v
                                      authoritative source materialization
                                                     |
                              predicate + posting + current-position checks
                                                     |
                                      emit once / skip and continue
```

A candidate group retains its logical ID, common position, and contributing
branch IDs. The branch manifest reconstructs physical posting proofs. Groups are
complete before page boundaries, so branch duplicates cannot leak across pages.
Query advances only through consumed groups, not prefetched branch heads.

Query checks source scope, visibility, the full predicate conjunction, current
ordering, and that at least one candidate posting still belongs to the document's
current projection. A stale position is skipped rather than reinserted elsewhere
in an already ordered page. Missing and rejected candidates trigger refill until
the document limit or exhaustion. Failures discard the page.

One index view does not create a historical source snapshot. Index lag can omit
recent writes; concurrent changes can cause cross-page omissions or repeats.
Every returned document must pass the source checks at materialization time.

### Pseudocode (conflict-aware matching)
```pseudo
function score(template):
  fixed = count_non_var_segments(template)
  total = segment_count(template)
  return (fixed, total)  // lexicographic

// Note: This function validates templates at load time, not at query time.
// Duplicate detection uses (normalizedPattern, templateIdentity) to allow
// multiple templates for the same pattern with different field lists.
function validateTemplates(templates):
  seen = {}
  for t in templates:
    norm = normalize_vars(t.collectionPattern) // replace {anything} with *
    key = (norm, t.templateIdentity)           // templateIdentity = name or fields signature
    if seen[key]: raise DuplicateTemplateError(t, key)
    seen[key] = true

function matchTemplates(path, templates):
  candidates = []
  for t in templates:
    if !segments_same_length(path, t): continue
    if !all_segments_match(path, t): continue  // fixed must equal; var matches any single segment
    candidates.append((t, score(t)))

  // group by best score
  if candidates is empty: return []
  best_score = max(candidates.score)
  winners = [t for (t,s) in candidates if s == best_score]

  // conflict detection: multiple templates with same priority AND same fields = conflict
  // (different field lists are allowed - Query-to-Index matching will select the best one)
  if len(winners) > 1:
    // Group by templateIdentity; if multiple have same identity, it's a conflict
    identities = unique([w.templateIdentity for w in winners])
    if len(identities) < len(winners):
      raise ConflictError(winners)

  // Return all matching templates; Query-to-Index matching will select the best one
  return winners

function all_segments_match(path, template):
  for i in range(len(path)):
    pseg = path[i]; tseg = template[i]
    if is_var(tseg): continue
    if pseg != tseg: return false
  return true
```

## Operations and Remaining Recovery Work

Production starts from a complete bootstrap catalog and validated retained
Puller boundary. The supported initialization is
[offline bootstrap](04.storage.md#offline-bootstrap-and-startup) with all source
writers quiesced. Persisted complete generations can resume after boundary
validation; memory mode requires rebuilding after process loss.

Automatic online scan/replay handoff, reconciliation of changed templates, and
history-gap recovery remain owned by the
[recovery proposal](../../../../.agents/notes/proposed/architecture/2026-09-07-indexer-recovery-lifecycle.md).
Nested object paths remain explicitly rejected pending their
[field-resolution proposal](../../../../.agents/notes/proposed/feature/2026-09-07-indexed-nested-fields.md).

The [completed query decision](../../../../.agents/notes/implemented/bug-fix/2026-09-07-indexed-query-filter-semantics.md)
records the typed query, membership, pagination, and breaking-upgrade contracts.
Instance [statistics](03.grpc.md#statistics) are observations, not proof of
checkpoint durability, projection success, or readiness.
