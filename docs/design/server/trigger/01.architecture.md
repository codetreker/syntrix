# Trigger Architecture

## Components

The trigger subsystem separates source evaluation from HTTP delivery so each
service can run independently in distributed deployments.

| Component | Responsibility |
|-----------|----------------|
| Puller watcher | Resume after the evaluator checkpoint and transform document changes |
| Evaluator | Match each event against active rules and build delivery tasks |
| Publisher | Submit matching tasks to the selected pubsub backend |
| Consumer | Partition queued tasks among delivery workers and acknowledge outcomes |
| HTTP worker | Send webhook requests with task headers, token, and optional signature |

Standalone mode uses the in-memory pubsub provider. Distributed mode uses NATS
JetStream. The provider controls what publisher success means and whether an
accepted task survives restart; the evaluator does not persist tasks itself.

## Event and Checkpoint Flow

```text
Puller -> watcher -> rule evaluation -> task publication -> eligible progress
                                                           |
                                                           v
                                               asynchronous checkpoint saver

pubsub -> consumer -> HTTP worker -> Ack, Nak, or Term
```

The watcher reads the global `sys/checkpoints/trigger_evaluator` token and
subscribes to Puller. It excludes changes to that exact checkpoint document so
its own saves cannot create another task or checkpoint write. Puller progress
covers all logical databases; each rule filters its own database, event type,
and collection. The evaluator processes
one source event at a time. It retries a reported evaluation or publication
failure on that event with cancellable backoff and offers its progress to the
checkpoint saver only after all rules finish. This ordering
keeps later source progress from passing a known unpublished task. See the
[checkpoint design](evaluator/01.checkpoint.md)
and [failure-gate decision](../../../../.agents/notes/implemented/bug-fix/2026-09-29-trigger-checkpoint-failure-gate.md).

The checkpoint saver may coalesce eligible tokens. If a write fails or the
process stops before persistence, replay can publish a task again. If a
publisher reports success but the selected queue loses the task, the source
checkpoint cannot recover it. Durable rule selection, task records, and
dispatch remain in the [scheduling proposal](../../../../.agents/notes/proposed/bug-fix/2026-09-07-trigger-publish-checkpoint-ordering.md).

## Task Routing

The publisher sends a serialized task to a subject built from the configured
stream prefix, logical database, collection, and encoded document ID. Long
subjects use a hash fallback and mark the task with `subjectHashed`. The task
contains the original document ID, which the consumer uses for worker
partitioning. The consumer dispatches to an HTTP worker; success is acknowledged,
retryable failures are negatively acknowledged with delay, and terminal
failures are terminated according to the delivery policy.

The current task has no stable source-derived delivery ID. Broker redelivery,
ambiguous publication, and source replay can repeat an HTTP request. The
[delivery identity proposal](../../../../.agents/notes/proposed/architecture/2026-09-07-trigger-delivery-idempotency.md)
owns a persistent identity and outbox; receivers currently need to tolerate
duplicate effects.

## Operational Boundaries

- The evaluator checkpoint is global and has no cross-instance ownership.
  Concurrent evaluators can publish duplicates and overwrite progress.
- A missing checkpoint follows `StartFromNow`: when enabled, subscription
  begins at the current admission boundary; when disabled, startup fails.
- A crash between a fresh `StartFromNow` subscription and its first successful
  checkpoint still has no recoverable admission boundary. Puller does not
  expose a durable live boundary for that interval.
- A permanently failing rule holds its source event and all later events until
  correction or cancellation. Retry logs include the event, rule, operation,
  error, and next delay.
- Standalone in-memory pubsub does not retain queued tasks across process
  restart. Distributed queue durability depends on the runtime stream policy.
