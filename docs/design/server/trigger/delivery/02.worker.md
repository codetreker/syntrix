# HTTP Delivery Worker

## Overview

The DeliveryWorker executes HTTP webhook requests for delivery tasks.

## Interface

```go
// DeliveryWorker processes delivery tasks by making HTTP requests.
type DeliveryWorker interface {
    ProcessTask(ctx context.Context, task *types.DeliveryTask) error
}
```

## Request Building

### URL

From `task.URL`:

```go
req, err := http.NewRequestWithContext(ctx, "POST", task.URL, body)
```

### Headers

1. **Content-Type**: Always `application/json`
2. **Custom Headers**: From `task.Headers` map
3. **Signature**: HMAC-SHA256 signature (if secret configured)
4. **Authorization**: Bearer token (if auth configured)

```go
// Base headers
req.Header.Set("Content-Type", "application/json")

// Custom headers
for k, v := range task.Headers {
    req.Header.Set(k, v)
}

// Signature
if secret != "" {
    sig := hmacSHA256(body, secret)
    req.Header.Set("X-Syntrix-Signature", sig)
}

// System token
if token != "" {
    req.Header.Set("Authorization", "Bearer " + token)
}
```

### Body

JSON-encoded payload:

```json
{
    "trigger_id": "notify-on-order",
    "database": "myapp",
    "event": "create",
    "collection": "orders",
    "document_id": "order123",
    "payload": {
        "id": "order123",
        "status": "pending",
        "amount": 100
    }
}
```

## Authentication

### Secret Resolution

Secrets are resolved via `SecretsRef`:

```go
if task.SecretsRef != "" {
    secret, err := w.secretProvider.GetSecret(ctx, task.SecretsRef)
    if err != nil {
        return err  // Fail task, retry later
    }
    // Use secret for signing
}
```

**Important**: Secrets are database-scoped. Cross-database reuse is forbidden.

### HMAC Signature

```go
func hmacSHA256(body []byte, secret string) string {
    h := hmac.New(sha256.New, []byte(secret))
    h.Write(body)
    return hex.EncodeToString(h.Sum(nil))
}
```

The signature is set in the `X-Syntrix-Signature` header.

### System Token

For internal services, a system token can be minted:

```go
if w.auth != nil {
    token, err := w.auth.MintToken(ctx, task.Database)
    if err != nil {
        return err
    }
    req.Header.Set("Authorization", "Bearer " + token)
}
```

## Response Handling

HTTP 2xx returns success. HTTP 400–499 responses other than 429 return a
`FatalError`; other non-2xx responses returned by the HTTP client return errors
containing the response status. HTTP 429 additionally follows the hint rules
below. The failure metric's fatal flag matches the returned fatal classification.
Transport errors and attempt timeouts remain retryable and preserve their error
chains. Redirect handling remains the HTTP client's responsibility.

HTTP 429 is retryable because an endpoint's throttling can recover after a delay.
The [classification decision](../../../../../.agents/notes/implemented/bug-fix/2026-09-07-trigger-retryable-http-statuses.md)
records that contract; the consumer retains ownership of attempts and scheduling.

### Retry-After

Hints are interpreted only on HTTP 429, using one physical `Retry-After` field.
Parsing accepts a supplied current time for deterministic HTTP-date handling.

| Hint | Worker result |
|------|---------------|
| Positive decimal delay-seconds or supported future HTTP-date | Wrap the status error in `RetryAfterError` with a relative delay |
| Missing, empty, malformed, signed, negative, zero, past/equal date, or multiple physical fields | Return the ordinary status error; use rule backoff |
| Valid delay exceeding `time.Duration` range | Return `FatalError`; report a fatal delivery metric |
| Any hint on a non-429 response | Preserve that response's existing classification |

Surrounding space or tab is ignored. Malformed combined values are ignored;
HTTP-date parsing accepts the standard library's supported formats. The duration
range is approximately 292 years. A valid hint exceeding that range returns the
sanitized explanation `Retry-After exceeds the maximum supported delay` with
the HTTP status, without raw header content. This prevents overflow from creating
an earlier retry. Response bodies are not included in hint diagnostics.

## Timeout

The consumer supplies one attempt context after queue waiting, using the captured
rule timeout or the 30-second default. The worker shares that budget across
preparation, secret resolution, token signing, and HTTP work; it does not start a
separate task deadline. Each retry receives a fresh consumer attempt context.

| HTTP client option | Behavior |
|--------------------|----------|
| `HTTPClientOptions.Timeout == 0` | No additional total client cap; the caller's context controls the attempt |
| Explicit positive timeout | An additional total HTTP cap; an earlier context deadline still applies |

Direct worker callers must supply a bounded or cancellable context. The worker
does not derive a deadline from `task.Timeout`. Context-aware secret resolution
and HTTP work observe cancellation. Local RSA token signing cannot be preempted
through the current synchronous identity API: it consumes the same elapsed budget
but may complete after the deadline. HTTP work then observes the expired context.

The [timeout decision](../../../../../.agents/notes/implemented/bug-fix/2026-09-07-trigger-rule-timeouts.md)
records why the rule value controls the attempt and the implicit client cap was
removed. The [public guide](../../../../reference/trigger_rules.md#delivery-timeouts)
defines rule validation, defaults, and broker acknowledgement limits.

## Retry Policy

The worker performs one HTTP attempt. The
[consumer](01.consumer.md#retry-behavior) owns total attempt accounting and
queue-delayed retries using the task's `maxAttempts`, `initialBackoff`, and
`maxBackoff`. A positive hint is combined as
`max(capped rule backoff, Retry-After hint)`; `maxBackoff` caps only rule backoff.
Representable endpoint hints are honored without an additional business ceiling.
The [public guide](../../../../reference/trigger_rules.md#delivery-retries)
defines the observable contract, and the
[Retry-After decision](../../../../../.agents/notes/implemented/feature/2026-09-07-trigger-retry-after.md)
records its limits and costs.

## Error Types

A `FatalError` terminates delivery immediately. Other non-nil errors enter the
consumer's retry policy. `RetryAfterError` carries a positive relative duration
and wraps the status error without changing the task wire format. Wrapped errors
retain their causes, and the consumer can recover a hint through error wrapping.
Raw header content is not retained in the error message.

## Observability

### Metrics

| Metric | Tags | Description |
|--------|------|-------------|
| `trigger.worker.request.count` | database, status_code, success | HTTP requests |
| `trigger.worker.request.latency` | database | Request latency |
| `trigger.worker.retry.count` | database | Retry attempts |

### Logging

| Event | Level | Description |
|-------|-------|-------------|
| Request started | Debug | HTTP request initiated |
| Request success | Debug | 2xx response |
| Request failed (retry) | Warn | 429, other nonterminal HTTP failure, network error, or attempt timeout |
| Request failed (fatal) | Error | 4xx (non-429), or 429 with an unrepresentable valid hint |
| Secret fetch failed | Error | SecretsRef resolution error |
