# Task Consumer

## Overview

The TaskConsumer pulls delivery tasks from NATS JetStream and dispatches them to workers with proper partitioning.

## Interface

```go
// TaskConsumer consumes delivery tasks from NATS.
type TaskConsumer interface {
    // Start begins consuming tasks. Blocks until context is cancelled.
    Start(ctx context.Context) error
    // Stop initiates graceful shutdown.
    Stop() error
}
```

## Subscription

### Subject Pattern

```
<stream_name>.>
```

Example: `TRIGGERS.>` subscribes to all messages in the TRIGGERS stream.

### Consumer Configuration

```go
consumerConfig := jetstream.ConsumerConfig{
    Name:          "TriggerDeliveryWorker",
    Durable:       "TriggerDeliveryWorker",
    FilterSubject: streamName + ".>",
    AckPolicy:     jetstream.AckExplicitPolicy,
    MaxDeliver:    -1,  // Unlimited retries (handled by retry policy)
    AckWait:       30 * time.Second,
}
```

The broker acknowledgement window includes time waiting in local queues and
executing an attempt. It is independent of the task's execution timeout; the
configuration does not guarantee that a long wait or attempt avoids overlapping
redelivery. The proposed [durable task handoff](../../../../../.agents/notes/proposed/architecture/2026-09-07-trigger-acknowledgement-window.md)
would acknowledge after durable task acceptance and recover execution from shared
database state. Current acknowledgement and execution behavior is unchanged.

## Partitioning

Messages are partitioned by document key to ensure ordering:

```go
func (c *consumer) dispatch(msg jetstream.Msg) {
    var task types.DeliveryTask
    json.Unmarshal(msg.Data(), &task)

    // Partition by docKey (from payload, not subject)
    partitionKey := task.DocumentID
    workerIndex := hash(partitionKey) % numWorkers

    c.workerChans[workerIndex] <- msg
}
```

### Why Payload DocKey?

The subject may contain a hashed docKey (when exceeding length limits). Using the payload's `DocumentID` ensures:

1. Correct ordering for the same document
2. Proper deduplication
3. Consistent routing

## Message Handling

### Acknowledgement

Successful delivery calls `Ack`. A fatal error calls `Term` immediately.
Retryable failures call `NakWithDelay(delay)` while attempts remain, or `Term`
when the attempt budget is exhausted. Queue scheduling releases the worker for
other tasks without sleeping during the delay. Scheduling errors are logged;
they do not cause a substitute acknowledgement or termination.

### Attempt Deadline

The consumer creates an attempt context immediately before invoking the worker,
after queue waiting. It uses the task's captured positive timeout, or 30 seconds
for a zero task value. Every retry creates a fresh budget from the same captured
value; earlier parent cancellation or deadlines still apply.

The budget includes preparation, secret resolution, system-token signing, and
HTTP work together. Context-aware operations observe cancellation. Local RSA
signing is synchronous and cannot be preempted through the identity API; its time
consumes the budget, but it can complete after the deadline. The deadline is
therefore not a hard interruption guarantee for synchronous preparation.
The [worker contract](02.worker.md#timeout) defines its caller-context and explicit
HTTP client cap behavior.

### Retry Behavior

| Scenario | Action |
|----------|--------|
| HTTP 2xx | Ack |
| HTTP 4xx (except 429) | Term |
| HTTP 429 with a valid hint beyond the supported duration range | Term with a sanitized error |
| Other HTTP 429 | Retry with `max(capped rule backoff, parsed hint)` while attempts remain |
| Other non-2xx HTTP response returned by the HTTP client | Retry with rule backoff while attempts remain |
| Network error or attempt timeout | Retry with rule backoff while attempts remain |

The consumer owns retry accounting. `maxAttempts` counts total deliveries,
including the initial attempt; a zero task value uses 3. After failed delivery
number `n`, rule backoff is `initialBackoff * 2^(n-1)`. A zero task
`initialBackoff` uses 1 second, and a positive `maxBackoff` caps that component.
The queue's delivered count determines whether another attempt is allowed;
exhaustion is logged and terminates the message before scheduling another retry.

The worker supplies a positive relative hint through `RetryAfterError`, preserved
through error wrapping. Missing or ignored hints contribute zero. The final delay
is the larger of capped rule backoff and hint: the endpoint's minimum pause can
exceed `maxBackoff`. This avoids retrying before a supported endpoint pause ends.
The [worker contract](02.worker.md#retry-after) defines accepted hints and the
terminal representability limit; the
[Retry-After decision](../../../../../.agents/notes/implemented/feature/2026-09-07-trigger-retry-after.md)
records the alternatives and long-delay costs.

Retry diagnostics include rule backoff, hint, selected delay, attempt, limit, and
existing task fields for correlation. Scheduling errors include delay and task
fields. These fields do not establish a new stable delivery identity. Raw headers,
response bodies, and request payloads are excluded from retry diagnostics.
Queue recovery limits remain unchanged; the in-memory queue does not preserve
delayed work across shutdown or restart.

## Worker Pool

### Structure

```go
type consumer struct {
    workerChans []chan jetstream.Msg
    wg          sync.WaitGroup
    numWorkers  int
}
```

### Initialization

```go
func (c *consumer) Start(ctx context.Context) error {
    // Create worker channels
    for i := 0; i < c.numWorkers; i++ {
        c.workerChans[i] = make(chan jetstream.Msg, c.channelBufSize)
        c.wg.Add(1)
        go c.runWorker(ctx, i)
    }

    // Start consuming
    return c.consumeLoop(ctx)
}
```
