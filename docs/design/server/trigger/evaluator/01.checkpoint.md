# Trigger Evaluator Checkpoint

## Source Position

The evaluator stores one Puller progress token for all logical databases at
`sys/checkpoints/trigger_evaluator` in the configured checkpoint database
(`default` by default). Puller progress is an aggregate source position, so a
checkpoint for one event also covers preceding events from other databases.
The watcher subscribes with consumer ID `trigger-evaluator` and passes
transformed events to the evaluator, except changes to its own checkpoint
document. Each rule checks its own database. Filtering this exact document
prevents a saved checkpoint from causing another checkpoint save indefinitely;
other system documents remain eligible for trigger evaluation.

The checkpoint document has a string `token` and an `updatedAt` Unix timestamp.
The watcher updates it, or creates it when no document exists. The token is
opaque to the evaluator.

## Startup

The watcher resumes after a stored string token. When the document is absent,
`StartFromNow=true` subscribes with an empty token and logs an audit message;
`StartFromNow=false` returns an error. The current watcher also treats a
checkpoint document with a non-string token as an empty token. Validation of
that malformed state is separate from the scheduling boundary described here.

## Advancement

The evaluator handles events in source order. For each event, it evaluates
every active rule and publishes every matching task. A reported evaluation or
publication failure retries the same rule with cancellable exponential
backoff from one to 30 seconds. The evaluator does not process a later event
or offer the failed event's token to the checkpoint saver during that retry.
A missing publisher for a matching rule stops the service with an error.

After all rules finish, the evaluator offers the event's nonempty token to an
asynchronous saver. Notifications may coalesce to the latest eligible token.
The saver logs write failures; a subsequent notification or shutdown can try
again. A failed checkpoint write leaves the older stored token in place, so
restart may replay already published tasks.

This ordering prevents a reported evaluation or publish failure from moving
the source checkpoint past an unpublished task. If no checkpoint exists, a
crash before the first successful save still leaves a new watcher with a new
`StartFromNow` admission point. Persisting a live admission boundary requires
a separate Puller contract. The evaluator does not persist rule selection or
tasks before checkpointing. Publisher acceptance, queue retention, and duplicate
handling have separate ownership. See the [implemented failure
gate](../../../../../.agents/notes/implemented/bug-fix/2026-09-29-trigger-checkpoint-failure-gate.md)
and [durable scheduling proposal](../../../../../.agents/notes/proposed/bug-fix/2026-09-07-trigger-publish-checkpoint-ordering.md).

## Multiple Evaluators

Evaluator instances share this checkpoint key but have no leader election or
conditional checkpoint ownership. Concurrent instances can publish duplicate
tasks and overwrite one another's progress. Run one evaluator for this source
until shared scheduling ownership is implemented.
