# Unified Instance Server Detailed Design

Status: source-aligned network contract; unimplemented requirements are identified explicitly.

## Ownership and current implementation

The [network architecture](01.architecture.md) centralizes transport inside one
instance process. The [system architecture](../../../architecture.md) and
[boundary decision](../../../../.agents/notes/proposed/architecture/2026-10-10-platform-console-instance-boundaries.md)
separate employee Management, developer Console, and application runtimes.
`services.Manager` constructs process dependencies; it is unrelated to the global
Management product's fleet scheduling and resource operations.

The current [configuration](../../../../packages/syntrix/internal/server/config.go),
[interface](../../../../packages/syntrix/internal/server/interface.go), and
[implementation](../../../../packages/syntrix/internal/server/service.go) own this
contract. Instance Identity's target project realms and OAuth/OIDC issuer remain
business-service responsibilities. Transport registration does not implement them.

## Configuration

The application embeds `server.Config` and applies its defaults before creation.
The current configuration surface is:

| Setting | Purpose/default |
|---|---|
| `host` | Bind host; development default `localhost` |
| `http_port` | HTTP listener; default 8080 |
| `http_read_timeout`, `http_write_timeout` | Default 10 seconds each |
| `http_idle_timeout` | Default 60 seconds |
| `enable_cors` | Enables configured CORS middleware |
| `allowed_origins`, `allowed_methods`, `allowed_headers` | CORS allow lists |
| `allow_credentials`, `cors_max_age` | Credentials and preflight-cache behavior |
| `rate_limit` | General and authentication request budgets/windows |
| `grpc_port` | gRPC listener; default 9000 |
| `grpc_max_concurrent` | Concurrent-stream setting |
| `enable_reflection` | Development reflection registration |
| `shutdown_timeout` | Shutdown budget; default 10 seconds |

The default CORS methods cover GET, POST, PUT, PATCH, DELETE, and OPTIONS. Headers
include content type, authorization, request ID, and expected database identity.
The preflight cache defaults to 86400 seconds. General rate-limit defaults are
100 requests per minute and authentication defaults are 5 per minute when the
limiter is enabled. `DefaultConfig` and applying defaults to a zero-value struct
have different boolean semantics; callers must use the actual assembly behavior
rather than infer enabled features from numeric defaults.

Header-size and gRPC keepalive controls are requirements, not additional current
configuration keys. `Config.Validate` currently provides no validation logic;
configuration documentation must not imply it enforces production safety.
Production exposure, CORS, reflection, and streaming timeouts require explicit
operational review. No Management/Console runtime flags are introduced here.

## Registration surface

```go
type Service interface {
    Start(ctx context.Context) error
    Stop(ctx context.Context) error
    RegisterHTTPHandler(pattern string, handler http.Handler)
    RegisterGRPCService(desc *grpc.ServiceDesc, impl interface{})
    HTTPMux() *http.ServeMux
    AuthRateLimiter() ratelimit.Limiter
}
```

Handler/RPC registration and direct mux use complete before `Start`. The
constructor `New(cfg, logger)` prepares a mux, gRPC server, optional reflection,
and configured limiters without listening. A process default facade supports
registration by assembled modules; it does not supply a global platform service.

## Startup and concurrency

A mutex protects startup state. Repeated startup returns `server already
started`. HTTP state is initialized while holding the lock, then the two listener
loops run concurrently. HTTP applies configured timeouts and shared middleware;
gRPC uses host/port, concurrent-stream configuration, and the existing receive
size limit required by query wire messages.

Listener failures are returned with protocol context and preserved error chains.
`Start` waits for the first failure or context cancellation. Cancellation ends
that wait normally; the owner remains responsible for `Stop` and dependency
shutdown. Returning from `Start` alone is not evidence that sockets have drained.

## Shutdown

`Stop` drains HTTP and gRPC concurrently. HTTP uses `http.Server.Shutdown(ctx)`;
gRPC attempts `GracefulStop` and calls `Stop` when the context ends. The method
waits for protocol shutdown, releases both general/auth limiter cleanup
resources, and joins HTTP shutdown errors.

A deadline bounds active work without hiding failures. The process manager owns
shutdown ordering among gateway/Identity, RPC handlers, subscriptions, storage,
and other runtime dependencies. Shutdown must not be delegated to employee
Management merely because an instance is platform-hosted.

## Middleware and interceptors

HTTP wrapping applies recovery, request ID, logging, and security headers, then
configured CORS/rate limiting. Handler wrappers remain able to support flushing
and hijacking required by streaming protocols.

- Recovery logs the panic/stack and emits the existing structured HTTP 500 error.
- Request IDs reuse `X-Request-ID` or generate a UUID and propagate it in context
  and response headers.
- Completion logs contain method, path, status, duration in milliseconds, request
  ID, and remote IP. Error/cancellation severity follows the implementation.
- CORS handles preflight and configured origin/method/header/credential policy.
- General request limiting and stricter auth limiting have separate owners and
  lifecycle resources.

Unary and stream interceptor chains provide panic recovery and call logging.
Recovery returns `codes.Internal`; logs include RPC service/method, code,
duration, and error as applicable. OpenTelemetry tracing is a monitoring target,
not a delivered interceptor guarantee.

Authentication, database identity binding, and document permissions belong to
module handlers. In the target, validated instance/project/realm authority must
precede application access; employee/developer tokens cannot acquire application
scope through a shared listener.

## Assembly and testing

Assembly constructs the server, registers gateway handlers and runtime RPC
implementations, then starts the process under an owned context. Tests can inject
`Service` implementations without opening real sockets; listener tests use
isolated addresses and bounded contexts.

Verify pre-start registration, duplicate startup, bind failures, configured
middleware, request-ID propagation, panic recovery, unary/stream interception,
HTTP flushing/hijacking, graceful drain, forced gRPC deadline handling, and
limiter cleanup. Existing server tests document current behavior. Target
project-realm token isolation and separate Management/Console service tests must
be added with those future implementations; this documentation change does not
claim their delivery.
