# Unified Instance Server Requirements

Status: implemented network layer with additional requirements identified below.

## Scope and rationale

The unified server in `packages/syntrix/internal/server` owns HTTP/gRPC listeners,
shared middleware, and shutdown for a Go instance process. Consolidating these
responsibilities avoids inconsistent timeouts, duplicated shutdown, fragmented
observability, and unnecessary listener ports.

The [system architecture](../../../architecture.md) and
[boundary decision](../../../../.agents/notes/proposed/architecture/2026-10-10-platform-console-instance-boundaries.md)
separate this instance network layer from employee Management and the developer
Console. `services.Manager` assembles local dependencies and lifecycle; it is not
the global Management platform. Instance Identity is a peer runtime service, and
its target project realms and OAuth/OIDC responsibilities remain separate from
network-server mechanics.

## HTTP contract

HTTP configuration covers host/port, read/write/idle timeouts, CORS, and rate
limits. Shared middleware provides panic recovery, structured `slog` logging,
request-ID generation/propagation, security headers, configurable CORS, and general
rate limiting. Authentication endpoints can use a stricter limiter. Registration
must finish before listener startup.

Graceful shutdown receives a context and drains active requests within its
budget. Health handlers register through the same network layer. Header-size
configuration is a requirement to evaluate; it is not an existing `server.Config`
field. Streaming routes must retain their protocol semantics under middleware
and timeout configuration.

## gRPC contract

Configuration covers host/port, concurrent streams, and development reflection.
Recovery and logging interceptors apply to unary and streaming calls. Services
register before startup. Shutdown attempts graceful drain and forces gRPC stop
when the context expires.

Keepalive configuration and OpenTelemetry interceptors remain observability and
connection-management requirements; their presence must be verified before they
are documented as available settings.

## Lifecycle and engineering requirements

- Construction prepares registration without opening listeners.
- Startup is single-use, propagates listener failures, and waits for cancellation
  or a fatal listener error.
- Cancellation and `Stop` are distinct: the process lifecycle owner must invoke
  shutdown and report errors.
- Each listener/process is identifiable for logs and diagnosis. In the target,
  instance identity accompanies runtime telemetry; project/database identity is
  added only when the operation owns that scope.
- Configuration has explicit development defaults; production security and
  streaming behavior require deployment-specific review.
- Modules may register handlers/interceptors without introducing business logic
  dependencies into the network package.
- Tests cover construction, registration, startup failure, context-bound drain,
  middleware, and existing protocol interfaces.

Dynamic port reloading and advanced traffic shaping remain outside this network
module's current contract. Gateway-specific authorization stays at the gateway,
including the future project identity realm and database ownership checks.
