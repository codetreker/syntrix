# API URL Structure and Authority Boundaries

Status: current database-addressed routes with accepted target identity boundaries.

## Why explicit database paths

Document, query, replication, and internal trigger routes select a logical
Syntrix database in the URL. This exposes request context for debugging and
allows a validated principal to address several databases without a single
implicit database token binding. Selecting a database never grants permission.

The [system architecture](../../../architecture.md) and
[boundary decision](../../../../.agents/notes/proposed/architecture/2026-10-10-platform-console-instance-boundaries.md)
separate employee Management, developer Console, and application instances. A
project belongs to an instance, has its own identity realm, and can own multiple
logical databases. These boundaries are accepted requirements; the current
routes below do not implement project realms or the complete OAuth/OIDC flow.

## Current routes

The [gateway router](../../../../packages/syntrix/internal/gateway/rest/handler.go)
registers these database-addressed operations:

| Surface | Methods and path |
|---|---|
| Documents | GET, POST, PUT, PATCH, DELETE `/api/v1/databases/{database}/documents/{path...}` |
| Query | POST `/api/v1/databases/{database}/query` |
| Replica download/upload | POST `/replication/v1/databases/{database}/pull`, `/push` |
| Internal trigger access | POST `/trigger/v1/databases/{database}/get`, `/query`, `/write` |

For example, document reads can address
`/api/v1/databases/prod/documents/rooms/room-1/messages/msg-1`; query requests can
address the same database and a collection such as `rooms/room-1/messages`.
Replication and trigger routes keep their distinct authentication/operation
contracts while making their selected database visible.

Authentication is currently global within the runtime identity model:

```text
POST /auth/v1/signup
POST /auth/v1/login
POST /auth/v1/refresh
POST /auth/v1/logout
```

Current administration routes include GET `/admin/users`, PATCH
`/admin/users/{id}`, GET `/admin/rules`, POST `/admin/rules/push`, GET
`/admin/health`, and CRUD-like database operations under `/admin/databases`.
Authenticated database-management operations also exist under
`/api/v1/databases`. GET `/health` is registered by the gateway; this list does
not imply that a gateway `/ready` route or project/OAuth endpoint exists.

The legacy `/auth/v1` and `/admin` routes remain current contracts. Their
unscoped identity/admin model is a gap against the accepted architecture. An
existing runtime `admin` role must not be interpreted as a Syntrix employee or a
developer Console account.

## Current claims and authorization

The [claims definition](../../../../packages/syntrix/internal/core/identity/types/types.go)
contains username, a `roles` array, disabled status, `db_admin`, user object ID,
and registered JWT fields. It has no project-realm authority. A current token
example is:

```json
{
  "sub": "user-123",
  "username": "alice",
  "roles": ["user"],
  "db_admin": ["prod", "staging"],
  "iat": 1705700000,
  "exp": 1705700900
}
```

Current administration middleware accepts the legacy `admin` or `system` role.
Database-administration grants and CEL authorization rules form other runtime
permission mechanisms; route registration and a database URL are not proof that
all operations enforce identical grants. Existing endpoint-specific middleware
must be assessed against its documented contract.

| Authority | Current meaning or target requirement |
|---|---|
| Legacy runtime `admin` / `system` | Current runtime privileges; not a platform employee/developer identity |
| `db_admin` | Current database grant carried by runtime claims |
| Application user | Target principal issued and validated within an instance project realm |
| Developer | Target Console principal, authorized for owned/delegated instances |
| Employee | Target Management principal, authorized for platform operations |

Target authorization must validate the token issuer/authority, instance,
project realm, selected database, and operation grant together. Instance Identity
issues application tokens and supports external-provider login. Developer and
employee tokens cannot bypass application authorization simply by including a
legacy role string. No future project route shape or token schema is established
by this document.

## Database resolution and security requirements

Resolve a supported database identifier to a live logical database, validate its
state, and apply the operation's permission contract. Names and identifiers must
not introduce path traversal or ambiguous authorization namespaces. Canonical
database identity and incarnation checks must survive database replacement and
repeated names where required by replication/read contracts.

Avoid database enumeration through distinguishable unauthorized responses under
the chosen endpoint contract. Privileged database grants require explicit
ownership and auditability. Audit records attach instance/project/database
correlation when the operation has that scope; instance health, platform
scheduling, and developer account operations need their own scope without a
fabricated database value.

## Delivery and migration obligations

Database-addressed routes and token/database decoupling are already represented
in current code. Future delivery must add project-realm isolation, own issuer and
external login flows, and distinct employee/developer authority without claiming
that the current global user model supplies them.

Update gateway, replica/trigger clients, SDKs, examples, benchmarks, and reference
contracts together when a future route or claims decision is implemented.
Persistent identity/schema changes require explicit migrations; compatibility
behavior is a separate decision. This document introduces no runtime endpoints,
flags, schemas, or compatibility layer.

## Current request examples

```bash
curl -X POST https://api.example.com/api/v1/databases/prod/documents/users \
  -H "Authorization: Bearer <instance-runtime-token>" \
  -H "Content-Type: application/json" \
  -d '{"name": "Alice", "email": "alice@example.com"}'

curl -X POST https://api.example.com/api/v1/databases/staging/query \
  -H "Authorization: Bearer <instance-runtime-token>" \
  -H "Content-Type: application/json" \
  -d '{"collection":"rooms/room-1/messages","filters":[{"field":"timestamp","op":">","value":1700000000000}],"orderBy":[{"field":"timestamp","direction":"desc"}],"limit":50}'
```

Examples address current instance APIs. They do not assert project isolation or
prove the principal's permission for the selected database.
