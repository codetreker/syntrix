# Query Engine and Indexer Integration Design

**Date:** January 11, 2026
**Status:** Design Draft
**Component:** Query Engine + Indexer Integration

## 1. Overview

This document designs the integration between Query Engine and Indexer service.

**Core Principles:**
1. Indexer is a **required dependency** for indexed queries; unsupported predicates do not trigger a storage-scan fallback
2. **Standalone mode only** (`--standalone`): direct in-process calls allowed
3. **Distributed mode** (default, including `--all`): must use gRPC, even if services are in same process

## 2. Design Rationale

### Why Indexer is Required

1. **Performance policy**: Filtered or ordered queries use Indexer, except unordered ID-only lookups; unfiltered, unordered listing uses Store directly
2. **Clear architecture**: Explicit dependencies, no implicit degradation
3. **Operational visibility**: Indexed queries fail explicitly if Indexer is unavailable
4. **Simplified code**: No fallback logic, reduced complexity

### Filter Planning and Page Coordination

All eight query operators have an explicit execution strategy under the
[filter contract](../../../reference/filters.md). Each predicate is assigned to
indexed access, residual source evaluation, or both. An incomplete access/order
plan fails explicitly; no predicate is discarded.

| Query shape | Execution contract |
|---|---|
| No filters and no ordering | Bounded authoritative Store scan, ID ascending |
| All filters are `id ==` or `id in`, without ordering | Authoritative Store lookups, ID ascending |
| Other queries | One complete Indexer candidate plan and authoritative materialization |
| No complete plan | No-matching-index error |

```text
Query -> Indexer candidate stream -> complete ordered groups
  |                                      |
  +-> authoritative Store reads <--------+
  |       full predicates + scope + current position/posting checks
  +-> documents + nextCursor + effectiveOrder
```

The candidate stream owns one index read view across its branches. It returns
metadata, complete equal-position groups, and explicit completion. Query validates
all source predicates, deletion visibility, current sort position, and posting
provenance. Rejected candidates advance traversal; Query refills to the final
document limit or exhaustion. Any error discards the page.

Materialization reads at most 128 candidate documents and 16 MiB of source
document bytes per batch. A batch contains no more potential results than the
page's remaining slots. Only consumed groups advance continuation; rejected
documents trigger another bounded batch. The same limits apply to direct ID
lookups and source listing. The Store byte bound is enforced before decoded
documents accumulate and is distinct from the 16 MiB HTTP typed-page and 20 MiB
Query protobuf-page limits.

Only a source byte-budget failure reduces the batch by halves and retries. Fitted
sub-batches are processed before the retained remainder; a single document that
cannot fit fails with a work-limit error. Source listing likewise reduces its
candidate cap and retains that smaller cap for the request. Other source errors
propagate immediately. No failed attempt or retained candidate advances the public
cursor. Any later page-budget or execution error discards all accumulated response
documents.

Exact int64/binary64 and versioned typed document transport preserve values across
local, gRPC, HTTP, and SDK paths. The page cursor binds query scope, effective
ordering, route, template fingerprint, generation, branch manifest, and the last
consumed group. Raw order keys and old cursors are invalid.

Authoritative reads select the logical database's write source without replica
fallback. This adds source-read load and does not establish a transaction or
snapshot across candidate reads or pages. Index lag can omit new writes; stale
positions are skipped. Per-page deduplication does not promise cross-page
exactly-once traversal during concurrent mutations.

The [index design](../indexer/02.index.md#query-to-index-matching-rules) owns plan
eligibility, scalar/membership strategies, and exact bounds. The
[completed query decision](../../../../.agents/notes/implemented/bug-fix/2026-09-07-indexed-query-filter-semantics.md)
records the trade-offs. Conditional-write, Store Watch, realtime, and replication
checkpoint contracts remain separate.

### Request Observations

At debug level, `Query page completed` records request ID, route, hashed scope/plan/
index-generation identities, branch count, candidate and examined counts, source
read/document counts, returned count, rejection counters, elapsed milliseconds,
and a termination reason. Rejection counters distinguish missing source rows,
wrong scope, deleted rows, predicate failures, stale positions/postings, and
within-page duplicates.

`source_reads` includes byte-budget retry attempts. `source_documents` counts
non-nil documents passed to validation after a successful read, including later
rejections; documents from failed partial attempts are not counted.

`x-request-id` propagates across Query and Indexer gRPC calls. Completion reasons
are stable categories such as exhausted, page limit, invalid query, stale cursor,
work limit, unavailable index, cancellation, deadline, or internal failure. These
structured records exclude filter values, raw cursors/positions, document payloads,
and unsanitized error messages. They are request diagnostics, not aggregate metric
exporters or proof of snapshot consistency.

### Why Distributed Mode Must Use gRPC

1. **Consistency**: Behavior is the same regardless of deployment topology
2. **Testability**: Dev environment behaves the same as production
3. **Simplified code**: No "same process or cross-process" branching logic

## 3. Architecture

### 3.1 Mode Determination

| CLI Flag | Config | Mode | Query → Indexer |
|----------|--------|------|-----------------|
| `--standalone` | - | Standalone | Direct call |
| - | `deployment.mode: standalone` | Standalone | Direct call |
| `--all` | - | Distributed | gRPC |
| `--query` | - | Distributed | gRPC |
| (default) | - | Distributed | gRPC |

### 3.2 Standalone Mode (`--standalone`)

```
┌─────────────────────────────────────────────────────┐
│                   Single Process                     │
│                                                      │
│  API ──► Query ──direct call──► Indexer ──► Puller  │
│            │                       │                 │
│            │                       ▼                 │
│            └───────────────────► Storage             │
└─────────────────────────────────────────────────────┘
```

### 3.3 Distributed Mode (default, including `--all`)

```
┌─────────────────┐      gRPC       ┌─────────────────┐
│  API Gateway    │ ───────────────►│  Query Service  │
└─────────────────┘                 └────────┬────────┘
                                             │ gRPC (required)
                                             ▼
                                    ┌─────────────────┐
                                    │ Indexer Service │
                                    └────────┬────────┘
                                             │ gRPC
                                             ▼
                                    ┌─────────────────┐
                                    │ Puller Service  │
                                    └─────────────────┘
```

**Note**: Even with `--all` (all services in same process), Distributed mode must communicate via gRPC.

## 4. Interface Changes

### 4.1 Query Engine

```go
// Before: Indexer optional
func New(storage storage.DocumentStore) *Engine

// After: Indexer required
func New(storage storage.DocumentStore, indexer indexer.Service) *Engine
```

### 4.2 Query Package

```go
// Before
func NewService(store storage.DocumentStore) Service

// After
func NewService(store storage.DocumentStore, idx indexer.Service) Service
```

### 4.3 Error Types

| Error | Meaning |
|-------|---------|
| `ErrIndexerRequired` | Indexer not configured |
| `ErrNoMatchingIndex` | No matching index for query |
| `ErrIndexRebuilding` | Index is rebuilding |
| `ErrIndexNotReady` | Index not ready |
| `ErrInvalidQuery` | Invalid query value, field, plan, or cursor scope/format |
| `ErrStaleCursor` | Cursor definition or generation changed |
| `ErrQueryWorkLimit` | Candidate, overlay, cursor, or page budget exceeded |

## 5. Configuration

### 5.1 New Config Fields

```yaml
gateway:
  indexer_service_url: ""  # Indexer gRPC address (required for Distributed mode)
```

### 5.2 Startup Commands

```bash
# Standalone - direct in-process calls
syntrix --standalone

# Distributed - all services, but must use gRPC between them
syntrix --all  # requires gateway.indexer_service_url for Query

# Distributed - Query only, requires Indexer gRPC address
syntrix --query  # requires gateway.indexer_service_url
```

## 7. Risks and Mitigations

| Risk | Mitigation |
|------|------------|
| Indexer down causes query unavailability | Multi-replica deployment + health checks |
| Query fails during index rebuild | Return clear error, client retry |
| Query fails with no matching index | Clear error message, guide to create index |
