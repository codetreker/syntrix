# Instance Identity Architecture

**Status:** Confirmed target architecture; current implementation is identified below.

The [system architecture](../../../../architecture.md) owns the distinction
between the employee-facing Management platform, the developer-facing Console
service, and end-user-facing Syntrix runtime instances. The
[boundary decision](../../../../../.agents/notes/proposed/architecture/2026-10-10-platform-console-instance-boundaries.md)
records the rationale and remaining design decisions.

## Ownership and isolation

Identity belongs to each Syntrix instance and serves the end users of applications
built on that instance. It is a peer runtime module to Indexer, Puller, Query,
and other instance services. Module ownership does not require a separate process
for every module; standalone and distributed execution must preserve the same
responsibilities.

| Authority domain | Account owner | Administrative scope |
|---|---|---|
| Syntrix platform employees | Management platform | Platform operations, orchestration, monitoring, and resource management |
| Developers | Console service | Developer accounts and their one or more Syntrix instances |
| Application end users | Instance Identity module, isolated by project | Application identity and permissions inside the selected instance and project |

An instance contains its own projects, users, databases, Syntrix services,
PostgreSQL, and MongoDB. A project is the end-user identity realm and can use
multiple logical Syntrix databases. Two projects can contain accounts with the
same username or external identity without sharing account state or permissions.
Disabling an account in one project does not disable an account in another.

Project application roles, including a role named `admin`, confer no employee
authority on Management and no developer authority to create or manage instances
through Console. Developer control of an instance also does not make the
developer's Console account an application end-user account.

## Runtime responsibilities

Identity owns the end-user directory, credentials, external identity bindings,
authentication policy, sessions, OAuth clients and grants, token issuance,
revocation state, and signing-key lifecycle. Both OAuth/OIDC roles are required:

- **Authorization server / OpenID Provider:** authenticate project end users and
  issue credentials for application clients using Syntrix as their identity
  authority.
- **OAuth client / OIDC Relying Party:** authenticate through an external
  identity provider and bind its identity to a stable local user in the selected
  project.

The Gateway exposes the instance's public HTTP and realtime entrypoints. It
validates the credential's authority and project binding before applying the
target database's document rules. Query, Indexer, and Puller retain their data
processing responsibilities. Application user authentication and document
authorization are related, but an authenticated project user is not automatically
authorized for every database or document in that project.

The exact OAuth routes, grant set, internal RPC surface, issuer/audience format,
and module deployment wiring still require design. A project-selection parameter
or an OAuth endpoint described here is not an implemented API.

## System data and business data

| Data | Target owner and backing store |
|---|---|
| Project directory and database configuration | Instance system data in PostgreSQL |
| End users, passwords, external identity bindings, OAuth state and sessions | Instance Identity system data in PostgreSQL |
| Developer application documents | Logical Syntrix databases backed by MongoDB |

PostgreSQL is an internal dependency that supports the instance. A Syntrix
database is the logical document database exposed to developers; it is not an
application-accessible PostgreSQL database. Its configuration is system metadata,
while its document content is business data.

Identity has authority over its own records; it does not own platform provisioning
or instance creation. Project/database lifecycle administration must coordinate
with the relevant instance modules without merging these account domains.
Deleting one database must not implicitly remove the project's shared users.
The exact lifecycle command protocol and deletion orchestration remain open.

## Authentication and authorization flow

```text
Application client
  -> Instance Gateway / authentication endpoints
  -> Instance Identity
       -> Local project account or external identity provider
       -> Project end-user session and Syntrix-issued credentials
  -> Instance Gateway / realtime
       -> Validate instance and project authority
       -> Resolve the database's project and evaluate document rules
  -> Query / Indexer / Puller / MongoDB business documents

Identity + project/database system configuration -> Instance-local PostgreSQL
```

External identity subjects are provider identities, not a replacement for the
local user identifier. Bindings include the project and provider identity; email
alone is not an account-merging key. Stable local identifiers allow sessions,
permissions, and replica namespaces to retain one identity through provider
changes. The final binding and token representation remain to be designed.

CEL-based document rules remain deny-by-default. Rule ownership follows the
target database and its project. Service credentials used by trigger workers
have their own authority and must not be confused with employee, developer, or
end-user credentials.

## Current implementation

Transport-free Identity contracts live in `packages/syntrix/internal/identity`.
The password/JWT implementation remains in
`packages/syntrix/internal/core/identity/authn`; Manager constructs it with
`authn.NewAuthService(config, userStore, revocationStore)`. Implementation and
repository relocation are separate structural work.

| Contract or adapter | Current responsibility |
|---|---|
| `identity.AccountService` | Signup, signin, refresh, logout, and authorized user list/update operations |
| `identity.TokenVerifier` | `VerifyToken(token)` returns an opaque `VerifiedIdentity` after existing JWT validation |
| `identity.SystemTokenIssuer` | `GenerateSystemToken(serviceName)` for trigger delivery credentials |
| `gateway/authentication` | Required/optional HTTP Bearer authentication and projection into existing context keys |
| `gateway/authorization` | Query-backed CEL document rules and evaluation types |

Account operations and token verification no longer expose HTTP middleware.
REST holds account and verifier capabilities; realtime needs token verification;
Trigger Delivery depends on the system-token issuer. Narrow contracts state each
consumer's authority without giving it unrelated user-management operations.
The current concrete implementation still creates the signing/validation key
service together; this separation does not provide a public-key-only verifier
or independent Identity deployment yet.

`VerifiedIdentity` privately binds a verified claims snapshot to the verifier
that issued it. Administrative list/update operations accept that identity and
require provenance from their own verifier plus an exact `admin` or `system`
role in the private snapshot. A nil/zero identity, an identity from another
verifier, or mutable caller-supplied claims cannot authorize user administration.
`Claims()` returns a detached snapshot for Gateway projections; changing it
cannot elevate the private administrative identity. This is an in-process
provenance contract, not a serialized RPC credential or a project-realm marker.

The public `identity.User` view contains ID, username, creation/update times,
disabled state, roles, database-admin assignments, profile, and login/lockout
statistics. It contains no password hash or algorithm. REST preserves its
existing user JSON by adding fixed empty `password_hash` and `password_algo`
fields to that safe view. Listing retains current pagination and nil/empty
result behavior; PATCH retains replacement of roles, database-admin assignments,
and disabled state. Internal repositories retain credential records.

Implemented authentication includes explicit signup, signin, refresh, logout,
RS256 JWT validation, user listing, and role/database-admin/disabled updates.
Users and logical database metadata are stored in PostgreSQL; token revocations
are stored in MongoDB. Usernames, `roles`, and `db_admin` belong to the current
instance-wide model. There is no project identity realm or complete OAuth/OIDC
authorization or federation flow yet. These current administrative claims do not
define the target Management or Console account systems.

Gateway authentication supplies the existing typed user ID, username, roles,
claims, and database-admin context keys after token verification. Required and
optional Bearer behavior, REST errors, realtime ownership/expiry checks, JWT
claims, and SDK session fences retain their existing contracts. Verification
and administrative provenance do not add user-state/revocation reads,
account-wide invalidation, or an additional time/disabled-state check at user
administration.

Gateway constructs `authorization.NewEngine(config, queryService)` separately.
Its module configuration owns `gateway.authz.rules_path` and its lifecycle;
Identity configuration owns authentication and administrator bootstrap settings.
Root runtime configuration references those module configurations directly.

The [Identity contract decision](../../../../../.agents/notes/implemented/architecture/2026-10-10-identity-contracts-and-gateway-authentication.md)
owns the account, verifier, safe-view, and HTTP adapter separation. The earlier
[document authorization decision](../../../../../.agents/notes/implemented/architecture/2026-10-10-gateway-document-authorization.md)
continues to own CEL/configuration separation. Concrete signing/public-key
verification separation and Identity repository/composition extraction remain
structural work. Project realms, PostgreSQL sessions/revocations, independent
deployment, and both OAuth roles follow with explicit activation contracts.

Existing routes and SDK behavior are documented in the
[API reference](../../../../reference/api.md) and
[SDK authentication design](../../../sdk/003_authentication.md).

## Reliability and remaining design

Authority checks must not reinterpret an unavailable or invalid identity as
another account domain. Separating Identity lets Gateway and data services
depend on public validation and authorization contracts rather than user-store
or private signing-key access.

Key publication and rotation, distributed validation, cache freshness, account
disable/revocation propagation, refresh replay handling, and active realtime
connection invalidation need explicit contracts. No revocation deadline,
cache TTL, emergency fail-open policy, or new storage dependency is selected by
this architecture. System records remain authoritative in the instance's
PostgreSQL even if a later design adds transient caches.

Observability should distinguish authentication failures, authorization denials,
dependency failures, key lookup errors, and session mutations by instance and
project without exposing credentials or business document contents.
