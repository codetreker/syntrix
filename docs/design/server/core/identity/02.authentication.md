# Instance Authentication and OAuth/OIDC

**Status:** Confirmed architectural ownership; implemented behavior and remaining
protocol design are separated below.

The [Identity architecture](01.architecture.md) defines the project end-user
realm inside a Syntrix instance. The [system architecture](../../../../architecture.md)
owns the three separate account domains: Management employees, Console
developers, and instance application end users. This document covers the last
domain. Neither the instance authentication API nor an application `admin` role
authenticates a developer to Console or an employee to Management.

## Target responsibilities

Identity is a peer module to Indexer, Puller, Query, and other runtime modules.
Each instance has its own Identity system data in PostgreSQL. Each project has
an isolated end-user directory and may use several logical Syntrix databases
backed by MongoDB. The user's account belongs to the project rather than to any
one of those databases.

Identity owns signup, signin, user management, local credentials, external
identity bindings, sessions, OAuth clients and state, token issuance and
revocation, and signing-key lifecycle. PostgreSQL is the authoritative store
for these records; MongoDB stores developer business documents. Authentication
does not grant unrestricted document access: Gateway and the data services must
still apply the target database's application authorization rules.

## Two OAuth/OIDC roles

Both roles must connect to the same local project account model:

| Role | Client or counterparty | Identity responsibility |
|---|---|---|
| OAuth authorization server / OpenID Provider | Developer applications using Syntrix authentication | Authenticate local project users and issue the application's Syntrix credentials |
| OAuth client / OIDC Relying Party | External identity providers | Complete external login and bind the provider identity to a local project user |

```text
Application client -> Instance Identity -> External provider, when selected
                                       -> Stable local project user
                                       -> Syntrix session and credentials
Application client -> Instance Gateway -> Application data authorization
```

An external token represents the external provider's authority. Account binding
maps it to the selected project's local identity; it does not grant Management
or Console permissions. Bind by the project and external provider identity,
including issuer and subject for OIDC. Email changes or reused email addresses
must not silently merge accounts. The same external identity can be represented
by independent accounts in different projects.

OAuth client registration, redirect validation, authorization/consent flows,
provider configuration, grant selection, protocol routes, issuer/audience
representation, and administrative credentials remain to be designed. The
existing JSON password login API is not a complete OAuth token endpoint.
OIDC discovery and JWKS publication are target responsibilities, not currently
supported endpoints.

## Identity and credential invariants

- Local user IDs remain stable through password changes and external provider
  binding changes. Project ownership is part of authentication and authorization
  context, not inferred from an email address or role name.
- A credential for one instance or project cannot authorize another realm.
  Target database membership and document permissions must be checked separately.
- Platform employees and developers use their own account systems. Application
  credentials cannot create instances, administer developers, or operate the
  platform.
- Private signing material belongs to Identity. Gateway and other services need
  an appropriate validation contract without acquiring user credentials or
  ownership of Identity's database records.
- Trigger/service identities are distinct from human end users. Their issued
  capabilities and lifetime must match the runtime operation that uses them.

The exact claims, storage tables, public verification contract, service RPCs,
and transport exposure are not finalized here. The existing SDK's local session
fences and replica subject/database bindings must remain explicit when the
project model is introduced; the current SDK does not yet encode that model.

## Implemented password authentication

Current AuthN lives in `packages/syntrix/internal/core/identity/authn` and is
constructed through `identity.NewAuthN(config, userStore, revocationStore)`.
Gateway exposes these implemented endpoints:

| Endpoint | Current behavior |
|---|---|
| `POST /auth/v1/signup` | Explicit username/password account creation; returns an access/refresh pair |
| `POST /auth/v1/login` | Signin for an existing username/password account; returns a pair |
| `POST /auth/v1/refresh` | Validate and rotate a refresh credential; reload the user before issuing a pair |
| `POST /auth/v1/logout` | Revoke the submitted refresh-token identifier |

Login does not register missing accounts. Current request types contain no
project or database selector. Usernames are instance-wide, and user records
contain roles, database-admin assignments, disabled state, password hash and
algorithm, and login statistics. Users and database metadata use PostgreSQL;
revocations use MongoDB. Moving all Identity state to instance-local PostgreSQL
and introducing project isolation are pending implementation.

Passwords use the existing hashing implementation and configured password
policy. `DefaultConfig` uses a 12-character minimum and upper/lowercase, digit,
and special-character requirements; the HTTP signup validator also enforces
its request bounds. Login records failed attempts on the user, locks after
10 failures for 5 minutes, and resets statistics after success. Gateway also
wraps signup, signin, and refresh with its authentication rate limiter. These
facts do not establish a distributed project-scoped throttling contract.

The configured admin username receives the current instance-wide `admin` role
on signup. `GET /admin/users` and `PATCH /admin/users/{id}` use the existing
administrative model. That bootstrap behavior is not the target employee,
developer, or project-administrator model and must be redesigned when the realms
are implemented.

## Implemented JWT and request context

The current token service signs and verifies RS256 JWTs with one configured RSA
key. Access-token defaults are 15 minutes and refresh-token defaults are 7 days;
deployment configuration may change them. Validation rejects another signing
algorithm and checks JWT validity using the local public key.

Current user claims include `sub`, `oid`, `username`, optional `roles` and
`db_admin`, `disabled`, `iat`, `nbf`, `exp`, and `jti`. `sub` and `oid` carry the
same local user ID. The refresh token does not carry the access token's role
list; refresh reloads current user state. These claims have no implemented
project or distinct Console/Management authority marker.

HTTP middleware extracts `Authorization: Bearer <token>` and supplies typed
user ID, username, roles, full claims, and database-admin context keys. It does
not look up user state or token revocation on every ordinary access request.
Therefore the embedded `disabled` claim does not establish immediate account
disable enforcement for previously issued access tokens.

Database selection comes from the API URL and SDK configuration. Current
`db_admin` assignments allow the existing database authorization bypass, while
replication has its separate owner/database-admin admission profile. These
current grants do not define the target permissions of project end users.
The [Gateway authorization design](../../gateway/authorization.md) owns document
rule behavior. Its Query-backed CEL evaluator is separate from Identity account
and token logic; the existing YAML `identity.authz` configuration remains supported.

## Implemented refresh and logout limits

Refresh validates the token, asks the revocation store to atomically check/revoke
its identifier using the configured overlap, loads the current user, rejects
a disabled user, and issues a new pair. Logout immediately records revocation
of the submitted token identifier. The current behavior does not imply a durable
session inventory, account-wide logout, refresh-family reuse detection, or
immediate invalidation of every access token.

The SDK independently fences local session replacement. Login, signup, logout,
and explicit credential replacement cannot revive an obsolete account through
a late refresh or retry. This protects client ownership; it does not accelerate
server token revocation or undo a request already executed by the server. See
the [SDK authentication design](../../../sdk/003_authentication.md).

## Remaining design and security requirements

The target must define key publication/rotation, public verification, project
selection and binding, refresh replay behavior, and retained session state.
Account disable, password change, session revocation, and active realtime
connection invalidation need a stated consistency policy. No immediate-revocation
deadline, cache TTL, overlap policy, additional backing store, or emergency
fail-open switch is selected by this document.

Credentials and signing keys require transport and storage protection. Auth
logs and metrics distinguish failed credentials, denied authorization, and
dependency failures while excluding passwords, hashes, and tokens. Backups
must treat the instance's PostgreSQL system data and MongoDB business data as
different responsibilities; exact retention and recovery procedures need design.

Additional password change, administrative provisioning, and durable audit
capabilities remain proposals:

- [Authenticated password change](../../../../../.agents/notes/proposed/feature/2026-09-07-password-change.md)
- [Administrative account provisioning](../../../../../.agents/notes/proposed/feature/2026-09-07-admin-account-provisioning.md)
- [Administrative audit records](../../../../../.agents/notes/proposed/feature/2026-09-07-administrative-audit-records.md)

These proposals must operate within the instance/project identity realm.
Password reset, MFA, and additional federation protocols are separate design
questions. Supported consumer APIs remain in the
[API reference](../../../../reference/api.md).
