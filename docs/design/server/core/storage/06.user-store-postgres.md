# Instance User Storage in PostgreSQL

**Status:** Current PostgreSQL UserStore and accepted project-scoped Identity target.

## 1. Identity and Storage Ownership

The [platform architecture](../../../../architecture.md) separates three user
domains: Management employees, Console developers, and application end users
served by a Syntrix instance. Developers can own multiple instances. Projects
belong to an instance, each project has its own end-user identity realm, and
one project can use multiple logical Syntrix databases.

Every instance contains Syntrix services, MongoDB, and private PostgreSQL
system storage. Project end users, credentials, OAuth/OIDC configuration,
sessions, projects, and database configuration belong in that PostgreSQL
system database. Logical Syntrix databases are the developer-facing document
product, with business documents in MongoDB. Console/Management identities
and platform inventory have their own service ownership.

Instance Identity manages project end users and both OAuth/OIDC roles: issuing
Syntrix credentials and accepting configured external-provider logins. It is
a runtime peer of Indexer and Puller. It does not acquire developer/employee
account or platform resource ownership by using the system PostgreSQL backend.

The accepted target is recorded in the
[boundary decision](../../../../../.agents/notes/proposed/architecture/2026-10-10-platform-console-instance-boundaries.md).
Current code uses PostgreSQL for users and logical database metadata but has
no project dimension. Current token revocation still uses MongoDB with TTL
cleanup. These current placements do not establish the target OAuth/session
schema or a final revocation policy.

## 2. Current UserStore Decisions

| Current mechanism | Meaning and reason |
|---|---|
| No `User.Database` field | The existing account is independent of one logical document database; this does not mean identities are global across instances or future projects |
| PostgreSQL UserStore | Authentication records use private system storage rather than application business collections |
| JSONB profile | Flexible user profile values without moving credentials into document APIs |
| Native arrays | Current `roles` and `db_admin` persist as PostgreSQL arrays |
| `github.com/lib/pq` | The driver already used by the current Go storage implementation |
| No Mongo UserStore | The current user persistence path is PostgreSQL; revocation remains a separate Mongo store |

These choices explain the existing module. They are not a decision to share one
user table across all Console developers, Management employees, or projects.
Project isolation needs an explicit schema and migration design.

## 3. Current Account Identity

The [current User type](../../../../../packages/syntrix/internal/core/storage/types/types.go)
contains the account ID, username, password hash/algorithm, timestamps,
disabled state, roles, database-admin grants, profile, and login/lockout state.
It has no project or logical database ownership field.

The store normalizes usernames to lowercase. Username uniqueness applies to
one current `auth_users` table. If ID is absent on creation, it generates
`hex(blake3(normalized_username)[:16])`, yielding 32 hexadecimal characters.
The schema allows up to 64 characters. That current deterministic generation
cannot be assumed suitable for two isolated projects with equal usernames;
future stable account IDs and external identity binding need their own design.
Existing IDs, profiles, roles, or database grants do not identify whether a
record should become a Console developer, employee, or project end user.

## 4. Current PostgreSQL Schema

The [user store](../../../../../packages/syntrix/internal/core/storage/postgres/user_store.go)
and [SQL definition](../../../../../packages/syntrix/internal/core/storage/postgres/migrations/001_create_users.sql)
own the current schema:

```sql
CREATE TABLE IF NOT EXISTS auth_users (
    id              VARCHAR(64) PRIMARY KEY,
    username        VARCHAR(255) NOT NULL,
    password_hash   TEXT NOT NULL,
    password_algo   VARCHAR(32) NOT NULL DEFAULT 'argon2id',
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    disabled        BOOLEAN NOT NULL DEFAULT FALSE,
    roles           TEXT[] NOT NULL DEFAULT '{}',
    db_admin        TEXT[] NOT NULL DEFAULT '{}',
    profile         JSONB NOT NULL DEFAULT '{}',
    last_login_at   TIMESTAMPTZ,
    login_attempts  INTEGER NOT NULL DEFAULT 0,
    lockout_until   TIMESTAMPTZ
);

CREATE UNIQUE INDEX IF NOT EXISTS idx_auth_users_username
    ON auth_users(username);
CREATE INDEX IF NOT EXISTS idx_auth_users_disabled
    ON auth_users(disabled) WHERE disabled = true;
```

There is no project column or OAuth client/provider/session schema in this
DDL. No foreign key or project-aware account mapping is added by this design
update. The current [database catalog](../database/03.schema.md) shares the
factory's PostgreSQL connection and keeps its existing owner fields.

## 5. Current Runtime Assembly

The [storage factory](../../../../../packages/syntrix/internal/core/storage/factory_impl.go)
opens the PostgreSQL connection, performs a context-aware connection check,
initializes user and database metadata schemas, and exposes their stores.
Mongo document and revocation stores use the same factory's configured Mongo
providers. The previously proposed `storage/auth_provider.go` is not the
current assembly owner.

The runtime `services.Manager` consumes that factory inside one instance.
It is separate from the external employee-facing Management platform.
Connection sharing does not merge the identity, catalog, and document module
responsibilities.

## 6. Current Storage Configuration

```yaml
storage:
  backends:
    instance_postgres:
      type: postgres
      postgres:
        dsn: postgres://syntrix:password@instance-postgres:5432/syntrix?sslmode=disable
        max_open_conns: 10
        max_idle_conns: 5
        conn_max_lifetime: 5m
  topology:
    user:
      strategy: single
      primary: instance_postgres
      collection: auth_users
```

This excerpt uses the existing `storage.backends`/`storage.topology` model;
it omits document/revocation bindings and is not a complete deployment file.
There is no separate current `storage.auth.postgres` configuration block.
See [storage architecture](01.architecture.md#22-current-configuration) for
the combined current topology.

## 7. Schema Initialization

Automatic PostgreSQL setup serializes authentication and database metadata DDL
across concurrent runtime processes sharing the instance system database. `CREATE TABLE IF NOT EXISTS` alone cannot prevent
concurrent catalog creation conflicts.

| Contract | Behavior |
|---|---|
| Coordination | One fixed transaction-level advisory lock per physical database, shared by user schema, database metadata schema, and independent user-index initialization |
| Transaction | Each initializer acquires the lock in an explicit `READ COMMITTED` transaction, then executes its table and index DDL on that transaction's connection |
| Visibility | Lock acquisition and DDL are separate commands; after waiting, DDL sees the preceding initializer's commit |
| Completion | Each initializer commits atomically; the Factory succeeds only after all required initializers succeed |
| Failure | Errors propagate; rollback releases the lock and undoes that initializer's DDL |
| Deadline | Connection checks, lock waits, and DDL use the Factory caller's context; standard CLI startup shares its existing 10-second initialization budget |
| Scope | The key is independent of DSN text and `search_path`; separate schemas in one physical database also serialize during initialization |

Normal CRUD uses no initialization advisory lock. Table and index definitions
and `search_path` resolution are preserved. Older binaries and external DDL must
participate in the lock protocol to receive its coordination guarantee.

See the [initialization decision](../../../../../.agents/notes/implemented/bug-fix/2026-09-15-postgres-concurrent-schema-initialization.md)
for the original failure, alternatives, and operational costs.

## 8. Target Migration Requirements

Project identity must remain independent of a single logical database so that
one project's users can access its multiple databases according to application
rules. It must also isolate equal usernames and external identities across
projects and instances. Account disablement, project deletion, database
cleanup, and instance retirement are distinct operations.

Delivering this target requires explicit account/project assignment, stable
identity and external-provider binding, OAuth/session persistence, active
session handling, and migration of current catalog ownership/grants. No
implicit default project, category inference, legacy fallback, new foreign
key, or token revocation SLA is defined here. See
[Identity architecture](../identity/01.architecture.md) for its domain design
and [catalog integration](../database/04.integration.md) for document namespace
and admission constraints.
