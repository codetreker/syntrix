# Multi-Database Storage

## 1. Goals and Implemented Scope

Logical databases share infrastructure by default. Explicit database fields,
database-aware document keys, and Store predicates keep their documents
separate. Selected databases can use dedicated Mongo backends to isolate load
and failures while the remaining databases use shared topology.

Document operations take a logical database explicitly. HTTP document APIs carry
it in the URL, as specified by the
[API URL structure](../../gateway/06.api-url-structure.md). User identity and
revocation remain global; document database routing does not make those records
database-scoped. The [Store interfaces](03.stores.md) own these signatures.

## 2. Document Identity and Physical Namespaces

The Mongo representation stores both:

- `database`, the logical database identifier;
- `_id = database + ":" + hash(fullpath)`, using the existing 128-bit path hash.

The key distinguishes equal paths in different databases and retains database
identity when a physical delete exposes only `documentKey._id`. It does not
encode the logical collection path. `collection`, `collection_hash`, and
`fullpath` retain that metadata in document images.

Ordinary logical collections share the configured `data_collection`. Paths
named `sys` or starting with `sys/` use `sys_collection`. These physical Mongo
collections can each contain records for multiple logical databases. Mongo's
physical database name and the logical `database` field have distinct roles.

CRUD and Query predicates scope data to the requested database. Soft deletion
marks a tombstone, clears business data, and schedules TTL cleanup; ordinary
reads exclude tombstones. Later physical removal is not another business
deletion; see [deletion semantics](03.stores.md#document-deletion-and-physical-cleanup).
The document Store's existing `EnsureIndexes` defines `(database, collection_hash)`
and `sys_expires_at` TTL indexes. Watch preserves the document-key format and
adds no change journal to CRUD writes; existing index setup retains its own
lifecycle.

## 3. Database and Operation Routing

The factory creates the default document topology from
`storage.topology.document`. Each explicit non-default entry in
`storage.databases` creates a single-store binding to its named backend.
Unlisted logical databases use the default topology while retaining their own
database predicates. Configuration validates the required `default` entry and
backend references; the default entry's backend does not override the document
topology's primary/replica selection.

The database router chooses placement before the operation router chooses a
Store. The shared `read_write_split` topology sends `OpRead` to the replica and
`OpWrite`/`OpWatch` to the primary. This keeps a watch on the authoritative write
source without changing ordinary read routing. `Get` with `ReadAuthoritative`
also selects `OpWrite` for the requested logical database and forwards its option
to the selected Store. Default and dedicated bindings therefore retain database
isolation while Push avoids replica reads for version decisions and conflict
lookups. Scans with `AtLeast` also select the authoritative source, whose adapter
validates the initial Watch boundary and supplies committed reads covering it.
Ordinary `Get`, `GetMany`, and `Query` retain their existing routing.
The [read contract](03.stores.md#11-documentstore) defines validation, backend
requirements, and the absence of locking or transaction guarantees.

Dedicated bindings currently select one Store for all operations. Their explicit
primary/replica configuration remains a
[proposed extension](../../../../../.agents/notes/proposed/architecture/2026-09-07-dedicated-backend-read-write-routing.md).
Changing a binding does not copy documents, transfer retained history, or migrate
checkpoints.

## 4. Watch Isolation and Recovery

```go
stream, err := store.Watch(ctx, "accounts", "orders", after, WatchOptions{})
```

This selects logical collection `orders` in database `accounts` through its
configured Store. An empty database fails. An empty collection selects that
database's ordinary collections in the data namespace; a system collection such
as `sys/rules` must be selected explicitly. A single watch does not discover
other databases or combine streams across dedicated backends. Mongo Watch
requires different physical names for `data_collection` and `sys_collection`.
An identical mapping returns `WatchUnsupported` before opening a cursor, so an
ordinary-collections watch cannot include system records. This Watch prerequisite
does not alter CRUD configuration handling.

Mongo filters document changes by the database prefix of the storage key and
validates available document metadata before emission. Physical cleanup produces
progress only, before image-dependent collection routing. Logical deletion copies
the existing StoredDoc collection and document ID into the event before clearing
`Document`. The Store requests available pre-images for routing and identity even
when `IncludeBefore` is false. If required metadata or non-delete enrichment is
absent, `WatchPayloadUnavailable` terminates the stream. The Store never emits an
event from an unknown collection or silently advances past a required payload.

`WatchCheckpoint` is an opaque, persistable Store-issued string. It binds the
physical source incarnation, logical database, collection selection, and
`IncludeBefore` to a source position. An initial `WatchStartForScan` checkpoint
also represents the committed scan lower bound and inclusive replay start; an
ordinary event checkpoint represents a completed source prefix. Neither can be reused for another database,
collection, or backend incarnation. Replacing the Store/client against the same
retained source preserves the binding. A dropped or recreated physical
collection, changed routing target, malformed checkpoint, or unavailable history
returns an explicit error; neither Store nor router silently restarts at the
present.

For a fresh watch, Mongo creates a missing selected physical collection so it
can establish a collection UUID and an initial checkpoint even while idle. This
can require collection-creation permission in addition to the metadata and
change-stream permissions needed for an existing source. Pre-images are not
enabled automatically, and source retention limits still apply.

`WatchStartCurrent` remains the default tail behavior. `WatchStartForScan` is an
explicit opt-in: retain C0 during ID-ordered committed scanning, then replay Watch
from the same C0. An actual replay read checks retained history; scanning does
not probe it on every page. Expiry can therefore require a fresh scan.

The [Watch contract](03.stores.md#2-document-watch) explains initial anchors,
ordered frames, payload limits, cancellation, and error handling. The
[Store Watch decision](../../../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md)
records why source identity and logical scope belong in the Store-issued
checkpoint.

## 5. Configuration Example

This excerpt defines a shared split topology and one dedicated document binding.
The global user and revocation topology settings are omitted from the excerpt.

```yaml
storage:
  databases:
    default:
      backend: shared_mongo
    accounts:
      backend: accounts_mongo
  backends:
    shared_mongo:
      type: mongo
      mongo:
        uri: mongodb://shared-primary:27017
        database_name: shared_data
    shared_replica:
      type: mongo
      mongo:
        uri: mongodb://shared-replica:27017
        database_name: shared_data
    accounts_mongo:
      type: mongo
      mongo:
        uri: mongodb://accounts-primary:27017
        database_name: account_data
  topology:
    document:
      strategy: read_write_split
      primary: shared_mongo
      replica: shared_replica
      data_collection: documents
      sys_collection: sys
      soft_delete_retention: 5m
```

A watch for `accounts` uses `accounts_mongo`. A watch for another logical database
uses `shared_mongo`; its ordinary reads use `shared_replica`. The document API
continues to pass the requested logical database in each case.

## 6. Migration and Integration Boundaries

Existing database-aware document keys are preserved. The Watch API replaces
untyped raw resume tokens with a strict Store-owned checkpoint encoding; there
is no runtime legacy-token inference. Any caller with persisted raw tokens must
establish an explicit migration or a deliberate new starting boundary and
account for the omitted history.

The current Puller still obtains Mongo clients directly from the storage
factory. Store Watch does not yet supply its ingestion, buffer, checkpoints, or
recovery. Store-level source/scope validation therefore does not establish
Puller durability, multi-backend aggregation, or consumer recovery. Those
separate decisions and their deferral costs are recorded in the
[Store Watch note](../../../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md#consequences).
