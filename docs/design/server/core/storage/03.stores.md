# Storage Interfaces and Data Model

## 1. Store Interfaces

Application services use Store interfaces independently of the backend and its
routing topology. Document operations take an explicit logical database; user
identity and token revocation remain global services.

### 1.1. DocumentStore

```go
type DocumentStore interface {
    Get(ctx context.Context, database string, path string, opts ...ReadOptions) (*StoredDoc, error)
    GetMany(ctx context.Context, database string, paths []string, opts ...ReadOptions) ([]*StoredDoc, error)
    Create(ctx context.Context, database string, doc StoredDoc, opts ...CreateOptions) error
    Update(ctx context.Context, database string, path string, data map[string]interface{}, pred model.Filters) error
    Patch(ctx context.Context, database string, path string, data map[string]interface{}, pred model.Filters) error
    Delete(ctx context.Context, database string, path string, pred model.Filters) error
    DeleteByDatabase(ctx context.Context, database string, limit int) (int, error)
    Query(ctx context.Context, database string, q model.Query) ([]*StoredDoc, error)
    Watch(ctx context.Context, database string, collection string, after WatchCheckpoint, opts WatchOptions) (WatchStream, error)
    Close(ctx context.Context) error
}
```

`Create` accepts at most one `CreateOptions{Condition, ExpectedVersion}` value.
Routing forwards it to the database's write source. Conditions are enforced by
the write, since an initial read alone cannot protect against concurrent changes.

| Create options | Atomic behavior |
|---|---|
| Omitted or zero value | Insert, or replace a still-deleted tombstone; live occupancy returns an existence error |
| `Condition: absent` | Pure insert; live and tombstone occupancy both conflict |
| `Condition: tombstone`, nonnegative `ExpectedVersion` | Replace only a retained tombstone with that version; no upsert |

`ExpectedVersion` is required only for the tombstone condition. A supplied version
with another mode, an unsupported condition, or multiple options values fails
validation. Failed conditions preserve the existing record; unrelated storage
errors propagate. The expected version constrains the old tombstone and does not
set the recreated document's metadata. The
[create-condition decision](../../../../../.agents/notes/implemented/feature/2026-09-07-replication-push-insert-only.md)
owns the choice and its generation/physical-cleanup limits.

`GetMany` preserves input order and returns a nil entry for a missing document.
`DeleteByDatabase` returns the number deleted; a positive limit bounds the batch.
The [multi-database design](05.multi-database.md) describes namespace selection
and isolation.

`Get` and `GetMany` accept at most one `ReadOptions` value. `Consistency` selects
read routing independently of `ShowDeleted`:

| Mode | Behavior |
|---|---|
| Omitted or `ReadDefault` | Preserve configured ordinary read routing |
| `ReadAuthoritative` | Read from the logical database's write source |
| Unsupported mode or multiple options values | Return an error |

Authoritative selection and read failures propagate without replica fallback.
`ShowDeleted` includes retained tombstones; its default excludes them. These
options provide no document lock, transaction, or linearizable-read guarantee.
Mutations must retain their atomic predicates.

The Mongo adapter uses a per-call collection clone with primary read preference
for authoritative reads. This requires a writer-capable topology: a direct
connection pinned to a secondary is not made writer-capable by the read
preference. Shared read settings remain intact.

The [HTTP Push decision](../../../../../.agents/notes/implemented/bug-fix/2026-09-07-http-push-version-preconditions.md)
records why Push uses authoritative reads. Its initial and conflict lookups also
include tombstones, as required by the
[conditional-write decision](../../../../../.agents/notes/implemented/bug-fix/2026-09-07-replication-push-version-checks.md).

`ReadOptions.MaxBytes` bounds one `Get` or `GetMany` result; zero disables the
bound and negative values fail validation. The shared accounting unit is the
canonical BSON-encoded complete StoredDoc, independent of adapter selection.
Nil positions cost zero; duplicate result positions each consume the document's
bytes. Included tombstones count; filtered tombstones do not. Exceeding the bound
returns `ErrReadBudget` with no partial result.

The Mongo adapter checks raw row bytes, including requested multiplicity, before
decoding/accumulating a row and then checks canonical bytes before admitting the
decoded document. Raw driver response batches retain their driver/wire bounds;
this option bounds application materialization, not the driver's response buffer.
Adapters may conservatively charge native record overhead. Routing preserves the
same byte bound together with consistency and deletion visibility.

### 1.2. Source scanning and collection enumeration

`DocumentScanner.ScanDocuments` supplies bounded raw candidates for one concrete
logical collection. Requests select consistency, an exclusive logical document
ID (`AfterID`), a positive candidate limit, and an optional byte budget. The
returned rows include tombstones, which consume both budgets. `NextAfter` is the
last candidate's logical ID, including a deleted candidate. A full page does not
prove exhaustion; `Exhausted` is true only after a short page. Exceeding the byte
budget returns `ErrSourceScanBudget` without a partial result.

`SourceScanRequest.AtLeast` accepts only the initial checkpoint issued by
`WatchStartForScan` for this exact source, database, and collection. A nonempty
value selects the authoritative source and requires committed reads covering
that boundary. Ordinary event checkpoints are rejected. Pages remain moving
reads: a later page can observe later committed writes, so callers retain the
original boundary and replay from it after scanning. Neither a primary read
preference nor ordinary `ReadAuthoritative` alone establishes this guarantee.

Mongo restores the boundary's causal session context and uses majority reads.
Source identity and ordered-scan index readiness are checked for the physical
collection incarnation; replacement or unavailable indexes fail explicitly.
Scanning does not probe retained change history on each page. Actual Watch
consumption checks history when replay begins, so expiry can require repeating
an otherwise completed scan.

`DocumentCollectionEnumerator.EnumerateCollections` supplies bounded concrete
collection names from the authoritative source, including collections containing
only tombstones. `afterCollection` is exclusive, names use binary order, and a
short page proves exhaustion. `IncludeSystem` includes system collections;
ordinary enumeration excludes them. Neither operation establishes a snapshot
across calls. Indexed queries and bootstrap combine these source operations with
explicit progress and readiness checks; see
[offline bootstrap and startup](../../indexer/04.storage.md#offline-bootstrap-and-startup).

The Mongo adapter requires a nonunique ascending
`{database, collection, fullpath}` index with simple collation in both configured
data and system collections. Index creation failures propagate. Scanning uses
that index, simple collation, and bounded cursor batches; collection enumeration
uses indexed seeks. Candidate byte accounting uses the source BSON record size.
These adapter constraints keep ordered source access bounded without a blocking
sort or an unbounded distinct query.

The [indexed-query filter decision](../../../../../.agents/notes/implemented/bug-fix/2026-09-07-indexed-query-filter-semantics.md)
owns the source-candidate and logical-identity requirements.

## 2. Document Watch

Document Watch exposes an ordered stream with explicit progress and terminal
failures:

```go
type WatchCheckpoint string

type WatchOptions struct {
    IncludeBefore bool
    StartMode     WatchStartMode
    MaxAwaitTime  time.Duration
}

type WatchFrame struct {
    Event      *Event
    Checkpoint WatchCheckpoint
    CaughtUp    bool
    SourceBytes int64
}

type WatchStream interface {
    InitialCheckpoint() WatchCheckpoint
    Next(context.Context) (WatchFrame, error)
    Close() error
}
```

### 2.1. Scope and start boundary

`database` is required. An empty `collection` watches that database's ordinary
logical collections in the selected data namespace. A nonempty collection
selects exactly that logical collection, including nested paths. System
collections require an explicit selection such as `sys/rules`; an empty
collection does not include the system namespace. One call selects one source
through the [document router](04.routers.md), without discovering or aggregating
other databases or backends.

An empty `after` uses `WatchStartCurrent` by default: a source-established current
boundary excluding earlier changes. `WatchStartForScan` explicitly establishes
an overlapping committed scan/replay boundary C0. It requires an empty `after`.
A successful Watch returns a nonempty `InitialCheckpoint()` even on an idle
source. Neither mode enumerates existing documents or holds a historical snapshot.

| Start or continuation | Meaning |
|---|---|
| `WatchStartCurrent` | Tail changes from the current source boundary |
| `WatchStartForScan` | Obtain C0 for `ScanDocuments.AtLeast` and inclusive replay |
| Resume C0 with default start mode | Replay including its committed boundary |
| Resume an event/progress checkpoint | Continue after its completed source prefix |

Resumption confirms the exact supplied checkpoint. Mongo's private C0 records
a majority-committed time and causal session context, and starts replay inclusively
at that time. Scan pages restore this context across clients and service instances.
Native event and cursor tokens take over once replay advances. This overlap covers
writes committed while scanning without relying on wall-clock document timestamps.

The Store owns checkpoint encoding. Callers may persist and transmit a
`WatchCheckpoint` as a string, but must not parse it, synthesize one, or compare
its bytes to determine order. A checkpoint is bound to the source incarnation,
logical database, collection selection, and options. Replacing a client, Store,
or Puller instance preserves resumability against the same retained source;
changing the source, scope, or `IncludeBefore` requires a deliberate new watch.
Invalid checkpoints and unavailable history return errors without resetting the
stream to the present.

`MaxAwaitTime` controls one source poll, not the lifetime of `Next`. Zero preserves
the one-second default; an explicit value must be at least one millisecond. It is
not checkpoint scope, so a resumed caller may change its polling interval.

### 2.2. Ordered processing and ownership

Each successful `Next` returns a nonempty checkpoint. `Event == nil` represents
ordered source progress without a document change, including progress past
excluded events or an idle batch. A progress frame may repeat the current
checkpoint. Save a frame's checkpoint only after its event, when present, and
all preceding required work have completed successfully. Receiving a frame does
not establish downstream durability or acknowledge a consumer's work.

`CaughtUp` means an accepted source prefix has reached a fixed committed target.
A successful empty batch alone is insufficient: filters can empty a batch while
the source still has earlier relevant changes to return. Mongo captures a committed
target when a resumed watch has no unfinished target, retains it in private
checkpoints across pages, and validates progress through a real nonzero-batch read.

| Mongo topology | Empty-read proof after preceding frames have been delivered |
|---|---|
| Direct replica set | Native progress timestamp is at least the committed target; transaction expansion drains before returning a pause |
| Mongos | Native progress timestamp is strictly beyond the target; equality can leave same-timestamp shard batches buffered |

Initial scan C0 carries no catch-up target. Resuming it after scanning captures a
new target, so reaching the pre-scan boundary alone cannot complete bootstrap.
Mongo's periodic no-op records allow idle sharded streams to move beyond the target
without application writes; disabling that progress mechanism can prevent idle
completion. Filters, cancellation, elapsed time, and page limits never substitute
for the proof. `SourceBytes` counts raw source bytes returned for
the frame, including filtered events; it does not measure all database work.
Consumers own page budgets and must retain the previous accepted checkpoint if
a fetched event cannot fit their response.

Target establishment adds a committed source read and topology/target checks.
Replay uses native batches of at most 100 documents; the driver retains its own
wire-byte limits. Mongo obtains the comparison target from a zero-batch native
probe at T for a replica set or the timestamp immediately after T for mongos,
then closes the probe. The adapter retains this native token rather than parsing
or constructing its ordering fields. A fresh default tail watch uses its initial
native head as the target, retaining its zero-batch start and avoiding this extra
boundary-read/probe sequence.

`Event.Id` remains the affected document's storage key. `Event.ChangeID`
identifies the source change and is stable when that change is replayed or read
through another watch of the same source. Neither identity is an ordered
checkpoint. `Event.Timestamp` is Unix nanoseconds; the Mongo adapter uses source
cluster time with second precision. It is metadata, not a resume position.
Backend-native resume tokens belong to the Store implementation and do not
appear in the shared `Event` type.

`Event.Database`, `Collection`, and `DocumentID` carry the existing StoredDoc
logical identity independently of its payload. The adapter copies that metadata
before constructing a documentless delete; it does not change StoredDoc identity
or recover a path by reversing the storage-key hash.

Callers serialize `Next` calls. Returned frames remain valid after subsequent
reads. Canceling the context supplied to `Watch` or to a `Next` terminates the
subscription; later reads retain its terminal error. `Close` can interrupt a
blocked read and is idempotent. It owns only that subscription, leaving the
Store connection and other watches available. The Mongo implementation gives
native cursor cleanup a five-second timeout and returns cleanup failures.

### 2.3. Event payloads and Mongo prerequisites

`Document` is committed document enrichment for create/update events; lookup may
observe state newer than the source change, including a tombstone. State consumers
inspect `Document.Deleted`; `Event.Type` describes the source operation rather
than a later lookup state. `IncludeBefore` exposes a genuine source pre-image
when available, without guaranteeing retained historical before/after payloads.
Logical deletes retain `EventDelete` and nil `Document`, with separate logical
identity. Physical removal produces progress only, before image-dependent routing.

The Mongo implementation requires distinct physical data and system collection
names. If both settings select the same collection, `Watch` returns
`WatchUnsupported` before opening a cursor, because an ordinary-collections
watch could otherwise include system records. This prerequisite is enforced by
Watch; it does not change CRUD configuration handling.

The Mongo implementation keeps the existing `database:hash(fullpath)` document
keys. Their hash cannot recover the logical collection path. The implementation requests
available pre-images internally even when `IncludeBefore` is false, so it can
route using source metadata. If neither a pre-image nor document enrichment
provides the metadata needed to establish collection membership, the stream
fails with `WatchPayloadUnavailable`. Missing enrichment for a non-delete event
also fails explicitly. Unknown membership is never treated as another
collection or silently skipped.

A missing current image may still identify a logical deletion when the source
update explicitly establishes deletion and a valid before-image supplies identity.
That image's business data is never treated as current state. Other missing
required payloads or identities terminate the stream, allowing consumers to
require resynchronization without silently advancing past the change.

Mongo pre-images are not enabled automatically. Operators must supply the source
capability and retained metadata needed for their selected scope; an optional
`Before` field is not a substitute for those routing prerequisites. Source
errors, malformed events, and cleanup errors remain visible to callers.

A Mongo watch reads the physical collection UUID and verifies that it remains
the same while opening the cursor. On a fresh watch, a missing selected physical
collection is created to establish that identity, including on an empty logical
database. Existing namespaces require metadata and change-stream read
permissions; creating one may additionally require collection-creation
permission. Permission failures are returned. Resuming a missing or replaced
collection fails with a source mismatch.

### 2.4. Failure categories and migration

`WatchError` carries a backend-independent code, logical database and collection,
and the original cause. `errors.As` exposes the category; `errors.Is` continues
to identify cancellation, deadlines, and other wrapped causes.
The error's displayed text excludes the backend cause, which can contain source
tokens or document data; callers must avoid logging sensitive unwrapped causes.

| Code constant | Meaning |
|---|---|
| `WatchInvalidScope` | Required watch scope is absent or invalid |
| `WatchInvalidCheckpoint` | The checkpoint encoding or continuation is invalid |
| `WatchScopeMismatch` | The checkpoint belongs to another logical scope or option set |
| `WatchSourceMismatch` | The source incarnation differs or has been invalidated |
| `WatchHistoryUnavailable` | The requested upstream history is unavailable |
| `WatchPayloadUnavailable` | Required event enrichment or scope metadata is unavailable |
| `WatchInvalidEvent` | The source event is malformed or cannot be represented |
| `WatchUnsupported` | Required watch capabilities or distinct physical data/system namespaces are unavailable |
| `WatchPermissionDenied` | Source authentication or authorization failed |
| `WatchSourceUnavailable` | The source or cursor failed for another reason |

The former channel API accepted an untyped raw token and had no public durable
codec. Callers migrate to the Store-issued `WatchCheckpoint` and explicit frame
processing. The Mongo decoder validates its versioned envelope strictly and
does not guess legacy encodings. Persisted raw tokens need an explicit migration
or deliberate new starting boundary; discarding an invalid token cannot claim
continuous recovery.

The scan-boundary extension uses a new private Mongo envelope version. Earlier
envelopes are rejected explicitly; there is no silent conversion or fresh-head
fallback. Consumers with saved earlier checkpoints must deliberately establish
a new boundary and rebuild the state whose continuity they can no longer prove.

The [Store Watch decision](../../../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md)
records source identity, alternatives, and the separate Puller integration work.
The [scan-boundary extension](../../../../../.agents/notes/implemented/architecture/2026-09-15-watch-scan-boundary.md)
owns committed scanning, logical deletion identity, and source watermarks.

## 3. Internal Document Model

The default Mongo document representation is:

| Field | Stored meaning |
|---|---|
| `_id` | String `database:hash(fullpath)`, using the 128-bit path hash |
| `database` | Explicit logical database identifier |
| `fullpath` | Full document path |
| `collection` | Parent logical collection path |
| `collection_hash` | Compact hash used in database/collection indexes |
| `parent` | Parent of the collection |
| `data` | Typed document content |
| `version` | Optimistic concurrency version |
| `updated_at`, `created_at` | Unix millisecond document timestamps |
| `deleted` | Soft-delete flag |
| `sys_expires_at` | TTL cleanup deadline for a tombstone |

The Mongo Store directs ordinary paths to the configured data collection and
`sys` or `sys/...` paths to the configured system collection. Logical collection
paths share these physical namespaces.

### Document deletion and physical cleanup

| Deletion kind | Stored change | Business meaning |
|---|---|---|
| Syntrix document deletion | Update to a retained tombstone | Logical deletion notification |
| Mongo physical document deletion | Remove the stored record, including expired tombstones | No business deletion notification |

```text
Syntrix delete -> tombstone -> logical deletion notification
                     |
                physical cleanup -> no second notification
```

| Tombstone field | Change on logical deletion |
|---|---|
| Document identity, database, path, collection, parent, creation time | Retained |
| `data` | Cleared to `{}` |
| `deleted` | Set to `true` |
| `version`, `updated_at` | Advance version and modification time |
| `sys_expires_at` | Set the cleanup deadline |

- Ordinary reads exclude tombstones; replication can expose retained tombstones.
- Default Create may replace a retained tombstone, requiring a still-deleted
  target atomically and checking that it matched. Explicit tombstone creation
  additionally matches its expected version; absent creation cannot replace it.
  A concurrent live recreation cannot be overwritten by a stale replacement.
- Update/Delete atomically match a live document and any supplied version predicate;
  a tombstone or physically missing target cannot satisfy that mutation.
- Cleanup requires an applicable retention policy and TTL index; a deadline alone does not guarantee physical removal.
- A tombstone does not retain former business fields or provide a historical before-image.
- Database purge can physically remove live records without per-document tombstone transitions.

| Event boundary | Logical deletion | Physical deletion |
|---|---|---|
| Puller native capture | Preserve the tombstone update or replacement | Filter the source `delete` operation |
| Business conversion | Deliver logical `delete` with the tombstone | Ignore the physical operation |
| Store Watch | `EventDelete`, `Document=nil`, retained logical identity | Progress only |

Store Watch and Puller native capture are separate inputs. Puller filters physical
deletion before buffering; business conversion also ignores a physical operation
if supplied directly. Store Watch advances past cleanup without emitting a second
business deletion. Suppressing cleanup must not suppress Syntrix logical deletion.

## 4. RoutedStore

`RoutedDocumentStore` implements the same interface and delegates to the selected
Store. Ordinary reads use `OpRead`; `Get`, `GetMany`, and source scans with
`ReadAuthoritative`, collection enumeration, and mutations use `OpWrite`. Read
options are forwarded to the selected Store, and watches use `OpWatch`. Source
capabilities remain explicit: a selected Store that lacks scanning or enumeration
returns an error.
Scans with nonempty `AtLeast` use `OpWatch` to select the same authoritative source regardless of
ordinary read routing; the selected adapter validates the boundary's source and
scope and applies its committed-read guarantee.
The distinct watch operation keeps checkpoints tied to the authoritative write
source under read/write splitting. Database and operation routing errors
propagate to the caller. Closing the facade does not close shared providers;
the factory owns their lifecycle.
