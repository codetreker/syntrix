# Storage Routing Strategy

## 1. Purpose

Routing selects a Store from the logical database and operation. It separates
backend placement from Store execution so callers use the same API with a shared
backend, a dedicated database binding, or read/write splitting.

A watch has its own operation kind because a continuation belongs to a specific
source incarnation. Selecting an independently configured ordinary read replica
could change that source even though CRUD reads remain valid.

## 2. Router Interfaces

The routing interfaces are:

```go
type OpKind int

const (
    OpRead OpKind = iota
    OpWrite
    OpMigrate
    OpWatch
)

type DocumentRouter interface {
    Select(database string, op OpKind) (DocumentStore, error)
}

type UserRouter interface {
    Select(database string, op OpKind) (UserStore, error)
}

type RevocationRouter interface {
    Select(database string, op OpKind) (TokenRevocationStore, error)
}
```

`OpMigrate` remains an operation value; it does not provide a migration or
dual-write implementation. Document operations use the caller's database.
The user and revocation facades use the global `default` routing selection;
their Store methods do not take a logical database.

## 3. Database Selection

`DatabaseDocumentRouter` first selects the router configured for the database.
An unlisted database uses the configured default router. If no router is
available, selection returns an error. This placement fallback does not change
the logical database passed to the Store.

`RoutedDocumentStore.Watch` rejects an empty database before selecting
`OpWatch`. It delegates the original collection, checkpoint, and options to the
selected Store. The facade neither opens additional sources nor aggregates
checkpoints across backends.

The factory constructs dedicated document bindings as single-store routers.
Their configurable read/write topology remains owned by the
[dedicated-backend proposal](../../../../../.agents/notes/proposed/architecture/2026-09-07-dedicated-backend-read-write-routing.md).
The [multi-database design](05.multi-database.md) owns configuration and isolation.

## 4. Operation Strategies

### 4.1. Single

A single router returns the same Store for every operation. Driver-managed
replica selection can still exist within that Store's connection.

```yaml
storage:
  topology:
    document:
      strategy: single
      primary: default_mongo
```

### 4.2. Read/Write Split

| Operation | Selected Store |
|---|---|
| `OpRead` (ordinary `Get`, `GetMany`, `Query`) | Configured replica |
| `OpWrite` (mutations, authoritative reads, and collection enumeration) | Configured primary |
| `OpWatch` (Watch and scans with `AtLeast`) | Configured primary |
| `OpMigrate` | Configured primary |

```yaml
storage:
  topology:
    document:
      strategy: read_write_split
      primary: default_mongo
      replica: default_mongo_replica
```

These are topology excerpts; the [multi-database design](05.multi-database.md)
describes backend bindings and physical collection settings.
The split router performs a pointer selection without I/O or health-based
failover. Ordinary reads retain the consistency of the configured replica;
using the primary for Watch does not make those reads current with an event.
`Get` validates its optional `ReadOptions` and routes `ReadAuthoritative` through
`OpWrite`, forwarding the option to the selected Store. Selection/read errors
propagate without replica fallback. This selects the write source without locking
data or establishing a transaction or linearizable-read guarantee; see the
[read contract](03.stores.md#11-documentstore).

`ScanDocuments` with a nonempty `AtLeast` selects `OpWatch`, even with default
read consistency. The facade forwards the original boundary and budgets. The
selected adapter checks scope/source identity and applies committed reads covering
that initial scan boundary. Routing alone does not establish that guarantee.

### 4.3. Future Sharding

Application-level shard selection is not implemented. It would require routing
inputs that identify the shard and a policy for watching multiple sources;
MongoDB can manage its own sharded deployment behind a single configured Store.

## 5. Watch Continuity and Lifecycle

The selected Store validates that a checkpoint belongs to its current source,
logical database, collection selection, and options. Moving a binding to another
source does not migrate its checkpoint or its data. A source/scope mismatch or
unavailable history is returned to the caller; routing never retries with an
empty checkpoint or substitutes another backend.

The same source validation applies to `ScanDocuments.AtLeast`. The caller retains
the initial C0 while scanning and resumes Watch from it afterward. Routing does
not aggregate checkpoints or maintain a server-side client session. Changing
service instances is safe when the selected source and retained history remain
the same; changing a source binding requires explicit recovery.

A successful Watch returns one subscription owned by its caller. Closing that
stream releases its cursor while the shared Store and providers remain
available. The factory owns provider shutdown. The
[Watch contract](03.stores.md#2-document-watch) and
[decision note](../../../../../.agents/notes/implemented/architecture/2026-09-08-store-watch-contract.md)
own progress processing, failure categories, and source identity.
