# Physical Backend Ownership and Borrowed Adapters

## 1. Responsibilities

`core/storage.Backends` owns named physical backend connections inside one
runtime process. It constructs configured Mongo providers and the PostgreSQL
pool selected by user topology, checks connectivity with the startup context,
and closes those resources once
after consumers stop. A backend name identifies connection ownership, not a
logical Syntrix database or a project identity realm.

Modules borrow those handles to construct their adapters. The document/catalog
factory owns document routing and catalog assembly. Identity runtime owns
credential and revocation repository assembly. Sharing one PostgreSQL pool or
Mongo provider does not merge their records, permissions, or lifecycle policy.

## 2. Providers and Adapters

The physical Mongo provider remains under `core/storage/mongo`; the coordinated
PostgreSQL schema helper remains shared infrastructure under
`core/storage/postgres/schema`. Identity user and revocation adapters live under
`identity/repository/postgres` and `identity/repository/mongo`. Their concrete
constructors accept already-owned handles rather than creating new providers.

The document store interfaces and routers remain under `core/storage`.
Credential repository contracts are owned by `identity/repository`; a common
storage `AuthProvider` is not the assembly or shutdown authority.

Required repository/catalog schema initialization completes before their
constructors return usable capabilities. Existing explicit index initialization
remains separate where not invoked by construction. Failure propagates without
disconnecting a borrowed handle. Identity repositories have no physical Close operation; the
process Manager closes Backends after consumers stop.

## 3. Current and Target Storage

Current users and database metadata remain in PostgreSQL; token revocation
remains in MongoDB with its existing TTL and routing behavior. The extraction
introduces no Redis dependency, replacement storage policy, or project schema.
The accepted target still places project/OAuth/session system records in
instance-local PostgreSQL. Its migration and revocation consistency need their
own design.
