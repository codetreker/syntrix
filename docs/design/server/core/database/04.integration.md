# Instance Catalog Integration with Document Operations

**Status:** Current admission paths and accepted project-aware target; no project-aware API or namespace migration is implemented by this document.
**Scope:** Database resolution, status checks, document authorization, and realtime/replication identity inside one Syntrix instance.

## 1. Instance and Project Boundaries

The [platform architecture](../../../../architecture.md) separates Management
employees, Console developers, and instance application end users. Developers
manage instance resources through Console; Management coordinates authorized
platform scheduling and lifecycle operations; each instance executes its own
catalog and data operations. Project and database configuration remain in its
private PostgreSQL system database. MongoDB holds business documents for the
logical Syntrix databases exposed to the developer.

In the accepted target, projects belong to instances, every project has an
isolated end-user identity realm, and one project can use multiple databases.
Instance Identity authenticates those users and handles OAuth/OIDC alongside
Indexer and Puller. A project login is not a developer Console login or an
employee Management login.

The current catalog has no project field and uses existing instance user
ownership and admin claims. The target requires an explicit project/database
binding and authorization design. It does not follow automatically from the
current `owner_id` or database path string.

## 2. Current Public Data Paths

| Operation | Existing path |
|---|---|
| Read/create/replace/update/delete document | `/api/v1/databases/{database}/documents/{path...}` |
| Query | `POST /api/v1/databases/{database}/query` |
| Replication Push | `POST /replication/v1/databases/{database}/push` |
| Legacy realtime | Database selected by the existing websocket protocol |
| Bound replication | Database namespace plus expected metadata identity according to the replication contract |

The current catalog accepts either a slug or `id:<metadata-id>`. Metadata
resolution and the document namespace are separate:

```text
URL namespace:                 my-app-prod
Resolved catalog metadata ID:  a1b2c3d4e5f67890
Physical MongoDB database:     configured backend database_name
```

The catalog row may be placed in request context while the document handler
continues to pass `my-app-prod` downstream. Resolving the slug does not by
itself change persisted document keys, index scope, backend bindings, or
checkpoints. An ID-prefixed request likewise cannot be assumed to address
an already-canonical namespace. Any change to this contract needs an explicit
stored-data and consumer migration.

## 3. Current Gateway Admission

### 3.1 Ordinary Document Requests

The [route registration](../../../../../packages/syntrix/internal/gateway/rest/handler.go)
wraps ordinary document operations with catalog validation, configured
authentication, and document authorization. Catalog validation currently sits
outside those authentication wrappers; this document does not promise that
an unauthenticated caller always receives 401 before any catalog error.
Authentication can also be disabled by the existing runtime configuration.

The [validator](../../../../../packages/syntrix/internal/gateway/rest/middleware_database.go):

1. Reads the URL `database` value and rejects an empty identifier.
2. Calls `ResolveDatabase`, which resolves slug/ID through the metadata cache
   and checks active status.
3. Stores the resolved catalog entity in context for downstream code.
4. Translates status/not-found errors or propagates a storage failure as an
   internal error.

`withDatabaseValidation` currently passes through if no validator is configured.
This is an implementation condition, not a target guarantee that unregistered
project databases are supported.

### 3.2 Current Document Authorization

Ordinary document handlers use the existing identity rule evaluator.
`authorized` builds auth claims from request context and uses the raw URL
namespace for resource lookup and rule evaluation. When the resolved catalog
owner matches the caller, it can add the metadata ID to `db_admin` in the
request authorization context. This does not rewrite that raw namespace.

Catalog CRUD ownership checks, `db_admin`, and document security rules have
separate purposes. Their presence does not prove complete database-level
access control for every route. In particular, the ordinary unbound Query
route currently uses authentication and catalog validation without the same
per-document rule wrapper. A bound Query follows the replication admission
path below. These current differences must not become an assertion that every
end user can access every project database or that Query already enforces the
accepted project boundary.

### 3.3 Bound Replication and Reads

The [replication admission helper](../../../../../packages/syntrix/internal/gateway/replication/authorization.go)
requires the resolved owner or a `db_admin` grant matching the metadata ID or
slug. A role string alone is not sufficient. The expected metadata identity
binds an existing namespace to a particular catalog incarnation and prevents
silent replacement after slug reuse.

Bound REST reads use `X-Syntrix-Expected-Database-Identity` and the shared
replication authorization path before document prefetch or replacement identity
disclosure. The identity value is a metadata ID; the request namespace remains
the existing document namespace. Authoritative admission can call
`ResolveDatabaseAuthoritative` to bypass metadata caches. See
[replication](../../gateway/replication.md) for the complete current wire,
authorization, and recovery contract.

## 4. Metadata Cache and Errors

The [cache](../../../../../packages/syntrix/internal/core/database/cache.go)
uses mutex-protected maps for metadata by ID, slug-to-ID lookups, and negative
lookups keyed by `id:` or `slug:`. It stores positive and negative results with
separate TTLs and evicts expired/oldest-expiring entries when capacity is
exceeded. It is not an LRU implementation.

Creation seeds the row and clears matching negative entries. Update and delete
invalidate local positive entries. `Warm` preloads active rows, but uses the
store's paginated List limit; it is not a guarantee that the entire catalog is
preloaded. Storage failures propagate and are not converted into not-found
negative entries.

| Validator condition | Current HTTP response |
|---|---|
| Empty identifier | 400 `BAD_REQUEST` |
| Missing row | 404 `DATABASE_NOT_FOUND` |
| Suspended row | 403 `DATABASE_SUSPENDED` |
| Deleting row | 410 `DATABASE_DELETING` |
| Storage/lookup failure | 500 internal error |

Example response structure:

```json
{
  "error": {
    "code": "DATABASE_SUSPENDED",
    "message": "Database 'my-app-prod' is suspended"
  }
}
```

Cache invalidation is local to the service process; it does not broadcast
suspension/deletion to other Gateways or already-admitted sessions. The
low-level cache and runtime configuration have separate negative-TTL defaults,
as described in [configuration](01.architecture.md#33-current-configuration).
TTL values are not a token revocation SLA or a platform-wide lifecycle barrier.

## 5. Realtime and Internal Service Admission

Legacy realtime and bound replication have distinct entry and continuation
contracts. Bound replica operations reauthorize using the shared database
identity model. Store Watch checkpoints separately bind the document namespace,
physical source, selected collection, and payload options. Neither a websocket
upgrade nor a cached initial status check establishes project membership or a
permanent right to continue after a lifecycle change.

Internal Query, Puller, Streamer, and Indexer calls carry database namespaces
for their current operations. That does not make an arbitrary caller-supplied
user ID or admin flag a trusted platform authority. The target must define
which service authenticates each caller, verifies instance/project/database
scope, and enforces changes on active subscriptions. Gateway validation alone
is not a universal proof that every internal call received that authorization.
The timing and transport of those target checks remain design decisions.

## 6. Target Admission Requirements and Migration

Routes that require authentication must authenticate the caller before
returning database existence or lifecycle-status information. An
unauthenticated caller must receive 401 Unauthorized before a missing,
suspended, or deleting database can be disclosed. After authentication,
admission resolves the database, checks its active status, evaluates the
applicable authorization policy, and executes the operation. Routes explicitly
configured for public access or optional authentication retain their own
admission policy. The current middleware ordering in Section 3.1 is an
implementation gap against this authentication-required ordering.

Project-aware admission must verify the selected instance, the project's
identity realm, the database's project binding, active lifecycle state, and
application permissions. Developer management operations need separate
Console ownership checks and authenticated coordination with Management and
the instance. Identity does not acquire ownership of all platform resources
because it issues end-user tokens.

The migration must explicitly map current users, catalog ownership, slugs,
document namespaces, index state, routing, and persisted client identities.
No default project, legacy claim fallback, guessed user category, silent
namespace normalization, or log-only acceptance phase is specified here.
Schema/API changes and handling of active sessions are separate implementation
work; the confirmed architecture does not settle their policy.

## 7. Validation Requirements

Validation must cover active/missing/suspended/deleting resolution, underlying
storage failures, local cache hits and invalidation, authoritative reads,
owner and explicit-grant admission, metadata replacement after slug reuse,
and existing document namespace preservation. Concurrent updates and cache
state across multiple Gateway processes require dedicated integration checks.

The target must verify that authentication-required routes return 401 without
disclosing missing/suspended/deleting database state, while public and
optional-authentication routes follow their configured policy. The project-aware
target additionally needs tests that reject credentials from another project
or account category and permit one project's users to access its multiple
databases according to application rules. Long-lived websocket
and replication behavior must match the eventual lifecycle/revocation policy.
Cache-hit latency and hit-rate estimates require measurement; no benchmark
results are asserted by this design document.
