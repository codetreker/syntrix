# Observability Pipeline and Controls

Status: target pipeline contracts; not an existing complete collector deployment.

## Product boundary and rationale

The [system architecture](../../architecture.md) and
[boundary decision](../../../.agents/notes/proposed/architecture/2026-10-10-platform-console-instance-boundaries.md)
separate employee Management, developer Console, and application instances.
Common OTel transport and schemas support investigation across these services;
publisher and reader authorization retain their distinct authorities.

The pipeline must keep business traffic independent of export health, bound
telemetry cost/cardinality, and preserve correlation at the operation's actual
scope. Current runtime metrics and local Grafana do not deliver fleet Management,
the developer Console, or project-realm isolation.

## Topology and collectors

Services and SDKs send OTLP over HTTP/gRPC to regional collectors. Local
collection can use a DaemonSet; regional processing retains at least two replicas
and consistent trace routing for tail sampling. Prometheus stores metrics,
Tempo/Jaeger traces, and Loki/ClickHouse logs. Alertmanager owns notification
routing; Grafana provides authorized views and exemplar drill-down.

Collector responsibilities:

- Receive authenticated OTLP; receive Prometheus self-metrics where appropriate.
- Batch at a target 200 ms / 5,000 spans to reduce chatter.
- Normalize resources and validate applicable scope without fabricating a
  database/project for unrelated platform work.
- Tail-sample 100% errors, 100% operations exceeding their latency target, and
  10% healthy baseline traffic. Explicit high-volume head sampling and scoped
  overrides require documented bounds.
- Apply resource-scoped rate caps, such as a proposed 200 spans/second database
  budget, without making database scope mandatory for every operation.
- Use a memory limiter targeting 30% of pod memory with safety margin and bounded
  queues that evict the oldest queued telemetry first when capacity is exceeded. Export failures record retries/drops and never block business requests.
- Export metrics by Prometheus remote-write, traces by TLS OTLP, and redacted
  structured logs to the chosen backend. Partition logs by their applicable
  instance/project/database or platform scope.
- Expose health, pprof, and zpages only under the operational access policy;
  authenticate services with mTLS or scoped publisher credentials.

These parameters are design targets, not current YAML configuration keys.

## Instrumentation and correlation

Common resources identify service name/version, deployment environment, and
region. Instance work carries instance identity, project/realm work carries
project identity, and database work carries database identity. Employee fleet
operations and developer account operations can have no project/database scope.
Validate correlation against the resolved operation/resource, not untrusted
client labels.

Propagate W3C trace context; baggage may carry safe resolved resource context or
query-plan correlation. Spans add request IDs, actor authority, permitted
principal identifiers, and applicable HTTP route/method, database operation, or
messaging fields. Trace/span IDs are per-work correlation, not metric labels.

Metrics use RED (`http_server_duration_seconds`, request/error totals), USE
(resource/pool/queue utilization), and domain measures for replication lag,
trigger dispatch, query planning, storage latency, and Identity outcomes. Labels
are bounded service/route/status/operation dimensions; authorized resource
slices must fit configured cardinality budgets.

Structured logs contain timestamp, severity, service, category, message,
applicable resource and request/trace/span context, and structured error details.
Redact secrets/tokens, hash sensitive IDs when raw values are unnecessary, and
validate schemas. A log without database context can be valid platform or
instance lifecycle telemetry.

## Alerting, views, and runbooks

SLO examples cover API availability 99.9%, realtime 99.5%, CRUD p95 below 200 ms,
query p95 below 400 ms, replication lag p95 below 5 seconds, and trigger success
above 99%. Page on 2h/6h burn above 14x; warn on 1h/24h above 2x. Guardrail alerts
cover queues, dropped spans/logs, scrape/export failures, missing exemplars, and
sampling/request-rate mismatch.

Templates include runbook/owner, deploy revision, relevant resource/endpoint, and
trace links. Management views cover fleet health/capacity and MTTR/MTTD/cost;
Console views cover only developer-owned/delegated instances and their
project/database slices. Service views retain RED/USE and dependencies.

Runbooks guide deployment checks, burn-rate review, trace/log pivots, authorized
mitigation, and incident timelines. Post-incident changes update sampling,
alerts, and missing instrumentation. The operations runbook location remains a
future delivery rather than a current directory contract.

## Security and delivery

Rotate publisher credentials; enforce TLS and schema/redaction checks. Separate
employee, developer, and application reader permissions, enforce resource-aware
access in dashboards/backends, and audit telemetry queries. Customer export must
include only the authorized instance's telemetry.

Validate instrumentation and collector schemas in staging, add exemplars/rules,
then canary production in one region with scoped caps before expansion. Log
backend/archive choice, Console embedding versus link-outs, custom SLOs, and
customer-provided OTLP destinations remain open decisions.
