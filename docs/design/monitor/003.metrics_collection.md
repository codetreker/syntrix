# In-Process Metrics Collection

Status: proposed shared registry and metric catalogue; current Puller metrics are implemented.

## Scope and current behavior

The [monitoring architecture](001.architecture.md) specifies the telemetry
pipeline; this document owns in-process collection and Prometheus exposition.
The [system architecture](../../architecture.md) and
[boundary decision](../../../.agents/notes/proposed/architecture/2026-10-10-platform-console-instance-boundaries.md)
separate employee Management, developer Console, and application instances.

The Go runtime has Puller Prometheus collectors under
`packages/syntrix/internal/puller/metrics/`. Trigger has a metrics interface and a
no-op implementation. The shared `internal/core/metrics` package, complete
Gateway/Query/Indexer/Streamer catalogue, and gateway metrics mounting described
here remain proposals. A configured Prometheus scrape target does not prove the
runtime exposes that endpoint or emits this catalogue.

Instance metrics describe runtime services, business-document MongoDB, and
private system PostgreSQL. The latter currently stores users and database
metadata; target project/realm, OAuth/client/provider, and session state are not
implemented. Developer Console and employee fleet Management instrumentation
belongs to those separate future services, not to `services.Manager`.

## Registry and exposition decisions

Use a custom `prometheus.Registry` per process with injectable registerer/gatherer
and an HTTP exposition handler. This isolates tests, avoids global `init`
registration conflicts, and permits selective Go/process collectors. Duplicate
registration remains visible. The intended package owns registry/configuration,
HTTP middleware, common-label validation, and service-specific collectors.

The proposed instance exposition uses the existing network listener, avoiding a
new port. Standalone has Gateway; distributed processes need their own supported
exposition registration when Gateway is absent. A runtime metrics listener does
not become a developer Console or employee Management endpoint. Exposition
access in production requires its own operational authorization decision.

Use histograms for latency so measurements aggregate across processes/instances.
The proposed HTTP latency buckets in seconds remain:

```go
[]float64{0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10}
```

## Names, labels, and scope

Names follow `{namespace}_{subsystem}_{name}_{unit}`; counters use `_total` and
latencies use `_seconds`. Service resources identify version, region,
environment, and process. Instance operations carry instance identity; project
or Identity-realm operations carry project identity; database operations carry
database identity. Fleet scheduling, developer profile operations, and instance
startup can have no database context. Validate relevant scope at collection;
do not invent a default database for unrelated work.

Metric labels use bounded method, normalized route, status/class, and operation
values. Instance/project/database slices require explicit cardinality budgets;
the earlier recommendation of ten values is useful for enums, not a limit of
ten databases in the product. Never put document, user, request, or session IDs
in labels. Trace/log context supplies permitted per-request and actor correlation.

## Proposed service metric catalogue

The tables preserve domain names/types for implementation planning. Their
`database` dimensions apply to database work; resolved instance/project scope
must be available when that work is aggregated across instances. Collectors must
not attach database labels to unrelated platform/Identity lifecycle metrics.

## Configuration and assembly contract

The proposed registry controls enablement, HTTP path, namespace, and optional Go
and process collectors. These are future metrics-module concepts; no current
`metrics` configuration block is introduced by this document.

The instance process manager would construct one registry, create service metrics,
inject them into runtime services, and register exposition with the unified
server. `services.Manager` owns that process assembly, not global Management.
Request middleware records bounded method/route/status and duration while
preserving existing response-writer flushing/hijacking behavior. Service metrics
record domain operations at their owning layer to avoid double counting.

Instance Identity instrumentation includes authentication outcomes and bounded
issuer/provider flow outcomes when those features are implemented. Project
realm correlation must come from validated context. Developer account metrics
belong to Console; employee resource/scheduling metrics belong to Management.
The same metric mechanism does not establish shared token authority.

## Delivery and testing

Implement the registry/exposition contract, then Gateway HTTP metrics, then
Query/Indexer/Streamer collectors, Puller registry migration, and the Trigger
backend. Synchronize dashboards and documentation with actual emitted names,
units, and semantics. These are pending deliveries, not current phases claimed
complete.

Unit checks cover isolated registration, duplicate conflicts, label validation,
and exposition format. Integration checks cover supported metrics routes,
operation increments, scraping, disabled collectors, and separate service
processes. Scope checks distinguish fleet/developer/instance/project/database
operations and reject untrusted identifiers without rejecting valid non-database
signals. Cardinality, overhead, and telemetry-failure behavior require observed
load measurements.

## Open decisions and references

Batch-job Pushgateway support, separate registries for particular isolation
needs, and production metrics authorization remain open. Resolve each against
runtime deployment and operational access requirements.
